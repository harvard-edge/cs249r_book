Scaling to 1000 GPUs

At 1024 GPUs, communication overhead is the cost everyone talks about. Is it the dominant one?

fleet
advanced
Sweep from 8 to 1024 GPUs and discover which overhead actually dominates at scale. The answer is not what most engineers expect.

The Question

A team has Llama-3.1-70B (70.6B parameters) and a budget for 1024 NVIDIA H100 GPUs. Communication overhead (AllReduce, pipeline bubbles) will consume some of the scaling efficiency, as every distributed-training engineer expects. How do communication overhead and cluster reliability evolve as the fleet scales from 8 to 1024 GPUs over a 30-day training run?

NotePrerequisites

Complete Tutorial 0: Hello, Roofline and Tutorial 1: The Memory Wall. This tutorial assumes familiarity with memory-bound vs. compute-bound regimes and the roofline model.

NoteLearning Objectives
  • Calculate scaling efficiency across GPU counts from 8 to 1024
  • Predict cluster Mean Time Between Failures (MTBF) using the reliability model
  • Compare communication overhead vs. checkpoint overhead over a 30-day training run
  • Explain how checkpoint I/O and failure rollbacks scale with cluster size
TipBackground: Cluster Reliability and the Young-Daly Formula

At scale, hardware failures are not rare events; they are routine. In the MLSys Zoo, a single GPU has a Mean Time To Failure (MTTF) of 50,000 hours, a NIC has an MTTF of 150,000 hours, and a PSU has an MTTF of 100,000 hours. A cluster of \(N\) GPUs alone has a collective MTBF of \(\text{MTTF} / N\) (97.7 hours at 512 GPUs). Including all node components (8 GPUs, 8 NICs, and 0 non-redundant PSUs per DGX H100 node) lowers the cluster MTBF to 73.2 hours at 512 GPUs and 36.6 hours at 1024 GPUs.

To survive failures, training jobs checkpoint periodically: save the full model state (weights + optimizer) to storage. The Young-Daly formula gives the optimal checkpoint interval that minimizes total wasted time:

\[T_{\text{opt}} = \sqrt{2 \cdot \delta \cdot M}\]

where \(\delta\) is the time to write one checkpoint and \(M\) is the cluster MTBF. This assumes failures arrive as a Poisson process (exponentially distributed inter-arrival times) and that on failure, work since the last checkpoint is lost (on average, half the checkpoint interval). The cost of checkpointing is therefore not only the write time but also this rollback time.

1. Setup

import mlsysim
from mlsysim import Engine

2. Single-Node Baseline

The simplest case is 8 GPUs in a single DGX H100 node (450 GB/s intra-node NVLink per direction), with no cross-node data-parallel traffic. This configuration sets the ceiling for scaling efficiency.

from mlsysim import Models, Systems
from mlsysim.solvers import DistributedModel
from mlsysim.systems.types import Fleet, Node, NetworkFabric
from mlsysim.core.units import Q_
from mlsysim.show import table, info

model = Models.Language.Llama3_70B
solver = DistributedModel()

# Single DGX H100 node: 8 GPUs, NVLink interconnect
single_node = Fleet(
    name="Single Node",
    node=Systems.Nodes.DGX_H100,
    count=1,
    fabric=Systems.Fabrics.InfiniBand_NDR
)

baseline = solver.solve(
    model=model, fleet=single_node,
    batch_size=64, precision="fp16", tp_size=8, pp_size=1
)

info("Single-Node Baseline",
     GPUs=single_node.total_accelerators,
     Compute_latency=baseline.node_profile.latency.to('ms'),
     Communication=baseline.communication_latency.to('ms'),
     Scaling_efficiency=f"{baseline.scaling_efficiency:.1%}")
── Single-Node Baseline ────────────────────
GPUs:                8
Compute latency:     14,037.3 ms
Communication:       2,674.7 ms
Scaling efficiency:  84.0%

With 8 GPUs on a single node at batch size 64, compute takes 14,037.3 ms and intra-node tensor-parallel AllReduce over NVLink takes 2,674.7 ms, yielding a baseline scaling efficiency of 84.0%.

This tutorial uses the three dimensions of 3D parallelism:

  • TP (Tensor Parallelism) = 8: splits each layer’s weight matrices across 8 GPUs within a node, communicating via NVLink (450 GB/s)
  • PP (Pipeline Parallelism) = 1: no pipeline stages (the model is not split across sequential stages), so no pipeline bubbles
  • DP (Data Parallelism) = \(N / 8\): each node processes different data batches, synchronizing gradients via AllReduce over IB NDR (400 Gbps)

Setting PP=1 isolates the communication vs. reliability comparison cleanly. Real production systems often use PP > 1 for models too large to fit on one node with TP alone, which introduces pipeline bubble overhead (idle time proportional to \(1/\text{PP}\) stages).

3. Scale Sweep: 8 to 1024 GPUs

The sweep below covers cluster sizes from 8 to 1024 GPUs. At each scale, it measures communication overhead (intra-node TP AllReduce plus inter-node DP AllReduce) and scaling efficiency.

gpu_counts = [8, 32, 64, 128, 256, 512, 1024]

rows = []
results = {}
for n_gpus in gpu_counts:
    n_nodes = n_gpus // 8
    fleet = Fleet(
        name=f"{n_gpus}-GPU Cluster",
        node=Systems.Nodes.DGX_H100,
        count=n_nodes,
        fabric=Systems.Fabrics.InfiniBand_NDR
    )
    # Use TP=8 within node, DP across nodes
    r = solver.solve(
        model=model, fleet=fleet,
        batch_size=max(64, n_gpus),
        precision="fp16", tp_size=8, pp_size=1
    )
    results[n_gpus] = r
    rows.append([
        n_gpus, n_nodes,
        f"{r.communication_latency.to('ms').magnitude:.1f}",
        f"{r.pipeline_bubble_latency.to('ms').magnitude:.1f}",
        f"{r.scaling_efficiency:.1%}"
    ])

table(["GPUs", "Nodes", "Comm (ms)", "Bubble (ms)", "Efficiency"], rows)
GPUs  Nodes  Comm (ms)  Bubble (ms)  Efficiency
───────────────────────────────────────────────
8         1     2674.7          0.0       84.0%
32        4     1199.9          0.0       74.5%
64        8      954.1          0.0       64.8%
128      16      998.3          0.0       63.8%
256      32     1020.5          0.0       63.3%
512      64     1031.9          0.0       63.0%
1024    128     1038.0          0.0       62.9%

Once the global batch scales linearly with GPU count from 64 GPUs (954.1 ms AllReduce, 64.8% scaling efficiency) to 1024 GPUs (1,038.0 ms AllReduce, 62.9% scaling efficiency), ring AllReduce bandwidth utilization stabilizes and scaling efficiency degrades gradually. This is Amdahl’s Law in action: if the serial fraction (communication) is \(f\), the maximum speedup at \(N\) GPUs is \(1 / (f + (1-f)/N)\).

This communication analysis, however, assumes that every node stays healthy for the entire 30-day training run. Communication is not the whole story.

4. The Reliability Reveal

A separate question is how often a 64-GPU, 512-GPU, or 1024-GPU cluster experiences a hardware failure. The ReliabilityModel computes cluster-level MTBF, expected failures, optimal checkpoint intervals, and steady-state goodput.

from mlsysim.solvers import ReliabilityModel

rel_solver = ReliabilityModel()

rows = []
rel_results = {}
for n_gpus in gpu_counts:
    n_nodes = n_gpus // 8
    fleet = Fleet(
        name=f"{n_gpus}-GPU",
        node=Systems.Nodes.DGX_H100,
        count=n_nodes,
        fabric=Systems.Fabrics.InfiniBand_NDR
    )
    # 30-day training run, 60-second checkpoint write time
    r = rel_solver.solve(fleet=fleet, job_duration_hours=30*24, checkpoint_time_s=60.0)
    rel_results[n_gpus] = r
    mtbf_h = r.fleet_mtbf.to("hour").magnitude
    rows.append([
        n_gpus, n_nodes,
        f"{mtbf_h:.1f} h",
        f"{r.expected_failures:.1f}",
        f"{r.optimal_checkpoint_interval.to('hour').magnitude:.1f} h",
        f"{r.goodput_ratio:.1%}"
    ])

table(["GPUs", "Nodes", "Cluster MTBF", "Failures/30d", "Optimal Ckpt", "Goodput"], rows)
GPUs  Nodes  Cluster MTBF  Failures/30d  Optimal Ckpt  Goodput
──────────────────────────────────────────────────────────────
8         1      4687.5 h           0.2        12.5 h    99.9%
32        4      1171.9 h           0.6         6.2 h    99.7%
64        8       585.9 h           1.2         4.4 h    99.6%
128      16       293.0 h           2.5         3.1 h    99.4%
256      32       146.5 h           4.9         2.2 h    99.2%

At 64 GPUs, the cluster MTBF is 585.9 h (1.2 expected failures over 30 days, 4.4 h optimal checkpoint interval, 99.6% steady-state goodput). At 512 GPUs, the cluster MTBF drops to 73.2 h (9.8 failures over 30 days, 1.6 h optimal checkpoint interval, 98.8% goodput). At 1024 GPUs, MTBF reaches 36.6 h, with 19.7 expected failures in 30 days, an optimal checkpoint interval of 1.1 h, and 98.3% steady-state goodput. Every checkpoint pauses training, and every failure rolls back to the last checkpoint, discarding all work in between.

5. The Hidden Cost: Communication vs. Checkpoints

The comparison below tracks how total time lost over a 30-day (720-hour) training run evolves across cluster sizes for both unoverlapped communication overhead and synchronous checkpoint plus rollback overhead.

from mlsysim.solvers import CheckpointModel

ckpt_solver = CheckpointModel()
job_hours = 30 * 24  # 30 days

rows = []
for n_gpus in [64, 256, 512, 1024]:
    dist_r = results[n_gpus]
    rel_r = rel_results[n_gpus]

    # Communication overhead per step as fraction of step time
    comm_fraction = 1.0 - dist_r.scaling_efficiency
    comm_loss_hours = comm_fraction * job_hours

    # Checkpoint overhead: write time per checkpoint + rollback from failures
    ckpt_r = ckpt_solver.solve(
        model=model, hardware=Systems.Nodes.DGX_H100.accelerator,
        optimizer="adam", checkpoint_interval_hours=rel_r.optimal_checkpoint_interval.to("hour").magnitude
    )
    ckpt_write_s = ckpt_r.write_time_seconds.to("second").magnitude
    ckpt_interval_h = rel_r.optimal_checkpoint_interval.to("hour").magnitude

    # Number of checkpoints in 30 days
    n_checkpoints = job_hours / ckpt_interval_h if ckpt_interval_h > 0 else 0
    total_ckpt_write_h = n_checkpoints * ckpt_write_s / 3600

    # Rollback cost: each failure loses ~half the checkpoint interval on average
    avg_rollback_h = ckpt_interval_h / 2
    total_rollback_h = rel_r.expected_failures * avg_rollback_h

    total_ckpt_loss_h = total_ckpt_write_h + total_rollback_h
    ratio = total_ckpt_loss_h / comm_loss_hours if comm_loss_hours > 0 else 0

    rows.append([n_gpus, f"{comm_loss_hours:.1f}", f"{total_ckpt_loss_h:.1f}", f"{ratio:.2f}x"])

table(["GPUs", "Comm Loss (h)", "Ckpt Loss (h)", "Ckpt/Comm"], rows)
GPUs  Comm Loss (h)  Ckpt Loss (h)  Ckpt/Comm
─────────────────────────────────────────────
64            253.4            9.1      0.04x
256           264.6           18.2      0.07x
512           266.4           25.8      0.10x
1024          267.4           36.4      0.14x
ImportantKey Insight

While ring AllReduce overhead plateaus with cluster size, reliability overhead grows as \(\sqrt{N}\). Between 64 and 1024 GPUs, unoverlapped communication loss changes by only 5.5% (from 253.4 h to 267.4 h over 720 hours), whereas synchronous checkpoint I/O and failure rollback losses grow 4.0× (from 9.1 h at 64 GPUs to 36.4 h at 1024 GPUs, or 14% of the unoverlapped communication loss). When DP communication is overlapped with backward computation, checkpoint I/O and failure recovery become the primary scaling bottleneck.

6. The Checkpoint Size Problem

Checkpoint overhead is costly because modern models produce large checkpoint files. The cell below computes the checkpoint size for Llama-3.1-70B with the Adam optimizer:

ckpt_result = ckpt_solver.solve(
    model=model,
    hardware=Systems.Nodes.DGX_H100.accelerator,
    optimizer="adam",
    checkpoint_interval_hours=1.0
)

info("Checkpoint Analysis",
     Model=model.name,
     Checkpoint_size=ckpt_result.checkpoint_size.to('GB'),
     Write_time=ckpt_result.write_time_seconds.to('second'),
     MFU_penalty_1h=f"{ckpt_result.mfu_penalty_pct:.2%}",
     Storage_bottleneck=ckpt_result.storage_bottleneck)
── Checkpoint Analysis ─────────────────────
Model:               Llama-3.1-70B
Checkpoint size:     988.4 GB
Write time:          141.2 s
MFU penalty 1h:      3.92%
Storage bottleneck:  True

A single mixed-precision Adam checkpoint for Llama-3.1-70B (70.6B parameters at 14 bytes per parameter) is 988.4 GB and requires 141.2 s of synchronous storage write time. At a 1-hour interval, checkpoint I/O alone imposes a 3.92% MFU penalty.
