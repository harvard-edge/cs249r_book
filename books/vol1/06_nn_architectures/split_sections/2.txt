## Architectural Principles {#sec-network-architectures-architectural-principles-engineering-tradeoffs-362e}

The dense multilayer perceptron (MLP) of @sec-neural-computation paid for a weight between every pixel and every hidden unit, including relationships an image rarely needs. Matrix multiplication, activation functions, and gradient computation form the "verbs" of neural networks, and architectures remove that waste by assembling the same verbs into computational graphs\index{Architecture!computational graph} shaped like the data. Under the silicon contract (principle \ref{pri-silicon-contract}), that shape is also an implicit agreement with hardware, trading computational patterns for efficiency on particular problem classes.

::: {.column-margin}
![](images/svg/nn_architectures_inductive_bias.svg){width="100%" fig-alt="Vertical list of three architectures with a dark-to-light dot ramp: CNN (darkest, strong spatial prior), Transformer (mid), MLP (lightest, no structural prior), ordered by inductive-bias strength."}

*Inductive bias from strong (convolutional) to weak (fully connected): stronger prior, less data needed.*
:::

Every neural network architecture decides how computation should be organized to match the inherent structure in the data. Images have spatial locality, language has sequential dependencies, and tabular records often lack a fixed spatial or sequential organization. The architecture encodes assumptions about these patterns directly into the computational graph, and those assumptions influence parameter count, hardware utilization, and deployment feasibility. Architecture selection is therefore a systems engineering problem\index{Architecture!systems engineering} that directly affects the iron law terms: the number of operations $\Operations$ and the volume of data movement $\DataVolume$. The structural assumptions that each architecture encodes are known as **inductive biases**\index{Inductive bias!definition},[^fn-inductive-bias-architecture] and they serve as the unifying concept for this entire chapter.

[^fn-inductive-bias-architecture]: **Inductive bias**\index{Inductive bias!etymology}\index{Inductive bias!systems consequence}: From Latin *inducere*, "to lead into," encoding a structural assumption "leads" the model toward a smaller solution space, which is why this concept unifies the entire chapter: every architecture discussed here—multilayer perceptron (MLP), convolutional neural network (CNN), recurrent neural network (RNN), and transformer—is defined by its choice of bias. A CNN's locality bias cuts parameters by orders of magnitude vs. an equivalent MLP, directly shrinking the iron law's $O$ and $\DataVolume$ terms, while global attention trades quadratic score computation for long-range connectivity.

```{python}
#| echo: false
from mlsysim import *
from mlsysim.core.units import *

# ┌─────────────────────────────────────────────────────────────────────────────
# │ INDUCTIVE BIAS LOCALITY PARAMETER REDUCTION
# ├─────────────────────────────────────────────────────────────────────────────
# │ Context: Inductive bias definition quantitative significance.
# │
# │ Goal: Keep the CNN-vs.-MLP locality ratio computed at its first use.
# │ How: Compare an ImageNet-sized dense input connection with a 3x3 RGB filter.
# │
# └─────────────────────────────────────────────────────────────────────────────
from mlsysim.fmt import fmt_int, fmt, fmt_qty_int, check, fmt_memory, fmt_bandwidth, fmt_flop_rate, fmt_power

class InductiveBiasLocalityCalc:
    """ImageNet-sized locality-bias parameter reduction for one feature detector."""

    # ┌── 1. LOAD (Constants) ──────────────────────────────────────────────
    img_dim = 224
    img_channels = 3
    kernel = 3

    # ┌── 2. EXECUTE (The Compute) ────────────────────────────────────────
    dense_input_weights = img_dim * img_dim * img_channels
    local_filter_weights = kernel * kernel * img_channels
    spatial_locality_reduction = dense_input_weights / local_filter_weights

    # ┌── 3. GUARD (Invariants) ──────────────────────────────────────────
    check(spatial_locality_reduction > 5_000, f"Expected ImageNet locality reduction above 5,000x, got {spatial_locality_reduction:.1f}x.")

    # ┌── 4. OUTPUT (Formatting) ─────────────────────────────────────────────
    spatial_locality_reduction_mult_str = fmt_multiple(spatial_locality_reduction, precision=1, commas=True)
```

::: {#dfn-nn-architectures-inductive-bias .callout-definition title="Inductive bias"}

***Inductive bias***\index{Inductive bias!definition} is a structural constraint built into a model architecture that restricts the hypothesis space, enabling generalization from finite data by encoding domain-specific assumptions (such as spatial locality or sequential ordering) directly into the computational graph.

1.  **Significance**: Inductive bias can reduce the dataset size $(\DatasetSize)$ required for generalization. For one output feature detector over $N_{\text{pix}}$ pixel positions with $C_{\text{in}}$ input channels, a dense connection uses $\mathcal{O}(N_{\text{pix}} C_{\text{in}})$ parameters, while a shared $K{\times}K$ CNN filter uses $\mathcal{O}(K^2 C_{\text{in}})$ parameters and is applied at every position, costing $\mathcal{O}(N_{\text{pix}} K^2 C_{\text{in}})$ operations. For a $224{\times}224$ RGB image, a shared $3{\times}3$ filter therefore uses roughly `{python} InductiveBiasLocalityCalc.spatial_locality_reduction_mult_str` fewer parameters than one dense feature detector, reducing parameter storage and often the data required to avoid overfitting.
2.  **Distinction**: Unlike regularization (which penalizes hypothesis complexity at training time via L1/L2 terms), inductive bias restricts the hypothesis space at architecture design time: a CNN represents nonlocal functions less directly than local patterns, while regularization discourages complexity through the training objective.
3.  **Common pitfall**: A frequent misconception is that stronger inductive bias is always better. A strong locality bias (CNN) excels on spatial data but represents long-range dependencies in language less directly than global attention, which supports long-range dependencies at $\mathcal{O}(\SequenceLength^2)$ score-computation cost.

:::

A convolutional neural network (CNN) encodes an inductive bias of spatial locality: nearby pixels matter more than distant ones. A transformer lets each element attend to any other, enabling long-range relationships at quadratic score-computation cost. These biases help architectures learn efficiently by restricting the space of functions they represent. Without an appropriate bias, a model may require substantially more data and compute to learn the same structure. The unified framework in @sec-network-architectures-architecture-selection-framework-a442 brings these architectural families together once each bias has appeared in practice.

Machine learning systems face a core engineering trade-off: **representational power vs. computational efficiency**\index{Architecture!representational power vs. efficiency}. Under the iron law of ML systems (principle \ref{pri-iron-law}), architectural choice is the primary determinant of the operation-count term $\Operations$. A transformer's attention mechanism enables global relationships but scales as $\mathcal{O}(\SequenceLength^2)$ operations with sequence length $\SequenceLength$; a CNN exploits spatial locality to reduce operations to linear scaling in the number of spatial positions. Matching the right inductive biases to a workload's data while setting a manageable operation-count budget defines the practice of neural architecture selection.

::: {#exmp-nn-architectures-netflix-prize-ensemble .callout-example title="The ensemble Netflix did not ship (2009)"}

**Context**: Netflix awarded its \$1M Grand Prize in 2009 for a 10 percent improvement in recommendation accuracy [@johnston2012netflixprize].

**Mechanism**: Bringing the winning improvement into production required substantial engineering effort just as Netflix's business was shifting from mailed DVDs to streaming. That shift also produced richer viewing signals and changed what personalization needed to optimize.

**Impact**: The additional accuracy did not justify the production effort, so Netflix did not deploy the Grand Prize code.

**Fix**: Netflix retained two algorithms from the earlier Progress Prize and redirected its recommendation work toward streaming-era personalization.

**Systems lesson**: An offline metric gain is only valuable when its integration cost and objective still match the production system.

:::

Choosing an architectural backbone sets the primary memory layout and compute pattern for downstream hardware. @Tbl-architecture-families contrasts the five major neural network families across their spatial/temporal inductive biases, tensor operations, and memory access characteristics.

Five specific model architectures recur throughout this book as lighthouse models: consistent reference points that ground abstract concepts in concrete systems reality. These examples are concrete implementations of the Workload Archetypes (such as Compute Beast and Bandwidth Hog). The two vision lighthouses sit on or near the empirical Pareto frontier\index{Pareto frontier} plotted in @fig-efficiency-frontier, which bounds ImageNet top-1 accuracy against logarithmic compute cost (GMACs per image); the other three were chosen for the bottlenecks they isolate: memory bandwidth, memory capacity, and an always-on power envelope.

These models serve as canonical workloads for understanding system constraints. The empirical Pareto frontier in @fig-efficiency-frontier illustrates how each architecture family occupies a distinct computational cost regime. The plotted curve should be read as a historical trajectory of the trade-off between representational power and computational efficiency, not as a controlled benchmark rerun. It isolates the progression from architectures that prioritize raw accuracy to those that minimize operations (GMACs) for constrained environments, and onward to models that trade substantial compute for flexible, long-range modeling. Architectural choices made at design time determine where a system lands on this frontier.
