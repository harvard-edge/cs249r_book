### Algorithmic structure {#sec-network-architectures-algorithmic-structure-8468}

Meeting the dynamic routing requirements of @sec-network-architectures-pattern-processing-needs-4b64 requires a formal operator that maps variable-length sequences to content-dependent affinity weights [@bahdanau2015neural]. The transformer architecture implements this mapping via the scaled dot-product attention operator introduced by @vaswani2017:
$$
\text{Attention}(\mathbf{Q}, \mathbf{K}, \mathbf{V}) = \text{softmax}
\left(\frac{\mathbf{Q}\mathbf{K}^T}{\sqrt{\AttentionHeadDimension}}\right)\mathbf{V}
$$

The inputs $\mathbf{Q}$ (queries), $\mathbf{K}$ (keys), and $\mathbf{V}$ (values)[^fn-attention-qkv-projections] are learned linear projections of the token representations ($\mathbf{Q} = \mathbf{X}\mathbf{W}_Q$, $\mathbf{K} = \mathbf{X}\mathbf{W}_K$, $\mathbf{V} = \mathbf{X}\mathbf{W}_V$). Attention uses three separate projection matrices rather than computing dot-product affinities directly between raw tokens ($\mathbf{X}\mathbf{X}^T$) for two architectural reasons:

1.  **Asymmetric relationships**: Direct token dot products $\mathbf{x}_i \cdot \mathbf{x}_j$ are strictly commutative ($\mathbf{x}_i \cdot \mathbf{x}_j = \mathbf{x}_j \cdot \mathbf{x}_i$). However, linguistic and contextual relationships are fundamentally asymmetric: in "the chef cooked the meal," the verb "cooked" must attend forward to find its direct object ("meal"), while "meal" plays a receptive role. Decoupling into query (what information a token seeks) and key (what features a token advertises) allows $\mathbf{q}_{\text{cooked}} \cdot \mathbf{k}_{\text{meal}}$ to be high while $\mathbf{q}_{\text{meal}} \cdot \mathbf{k}_{\text{cooked}}$ remains low.
2.  **Decoupling routing from content**: The dot products $\mathbf{Q}\mathbf{K}^T$ determine *where* to look (routing coefficients), while the value projection $\mathbf{V}$ determines *what* information to retrieve. Without a separate value projection, a token acting as a strong structural signpost (such as a preposition or punctuation mark) would force its entire raw embedding into downstream layers. Projecting through $\mathbf{W}_V$ allows the network to strip away irrelevant lexical identity and extract only task-relevant features.

For an input sequence of length $\SequenceLength$ projected to the head dimension $\AttentionHeadDimension$ (the full width $\HiddenDimension$ when there is one head), the dot product $\mathbf{Q}\mathbf{K}^T$ computes all $\SequenceLength^2$ pairwise token similarities. Scaling by $1/\sqrt{\AttentionHeadDimension}$ prevents dot products from growing large in magnitude at high dimensions, which would push softmax into regions with vanishingly small gradients. The softmax operator[^fn-softmax-normalization-reduction] normalizes each row of the score matrix into a probability distribution over key positions. Finally, multiplying these normalized weights by $\mathbf{V}$ produces output vectors formed as weighted combinations of the value representations.

[^fn-softmax-normalization-reduction]: **Softmax**\index{Softmax function!systems}: Named as a "soft" (differentiable) version of argmax, with mathematical roots in Boltzmann's statistical mechanics, softmax normalizes each query row over all $\SequenceLength$ scores and therefore requires a reduction over each row. Online softmax lets that reduction run over tiles with running statistics, which is why it need not force quadratic storage (@sec-network-architectures-memory-requirements-72c3). \index{Softmax function!quadratic bottleneck}

[^fn-attention-qkv-projections]: **Query-key-value (QKV)**\index{Attention mechanism!query-key-value}\index{Query-key-value}: The terminology is borrowed from information retrieval, explaining why the equation uses three distinct learned projections to calculate pairwise scores. Creating these projections requires three independent weight matrices, costing $3 \times \HiddenDimension^2$ parameters per layer. The direct systems consequence is the "KV cache"\index{QKV!KV cache} for autoregressive inference: all prior key and value vectors must be stored for the next token, causing memory to grow linearly ($\mathcal{O}(\SequenceLength)$) with sequence length and potentially dominate serving memory at long contexts or high concurrency.

::: {.column-margin .margin-pointer}
↪ The dot product as a similarity measure is developed in @sec-appdx-algorithm-foundations-dot-product-similarity-7957.
:::

Each row of the resulting $\SequenceLength{\times}\SequenceLength$ matrix determines how strongly an individual token attends to every token in the sequence. In a trained model, the largest affinity values reflect strong contextual dependencies, while near-zero entries suppress irrelevant positions.

While attention weights vary dynamically with the input tokens, generating the query, key, and value vectors requires static linear projections against learned parameter matrices. In accelerator implementations, these three operations are fused into a single batched matrix multiplication to maximize tensor core saturation and eliminate kernel launch overhead. @Fig-attention-weightcalc diagrams this fused projection: multiplying the $6{\times}768$ token embedding matrix by the packed $768{\times}2304$ weight matrix and adding the bias vector produces a concatenated $6{\times}2304$ output tensor in a single kernel pass.

```{python}
#| echo: false
#| label: qkv-projection-costs

# ┌─────────────────────────────────────────────────────────────────────────────
# │ QKV PROJECTION COSTS
# ├─────────────────────────────────────────────────────────────────────────────
# │ Context: @fig-attention-weightcalc caption
# │
# │ Goal: Derive MAC count for the combined QKV projection.
# │ Show: 6 * 768 * 2304 = 10.6 million MACs.
# │ How: Matrix multiplication dimensions from the figure.
# │
# └─────────────────────────────────────────────────────────────────────────────

from mlsysim.fmt import fmt_int, fmt, fmt_count, check

# ┌── LEGO ───────────────────────────────────────────────
class QKVProjectionCosts:
    """MAC count for a 6-token GPT-2-style combined QKV projection."""

    # ┌── 1. LOAD (Constants) ──────────────────────────────────────────────
    tokens = 6
    d_model = 768
    qkv_dim = 2304

    # ┌── 2. EXECUTE (The Compute) ────────────────────────────────────────
    qkv_macs = tokens * d_model * qkv_dim
    qkv_macs_m = qkv_macs / MILLION

    # ┌── 3. GUARD (Invariants) ──────────────────────────────────────────
    check(qkv_macs == 10_616_832, f"QKV projection MAC count should be 10,616,832, got {qkv_macs}.")

    # ┌── 4. OUTPUT (Formatting) ─────────────────────────────────────────────
    qkv_macs_str = fmt_count(qkv_macs, scale="million", scale_style="word", precision=1, commas=False, label="MAC")
```
