### Computational mapping {#sec-network-architectures-computational-mapping-824c}

Translating mathematical convolution into hardware execution requires bridging the gap between high-level software interfaces and silicon execution pipelines. High-level frameworks abstract convolution as a unified layer dispatch, shown in @lst-conv_layer_spatial. Behind this concise API, the underlying runtime must schedule memory traffic across cache hierarchies and lower sliding-window stencils onto matrix execution hardware.

::: {#lst-conv_layer_spatial lst-cap="**Convolutional Layer Abstraction**: Framework-level convolution operations hide the complexity of sliding window computations, typically dispatching to cuDNN or MKL which internally handle im2col transformations or direct convolution algorithms."}

```{.python}
def conv_layer_spatial(input, kernel, bias):
    """Framework-level convolution.

    Single call dispatches to optimized kernel (often via im2col + GEMM).
    """
    # Convolution applies shared weights across all positions
    # For a 3x3 kernel on 28x28 input (padded): 9 MACs per position x 784 positions
    output = convolution(input, kernel) + bias
    return activation(output)
```

:::

To expose the mechanics that the framework abstraction conceals, @lst-conv_layer_compute details the canonical seven-deep loop nest required to evaluate a direct 2D convolution. These loops partition into three structural tiers: batch iteration across samples, spatial traversal over feature map coordinates $(y, x)$, and channel accumulation over input and output dimensions $(C_{\text{in}}, C_{\text{out}})$ coupled with kernel offsets $(k_y, k_x)$. Traversing spatial coordinates and output channels defines the grid of independent output activations.

::: {#lst-conv_layer_compute lst-cap="**Logical Convolution Computation**: Seven nested loops expose $\mathcal{O}(B \times H_{\text{img}} \times W_{\text{img}} \times C_{\text{out}} \times K \times K \times C_{\text{in}})$ complexity. While logically sound, this pattern is inefficient on hardware; production systems transform this into tiled matrix multiplications."}

```{.python}
def conv_layer_compute(input, kernel, bias):
    # Logical view of convolution (usually implemented via im2col +
    # GEMM)
    # Loop 1: Process each image in batch
    for image in range(batch_size):
        # Loop 2&3: Move across image spatially

                for out_channel in range(num_output_channels):
                    result = bias[out_channel]
                    # Loop 5&6: Move across kernel window
                    for ky in range(kernel_height):
                        for kx in range(kernel_width):
                            # Loop 7: Process each input feature
                            for in_channel in range(num_input_channels):
                                # ... MAC operations ...
```

:::

The inner three loops execute the kernel dot product at each spatial site. For each output activation, the kernel evaluates a local $3{\times}3$ input patch across all input channels. Executing this direct loop nest on modern hardware yields poor cache locality and uncoalesced memory accesses because neighboring spatial iterations access overlapping input patches through strided offsets.

To avoid strided memory access, production libraries like cuDNN and oneDNN typically lower convolutions via the **im2col**\index{im2col} (image-to-column) transformation.[^fn-im2col-lowering-transformation] By unfolding each receptive-field patch into a contiguous row of an input matrix and stacking filter weights into columns—a layout transformation diagrammed for two input channels in @fig-im2col-diagram—im2col recasts the entire convolution as a dense general matrix multiply (GEMM) that runs on mature, vendor-tuned libraries. To see how the lowering rearranges data in memory, consider a miniature single-channel image ($C_{\text{in}} = 1$) of size $3 \times 3$ convolved with a $2 \times 2$ filter ($K = 2$) with valid padding:
$$
\mathbf{X} = \begin{bmatrix} 1 & 2 & 3 \\ 4 & 5 & 6 \\ 7 & 8 & 9 \end{bmatrix}, \qquad \mathbf{W} = \begin{bmatrix} w_1 & w_2 \\ w_3 & w_4 \end{bmatrix}
$$
A sliding window sweeps across four overlapping $2 \times 2$ receptive fields:

- **Top-left window**: $[1, 2, 4, 5]$
- **Top-right window**: $[2, 3, 5, 6]$
- **Bottom-left window**: $[4, 5, 7, 8]$
- **Bottom-right window**: $[5, 6, 8, 9]$

To execute all four sliding-window evaluations simultaneously as a single matrix multiplication, `im2col` extracts each $2 \times 2$ patch, flattens it into a row vector of length $K^2 = 4$, and stacks them vertically into an unfolded matrix $\mathbf{X}_{\text{col}}$:
$$
\mathbf{X}_{\text{col}} = \begin{bmatrix} 1 & 2 & 4 & 5 \\ 2 & 3 & 5 & 6 \\ 4 & 5 & 7 & 8 \\ 5 & 6 & 8 & 9 \end{bmatrix}
$$
Flattening the filter weights into a column vector $\mathbf{w}_{\text{col}} = [w_1, w_2, w_3, w_4]^T$, the entire convolution collapses into a single standard matrix product: $\mathbf{Y}_{\text{col}} = \mathbf{X}_{\text{col}} \mathbf{w}_{\text{col}}$.

Generalizing to batched multi-channel inputs, a tensor of shape $(\BatchSize, C_{\text{in}}, H_{\text{img}}, W_{\text{img}})$ unpacks into an unfolded matrix of shape $[(\BatchSize \cdot H_{\text{out}} \cdot W_{\text{out}}) \times (K^2 \cdot C_{\text{in}})]$, while convolutional filters reshape to $[(K^2 \cdot C_{\text{in}}) \times C_{\text{out}}]$. Their product yields an output matrix of shape $[(\BatchSize \cdot H_{\text{out}} \cdot W_{\text{out}}) \times C_{\text{out}}]$. In $\mathbf{X}_{\text{col}}$, input element `5` appears in all four rows. For stride-1 convolutions with kernel size $K$, input pixels shared across overlapping receptive fields are duplicated up to $K^2$ times in memory (a $4\times$ memory footprint expansion for $2\times 2$, or $9\times$ for $3\times 3$). Compilers willingly accept this temporary memory expansion because modern accelerators contain wide matrix engines optimized specifically for peak GEMM throughput.

[^fn-im2col-lowering-transformation]: **im2col (image to column)**\index{im2col!memory trade-off}: Rather than being a new learning algorithm, im2col-style lowering is an implementation technique used by CNN frameworks and libraries such as Caffe and cuDNN [@jia2014; @chetlur2014cudnn]: it converts convolutions into standard GEMM calls by unfolding overlapping patches into matrix columns. The trade-off is memory: in a simple fully materialized stride-1 $K{\times}K$ transform, interior input elements can appear in up to $K^2$ columns (9 times for $3{\times}3$ filters), though borders, stride, padding, tiling, and direct-convolution algorithms reduce the realized expansion. This memory-for-simplicity exchange explains why mobile frameworks (TFLite, NNAPI) prefer direct convolution, while data center GPUs with abundant HBM may use GEMM-oriented lowering when it improves throughput. \index{im2col!data center vs. mobile}

Implicit GEMM techniques avoid even that temporary expansion by generating the matrix coordinates on the fly in register files, never materializing the duplicated buffer. With $3{\times}3$ filters and 32 output channels, each output coordinate requires only 9 MAC operations per input channel, compared to 784 MACs in the reference MLP layer. While reducing operations per activation, the sliding window introduces distinct data reuse profiles that dictate memory staging.
