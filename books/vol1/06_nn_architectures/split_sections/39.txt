### Five families on one machine {#sec-network-architectures-machine-demand-profile}

@Tbl-nn-architectures-machine-demands collects that profile. Each row is a family in a representative execution regime; the transformer takes two rows because prefill and decode reuse the same weights differently (@sec-network-architectures-inference-memory-bandwidth-wall-98d1). The compute-bound rows assume sufficient reuse to exceed the machine's balance, the bandwidth-bound rows assume streamed operands, and the capacity-bound row assumes oversized tables. The columns follow a request through the machine: persistent state, per-request state, arithmetic intensity, parallel axes, and the likely limiting term under those assumptions.

Symbols follow the family sections: $B$ is batch size, $S$ sequence length, $d$ the hidden dimension, $\LayerInputWidth$ and $\LayerOutputWidth$ a layer's input and output widths, $d_{\text{ff}}$ the feed-forward width, $K$ kernel size, $C_{\text{in}}$ and $C_{\text{out}}$ input and output channels, and $H_{\text{img}} \times W_{\text{img}}$ the feature-map size. Intensity regimes are qualitative; @tbl-workload-signatures gives weight-only proxies for the lighthouses. The $\mathcal{O}(B S^2)$ prefill term assumes materialized attention scores (@sec-network-architectures-memory-requirements-72c3). {#tbl-nn-architectures-machine-demands tbl-colwidths="[12,17,17,16,13,15,10]"}

The parameter and activation columns decide how data reaches the arithmetic units, and the pattern of access matters as much as the volume. Three patterns cover the table. Sequential access\index{Memory access!sequential}, the streaming of contiguous weight rows in an MLP layer or a transformer projection, lets DRAM deliver long bursts and lets hardware prefetchers run ahead, so it approaches the interface's peak bandwidth. Strided access\index{Memory access!strided}, which a native convolution produces as it steps across the rows of a feature map, fetches whole cache lines to use a fraction of each; im2col lowering (@sec-network-architectures-computational-mapping-824c) converts it into sequential access at the price of up to $K^2$-fold duplication. Random access\index{Memory access!random} is the DLRM row. Sparse IDs index arbitrary rows of multi-gigabyte tables, defeating prefetchers and wasting most of each burst, which is why caching the popular rows matters so much there. Attention is not random access despite its content-dependent weights, because its queries, keys, and values sit in contiguous tensors that tiled kernels stream through on-chip SRAM.

Whether an access pays DRAM prices at all depends on the working set\index{Working set size}, the data the execution units need at once. Small layers, such as the $784{\times}100$ reference layer at `{python} MLPLayerStats.weight_kb_str` in FP32, fit in on-chip SRAM. Production-width layers of tens of megabytes do not, which is why unbatched MLP inference and transformer decode stream their weights from off-chip memory on every request. Accelerators answer both ends of the table with memory hierarchy rather than arithmetic. High Bandwidth Memory (**HBM**\index{HBM!definition}) stacks DRAM dies beside the processor to supply the streaming rows at more than an order of magnitude above standard DDR channels, and multi-megabyte on-chip SRAM, often an explicitly managed scratchpad\index{Scratchpad memory!explicit control}, lets compilers stage tiles so that reuse happens on chip. The intensity column measures how much a family can profit from that staging, and it doubles as an energy column.

```{python}
#| echo: false
#| label: energy-consumption-analysis

# ┌─────────────────────────────────────────────────────────────────────────────
# │ ENERGY CONSUMPTION ANALYSIS
# ├─────────────────────────────────────────────────────────────────────────────
# │ Context: Energy perspective callout in the workload-profile subsection
# │
# │ Goal: Contrast the energy cost of compute vs. data movement.
# │ Show: That DRAM access consumes over 100× more energy than an FP32 multiply.
# │ How: Compare picojoules per FLOP vs. a 32-bit DRAM read.
# │
# └─────────────────────────────────────────────────────────────────────────────

from mlsysim.fmt import fmt_int, fmt, check, fmt_energy, fmt_energy_per_flop, fmt_multiple

class EnergyConsumptionAnalysis:
    """Contrast energy cost of compute vs. data movement using Horowitz-style anchors."""

    # ┌── 1. LOAD (Constants) ──────────────────────────────────────────────
    ENERGY_FLOP_FP32_PJ = Hardware.Tech.Op.FlopFp32.energy
    ENERGY_DRAM_ACCESS_PJ = Hardware.Tech.Memory.DRAM.energy_per_access
    multiply_pj = ENERGY_FLOP_FP32_PJ.to(pJ / flop).magnitude  # pJ per FP32 multiply
    dram_pj = ENERGY_DRAM_ACCESS_PJ.to(pJ).magnitude  # pJ per 32-bit access

    # ┌── 2. EXECUTE (The Compute) ────────────────────────────────────────
    dram_to_flop_ratio = dram_pj / multiply_pj

    # ┌── 3. GUARD (Invariants) ──────────────────────────────────────────
    check(dram_to_flop_ratio > 100, "DRAM access should cost over 100x a reference FP32 FLOP.")

    # ┌── 4. OUTPUT (Formatting) ─────────────────────────────────────────────
    energy_multiply_pj_str = fmt_energy_per_flop(ENERGY_FLOP_FP32_PJ, precision=1, commas=False)
    energy_dram_pj_str = fmt_energy(ENERGY_DRAM_ACCESS_PJ, unit=pJ, precision=0, commas=False)
    energy_ratio_mult_str = fmt_multiple(round(dram_to_flop_ratio), precision=0, commas=True)
```

*Moving a 32-bit value from DRAM costs far more energy than one FP32 multiply.*

::: {#psp-nn-architectures-energy-cost-data-movement .callout-perspective title="The energy cost of data movement"}

A core systems principle: *moving data costs more than computing on it*. In the reference model of @horowitz2014, an FP32 multiply costs about `{python} EnergyConsumptionAnalysis.energy_multiply_pj_str`, while fetching one 32-bit operand from off-chip DRAM costs `{python} EnergyConsumptionAnalysis.energy_dram_pj_str`, a gap of `{python} EnergyConsumptionAnalysis.energy_ratio_mult_str`. Low-intensity rows are therefore energy-dominated by DRAM traffic. An unbatched MLP or a decode step loads each weight once per request and spends most of its energy moving it. A CNN amortizes each filter load over $H_{\text{img}} \times W_{\text{img}}$ applications, so the locality that makes it compute bound also makes it energy efficient, unless a fully materialized im2col buffer inflates temporary traffic by up to $K^2$. An RNN keeps its compact state in SRAM but idles execution units across serial steps, which raises energy per token. Tiled attention keeps score blocks on chip, so its energy tracks matrix multiplication rather than DRAM round-trips.

Later optimizations exploit this principle directly. Quantization reduces the bits moved per value; pruning removes unnecessary movement; and tiling keeps working sets in faster, lower-energy memory.

:::

The parallel-axis column determines how data must move among processing elements once the work is spread out. @Fig-collective-comm schematizes the four fundamental data movement topologies—broadcast, scatter, gather, and reduction—that govern tensor routing across distributed ranks. Batch parallelism in MLPs, CNNs, and prefill broadcasts\index{Data movement!broadcast} stationary weight tiles to many units, each working on a different example or position, and compilers tile loops\index{Matrix tiling} to reuse each broadcast value as often as possible. Spatial and model partitioning scatter\index{Data movement!scatter} a tensor across tiles or devices; mixture-of-experts models, which route each token to a few of many feedforward subnetworks, make the scatter input-dependent, so a popular expert can overload one accelerator while others idle. DLRM gathers\index{Data movement!gather} embedding rows from wherever the sharded tables live, and each attention query gathers keys and values from every position in its sequence. Reductions\index{Data movement!reduction} combine values through sums or maxima (softmax denominators, normalization statistics, gradient synchronization across data-parallel workers), and tree-structured reduction hardware finishes a reduction over $n$ values in $\mathcal{O}(\log n)$ stages rather than $\mathcal{O}(n)$. The rows with a serial axis, RNNs and decode, are the rows these collectives cannot rescue, because no amount of broadcast or reduction bandwidth shortens a dependency chain.

Gather (bottom-left) collects distributed values to a single location, as in attention pooling. Reduction (bottom-right) combines multiple values through aggregation (sum, max), appearing in gradient synchronization and attention scoring. The last column applies the iron law under each row's execution assumptions. When effective intensity exceeds the machine's balance and parallel work is sufficient (batched CNNs, prefill), the compute term $\Operations/(\PeakRate\,\EfficiencyHw)$ binds. Below that balance (streamed small-batch MLPs, decode), the data term $\DataVolume/\Bandwidth$ binds, favoring fewer transferred bytes, more reuse, or higher bandwidth. RNNs add a serial chain of state updates: faster arithmetic, memory, and reduced launch overhead $(\Latency)$ can shorten each step without removing the dependency. DLRM adds a constraint that sits in front of the equation. Capacity decides where the tables live and thus which bandwidth the data term pays. ResNet-50, GPT-2, and DLRM isolate these representative regimes. MobileNetV2 and KWS share the CNN row, with depthwise layers pulling their intensity down, because latency and power are deployment budgets that constrain the entire execution. No lighthouse occupies the RNN row, whose serial chain the recurrent family section analyzes directly.
