### System implications {#sec-network-architectures-system-implications-0550}

Dense pattern processing concentrates hardware pressure across three dimensions: memory capacity for parameter storage, compute throughput on matrix engines, and memory bandwidth for weight movement.

```{python}
#| echo: false
#| label: large-mlp-memory

# ┌─────────────────────────────────────────────────────────────────────────────
# │ LARGE MLP MEMORY SCALING
# ├─────────────────────────────────────────────────────────────────────────────
# │ Context: Memory Requirements paragraph showing M by N parameter scaling
# │
# │ Goal: Demonstrate the prohibitive memory scaling of large dense layers.
# │ Show: That a single 2048x2048 layer consumes 16 MB, limiting depth.
# │ How: Calculate parameter count and FP32 size for a wide MLP layer.
# │
# └─────────────────────────────────────────────────────────────────────────────

from mlsysim.fmt import fmt_int, fmt, fmt_count, check
from mlsysim.physics import model_memory

# ┌── LEGO ───────────────────────────────────────────────
class LargeMLP:
    """
    Namespace for Large MLP Memory Scaling.
    Scenario: The quadratic cost of dense layers (2048 -> 2048).
    """

    # ┌── 1. LOAD (Constants) ───────────────────────────────────────────────
    width = 2048

    # ┌── 2. EXECUTE (The Compute) ─────────────────────────────────────────
    params = width * width
    mem = params * BYTES_FP32

    # ┌── 3. GUARD (Invariants) ───────────────────────────────────────────
    check(params >= MILLION, f"{width}x{width} layer should be large (>1M params).")

    # ┌── 4. OUTPUT (Formatting) ──────────────────────────────────────────────
    dim_str = fmt(width, precision=0, commas=False)
    params_str = fmt_count(params, label="parameter", commas=True)
    mem_mb_str = fmt_memory(mem, unit=MB, precision=1, commas=False)

# Note: Use LargeMLP.dim_str directly.
```

All three constraints originate from all-to-all connectivity. Memory footprint is dominated by parameter storage. While the reference MNIST layer $(784{\times}100)$ requires only 78,400 parameters, $\mathcal{O}(\LayerInputWidth \times \LayerOutputWidth)$ scaling becomes prohibitive for wide hidden states. A layer connecting `{python} LargeMLP.dim_str` inputs to `{python} LargeMLP.dim_str` outputs requires `{python} LargeMLP.params_str` (`{python} LargeMLP.mem_mb_str` at FP32). Single-sample inference provides one use per weight within that layer evaluation. When weights exceed cache capacity and stream from DRAM for each request, this limited reuse makes bandwidth a likely constraint.

The core computation is dense GEMV, or GEMM when batched. This computation is regular and parallelizable, but the arithmetic intensity (FLOP/byte) is low for small batches. A larger batch size\index{Batch size} amortizes weight-loading cost over more computations. Modern processors optimize dense layers with single instruction, multiple data (SIMD) units such as AVX-512 on CPUs or with dense matrix engines such as Tensor Cores on GPUs and systolic arrays on Tensor Processing Units (TPUs), amortizing control overhead over large blocks of parallel arithmetic.

The streamed-weight model makes this data-movement cost explicit. To compute 100 hidden values from 784 inputs, the system reads $784{\times}100$ weights. Applying the arithmetic intensity framework from @sec-network-architectures-understanding-arithmetic-intensity-ade5 to this layer yields roughly `{python} MLPLayerStats.dense_batch1_intensity_str` for batch-one FP32 execution. Under a weight-only model that counts one FP32 read per weight and omits input, output, bias, and cache traffic, @eq-dense-intensity gives this ratio, where $\LayerInputWidth$ and $\LayerOutputWidth$ are the input and output widths. The memory tier serving those reads determines the relevant bandwidth.
$$
I \approx \frac{2 \cdot \LayerInputWidth \cdot \LayerOutputWidth \text{ FLOPs}}{4 \cdot \LayerInputWidth \cdot \LayerOutputWidth \text{ bytes}} = 0.5 \text{ FLOP/byte}
$$ {#eq-dense-intensity}

On accelerators with ridge points in the hundreds of FLOP/byte, this batch-one FP32 layer is memory-bandwidth bound. Batching can raise intensity by amortizing weight traffic, but the crossover depends on matrix shape, precision, implementation, and hardware. Specifically, increasing batch size to $\BatchSize$ scales arithmetic to $2 \cdot \BatchSize \cdot \LayerInputWidth \cdot \LayerOutputWidth$ FLOPs while loading the weight matrix once ($4 \cdot \LayerInputWidth \cdot \LayerOutputWidth$ bytes), driving weight-bound arithmetic intensity up to $\ArithmeticIntensity \approx 0.5 \BatchSize \text{ FLOP/byte}$ until input and activation traffic begin to dominate. This is why fully connected layers can become inference bottlenecks despite performing fewer total FLOPs than convolutional layers.

The most established such architecture is the convolutional neural network.
