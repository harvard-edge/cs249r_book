\begin{abstract}
Professional machine-learning benchmarks teach a discipline that is often absent
from coursework. A valid result must bind a workload, data, model, quality gate,
system description, measurement protocol, and evidence package. Official MLPerf
suites establish this discipline at production scale~\citep{mattson2020,reddi2020mlperf,banbury2021mlperf},
but many of their representative workloads are too costly for an individual
student to reproduce. We present \project{}, an independent, executable framework
that adapts the structure of benchmark submissions to laptop-class teaching and
research. Its current registry contains \RegistryRows{} workload rows across
\RegistrySuites{} suites. Only \ScoreBearingRows{} rows are score-bearing and
\PerformanceBearingRows{} are performance-bearing. The remaining
\SystemsOnlyRows{} are explicitly systems-only and cannot support a public score.
The implementation couples real-data quality gates, checkpoint-backed inference,
repeatable timing, artifact manifests, dataset and model dossiers, and a review
contract that rejects synthetic or incomplete evidence from public-result paths.
This paper describes the contract and reports \ReferenceEvidenceRows{} committed
five-run project references produced from one clean source revision. These
measurements are not MLCommons-verified results. Their indexed raw packages are
retained for local reviewer handoff, while cross-platform replication,
dataset-policy decisions, public package hosting, and MLCommons feedback remain
release gates.
\end{abstract}

\section{Motivation and Scope}

ML systems education needs more than a collection of small models. Students must
learn why a fast run with the wrong dataset is not comparable, why inference speed
is meaningless when task quality changes, and why a median without raw runs is not
auditable. These lessons complement model and systems design material such as the
\emph{Machine Learning Systems} text~\citep{mlsysbook2025}.

\project{} makes the submission contract itself inspectable. A single command-line
interface selects a suite, workload, variant, and one of three profiles. The runner
produces machine-readable and human-readable reports, records execution and asset
metadata, applies the declared gate, and emits an integrity manifest. The design
borrows benchmark methodology from MLPerf, DAWNBench, and long-standing systems
benchmark practice~\citep{mattson2020,coleman2019,henning2006}. It does not reuse
official rules by implication. Any eventual relationship to MLCommons, including
the project name, would require explicit review and approval.

The framework has three intended uses. In a course, a student can change one
systems variable and submit comparable artifacts. In a research lab, an author can
use the same local path for preflight checks before a larger experiment. In an
artifact evaluation, a reviewer can distinguish executable teaching scaffolds from
rows whose evidence is strong enough for a public comparison.

\section{Benchmark Contract}

We model a benchmark run as
\begin{equation}
  \mathcal{R}=f(M,D,H,S,C,P),
\end{equation}
where $M$ is the model, $D$ is the data recipe, $H$ is the system under test, $S$
is the scenario, $C$ is the correctness or quality constraint, and $P$ is the
measurement protocol. The result $\mathcal{R}$ is valid only when its evidence
binds all six inputs. Raw speed is therefore never sufficient.

Scenario names bind measurement semantics rather than execution scale. All five
score-bearing registry rows use the project-defined \code{training} scenario.
Performance-bearing inference rows retain \code{single\_stream}, \code{offline}, or
\code{server} as applicable. Here, \code{training} is proposed \project{} vocabulary,
not an official MLPerf Inference scenario. Its name and relationship to MLPerf
scenario terminology require MLCommons review.

\subsection{Result Roles}

Every registry row has one public role.

\begin{itemize}
\item \textbf{Score-bearing.} A real-data training path declares a task metric,
  direction, target, five-seed protocol, and aggregation rule. Runtime can be
  compared only when the quality gate passes.
\item \textbf{Performance-bearing.} An inference path declares a functional or
  task-quality gate, warmup and measurement counts, latency statistics, and model
  provenance. A checkpoint dependency must include its digest and source quality.
\item \textbf{Systems-only.} A path can teach an architecture or optimization but
  lacks the evidence needed for a public score. The validator treats this label as
  a prohibition, not a weaker endorsement.
\end{itemize}

This distinction addresses a common failure mode in educational benchmark suites.
A script that runs is not automatically a benchmark result. Synthetic data,
random weights, a failed quality-parity check, or an unresolved model dependency
keeps a row in the systems-only category.

The score-bearing set covers language modeling, recommendation, anomaly detection,
and two image classifiers. NanoGPT uses a character-level Transformer and a
cross-entropy gate. Micro-DLRM adapts the sparse-embedding and dense-interaction
shape of recommendation models~\citep{naumov2019deep}. ResNet-18 and MobileNetV2
retain the residual and depthwise-separable structures of their source
architectures~\citep{he2016,sandler2018}. The anomaly autoencoder trains on MNIST
digit zero and evaluates reconstruction-error discrimination over the full test
split. Its public metric is AUROC, not training loss, which better matches anomaly
detection semantics~\citep{lecun1998,koizumi2019}.

The performance-bearing set contains checkpoint-backed NanoGPT prefill and decode,
plus a pinned SmolLM2-135M-Instruct serving path. Other variants remain
systems-only. One important example is dynamic INT8 SLM inference. It completes
generation but currently violates the continuation-quality parity gate, so its
timing cannot be presented as a performance-bearing optimization.

\section{Evidence and Provenance}

\subsection{Five-Seed Training Protocol}

Each score-bearing row declares seeds 0 through 4 and uses the median task metric.
The reference-sweep tool starts every seed in a fresh process through the public
command path. It verifies the report and provenance manifest, checks that both
record the requested seed, resolves the declared metric, and rejects synthetic data
from public-candidate evidence. The sweep preserves per-seed reports, manifests,
checkpoints, and declared sidecars in an immutable attempt directory. If one seed
fails, the policy requires a new five-seed attempt rather than selective replacement.

Release evidence must be generated from a clean commit. It must record the commit,
dependency lock, data and model digests, hardware and software fingerprints,
command, environment overrides, raw per-seed values, aggregation, and acceptance
decision. One passing seed does not establish a target.

\subsection{Integrity Boundaries}

The provenance manifest indexes artifact bytes and sizes with SHA-256. This is an
unauthenticated integrity digest, not a signature or proof that computation
occurred. It detects accidental changes and binds a reviewed package to exact
files. It does not prevent a submitter from fabricating a self-consistent package.
Stronger trust would require independent reruns, signed attestations, controlled
execution, or a combination of these measures. The paper therefore avoids claims
that hashing alone prevents fraud.

The package verifier resolves paths relative to the extracted package, checks every
indexed size and digest, and verifies the report against its provenance manifest.
Absolute paths from the generating machine are rewritten for portability. This
supports clean-directory verification without presenting a checksum as an identity
or authenticity mechanism.

\section{Inference Methodology}

Inference timings are eligible only after correctness and model identity are
established. NanoGPT prefill and decode load the same quality-approved training
checkpoint and record its SHA-256 digest. The prefill default performs
\PrefillWarmups{} warmup passes followed by \PrefillMeasurements{} measured passes
over a fixed 1,792-token context. It reports median, p90, and p99 latency plus token
throughput. The decode default performs \DecodeWarmups{} warmup requests followed
by \DecodeMeasurements{} measured requests, each with \DecodeSteps{} decode steps. It
reports time to first token, per-token inter-token latency samples, percentile
statistics, and output throughput.

The SLM path pins the model revision and evaluates a bundled four-case continuation
suite. A performance-bearing result must generate at least \SLMTokenFloor{}
continuation tokens and keep continuation perplexity at or below
\SLMPerplexityLimit. The default timing protocol uses \SLMWarmups{} warmup requests
and \SLMMeasurements{} measured requests with separate prefill and generation timing.
Quantized variants additionally compare continuation negative log-likelihood with
the floating-point model. These are deliberately modest gates. They detect broken
or materially changed inference paths; they are not broad capability evaluations.

The three inference references also pass all five functional gates. On the recorded
Apple M5 Max MPS system, median prefill throughput is \NanoGPTPrefillMedianK{}
thousand tokens/s, NanoGPT decode is \NanoGPTDecodeMedian{} tokens/s, and SLM
decode is \SLMDecodeMedian{} tokens/s. The SLM range,
\SLMDecodeMin--\SLMDecodeMax{} tokens/s, is substantially wider than NanoGPT decode. These figures
are disclosed machine observations, not portable performance targets. Their value
is the complete checkpoint, model, protocol, sample, and hardware context that
accompanies them. Cross-machine repetitions are still required for broader claims.

\section{Educational Integration}

The teaching design uses the benchmark contract as the learning object. Three local
labs cover optimization, an inference system-under-test interface, and architecture
comparison. Each lab has a deterministic smoke mode that executes real forward,
backward, inference, or parity checks without a network connection. A separate
tutorial runs a first benchmark and verifies its generated report and manifest.

The intended learning progression has four stages.

\begin{enumerate}
\item \textbf{Reproduce.} Run a fixed profile and verify its artifact package.
\item \textbf{Diagnose.} Attribute time to data loading, model execution, or request
  scheduling using the report and profiler output.
\item \textbf{Optimize.} Change one variable while preserving the quality gate and
  recording the configuration.
\item \textbf{Defend.} Explain whether the result is comparable and identify every
  source of evidence that supports the claim.
\end{enumerate}

This progression makes a failed quality gate pedagogically useful. A quantized path
that is smaller but changes model behavior is not a successful benchmark result.
Students must decide whether to repair the technique, change its role to
systems-only, or propose a justified parity rule.

No classroom-learning outcome is claimed in this draft. The labs have executable
regression checks. Formal course, accessibility, and instructor studies remain
future work. Educational usefulness and benchmark validity are related but separate
hypotheses.

\section{Validation and Release Gates}

The repository uses layered checks rather than one aggregate green status.

\begin{enumerate}
\item \textbf{Schema and mirror checks} validate the native registry, generated
  compatibility mirror, dataset catalog, review packets, and taxonomy.
\item \textbf{Unit and entry-point checks} exercise runners, reports, manifests,
  package extraction, reference sweeps, tutorials, and labs.
\item \textbf{Actual smoke validation} executes the public command path. Dry runs
  are not accepted as evidence that a benchmark works.
\item \textbf{Release validation} runs the full \code{max} public-candidate set,
  applies the review contract, builds a wheel, installs it in a clean environment,
  and checks the documentation and paper.
\item \textbf{Reference evidence} reruns every declared seed from a clean commit and
  preserves the resulting bundle. This is intentionally separate from ordinary CI.
\end{enumerate}

The distinction between continuous integration and reference evidence is important.
A quick CI job should catch regressions. It should not be cited as a stable baseline
unless it used the declared data, model, protocol, and evidence-retention policy.

\section{Prior Benchmark Context}

Official MLPerf Training, Inference, and Tiny define production-oriented workload
and submission rules~\citep{mattson2020,reddi2020mlperf,banbury2021mlperf}.
\project{} is smaller in scale and currently independent. Its contribution is an
inspectable educational contract rather than a claim of equivalent coverage or
competitive validity.

DAWNBench emphasized time to accuracy and cost to accuracy~\citep{coleman2019}.
\project{} similarly treats quality as a prerequisite for performance, but shifts
the setting from cloud competition to local instruction. TorchBench provides broad
framework regression coverage~\citep{ansel2024torchbench}; it is complementary
because framework coverage and submission-style task-quality evidence serve
different purposes. MLPerf Tiny is the closest precedent for accessible scale, yet
its target remains deployed embedded inference rather than a notebook-centered
course workflow~\citep{banbury2021mlperf}.

\section{Limitations and Review}

The current framework is ready for technical review, not an official or competitive
claim. Five limitations are material.

\begin{itemize}
\item The committed summaries index complete raw packages retained for local reviewer
  handoff, but those packages do not yet have stable public URLs. A summary alone is
  not a self-contained reproduction bundle.
\item All eight references come from one Apple M5 Max host. Inference therefore lacks
  a multi-machine comparison suitable for a portable performance claim.
\item MovieLens-100K requires an explicit decision about public benchmark use and
  artifact redistribution.
\item Cross-platform replication on at least one CUDA system and a second CPU class
  is pending. Hardware fingerprints describe a result but do not make different
  systems numerically equivalent.
\item Micro-scale workloads preserve model structure more reliably than production
  bottlenecks. DLRM's small embedding tables, for example, do not reproduce the
  memory pressure of production recommendation systems.
\end{itemize}

External review would be most valuable on the following questions.

\begin{enumerate}
\item Is the project name acceptable, and what wording is required to avoid implied
  MLCommons endorsement?
\item Are the score-bearing, performance-bearing, and systems-only roles a useful
  separation for education, and is the project-defined \code{training} scenario
  acceptable, or should these concepts map to different vocabulary?
\item Is median-of-five an adequate educational reference protocol, and what
  cross-platform tolerance policy should accompany it?
\item Which functional and task-quality gates are sufficient before local inference
  timing becomes comparable?
\item What dataset and model release review is required before a public reference
  package can be distributed?
\end{enumerate}

\section{Conclusion}

\project{} treats benchmarking literacy as a first-class learning outcome. Its
central mechanism is an executable boundary between a run that completes and a
result that is comparable, reviewable, and reproducible. The eight committed
references show five real-data training paths passing their targets and three
inference paths passing their functional and lineage gates. They also expose narrow
DLRM headroom and machine-specific inference variance.

Independent replication and governance are next. The raw packages need stable
reviewer access, the MovieLens policy needs resolution, and the suite needs
reproduction beyond the development host. Naming, scenario vocabulary, target
rationale, and result wording also require external review. Until those gates close,
this document remains a review draft rather than a benchmark release.

\noindent\textit{Reproducibility.} \code{make clean all check} derives every table
from the registry, asset catalog, and eight content-addressed summaries, then rejects
evidence drift, reference errors, placeholders, and layout overflows.
