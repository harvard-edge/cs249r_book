\section{The Log}

\begin{frame}{A crash erases the record; the context is only a transcript}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.6cm,keepaspectratio]{lost_step}{2}
  \mlsyscredit{After Durable Execution, \S11.1 (the worksheet crash).}
  \note{%
    \mlsysnotemeta{3.5 min}{Core}%
    Mid-trajectory crashes are not rare anomalies. Recall from Lecture 1 that the METR trend places frontier task horizons near 17 hours of expert time by 2026, so daily worker restarts, cloud spot preemptions (when a provider reclaims an interruptible machine), and rolling software updates occur routinely during a run. In host memory, Lecture 10's trajectory record sits separate from the model's curated context window. That record holds dispatched test\_r18, its \$0.50 reservation, capability grants, Lecture 10's control epoch, and a pending approval. When the worker dies, all of that state vanishes, and losing the dispatched test is the gravest loss because the remote job may still run and bill. Because the context window holds no reservations, meters, or in-flight entries, and Lecture 4's compaction summarizes earlier turns away, only durable storage can rebuild the record.

    \notecue{Watch for}{Do not treat the chat transcript as agent state. It is a lossy input assembled for the model, whereas the runtime's record lives separately.}

    \notecue{Next}{Slide 8 defines the append-only trajectory log and shows how folding rebuilds the record without calling the model.}
  }
\end{frame}

\begin{frame}{The log is folded into the record, without calling the model}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.98cm,keepaspectratio]{fold_step}{3}\\[0.03cm]
  \uncover<2->{\footnotesize $R_j = \mathrm{fold}(R_0,\ e_1, \dots, e_j)$:\enspace $R$ is the record, $e$ the logged events}
  \mlsyscredit{After Durable Execution, \S11.2.1, def.~11.1 and fig.~1 (Explore: Trajectory Log Fold on mlsysbook.ai).}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    If durable storage must rebuild the erased record without re-prompting a stochastic model, it must record every decision and observation as it happens. Definition 11.1 defines that store as the trajectory log, an ordered sequence of typed events that is append-only, meaning entries are added only at the end. A deterministic reducer function rebuilds control state according to $R_j = \mathrm{fold}(R_0, e_1, \dots, e_j)$. Starting from initial state $R_0$, the reducer folds five durable events running from task start through the intent for test\_r18, with no result logged. It calls neither the model nor any tool, reusing the logged model reply because sampled outputs cannot be regenerated reliably. The rebuilt record preserves the admission and \$0.50 reservation while marking test\_r18 unresolved rather than inventing an outcome.

    \notecue{Watch for}{Keep three artifacts separate. The log is append-only history, the record is its folded projection, and the context window is a lossy prompt view assembled from it.}

    \notecue{Next}{Slide 9 tests this log-folding recovery on a live Temporal workflow whose worker is killed mid-test.}
  }
\end{frame}

    \mlsysnotemeta{2.5 min}{Core}%
    Does log folding avoid calling the model again in production software? \mlsysdivider{When must the intent reach storage, and which storage counts?}{Durable Execution, \S11.3}
\section{Intent}

\begin{frame}{Intent before dispatch makes every escaped effect visible}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.5cm,keepaspectratio]{intent_step}{3}
  \mlsyscredit{After Durable Execution, \S11.3.2, eq.~1 and fig.~2 (Explore: Durable Intent Zones on mlsysbook.ai).}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    To keep an external effect from escaping unrecorded before a crash, the runtime places a write-ahead barrier before every network send. Definition 11.2 defines durable intent as the operation identity, arguments, grant reference, and reservation acknowledged before dispatch on storage surviving the declared failure domain (the set of faults across which a persistence guarantee holds). Equation 1 enforces the strict order of propose, admit, intent acknowledged, dispatch, and evidence. A crash before acknowledgment proves non-dispatch in a complete log, whereas a crash after correlated evidence establishes the outcome under the endpoint contract (Lecture 7's service promise on repeats and confirmation). Between acknowledgment and evidence lies the in-doubt window, where any crash, even immediately before dispatch, forces recovery to reconcile before dependent work proceeds.

    \notecue{Watch for}{A durable intent proves that work may have escaped. It neither proves the endpoint ran the operation nor authorizes a blind retry.}

    \notecue{Next}{Slide 13 compares unkeyed and keyed executors on the Temporal crash run when test\_r18 lands in doubt.}
  }
\end{frame}

    \end{column}
    \begin{column}{0.47\textwidth}
      {\footnotesize\textbf{macOS} \texttt{man 2 fsync}}\\[0.05cm]
      \codeblock{the drive itself may not physically write the data to the platters for quite some time\dots\\[0.3em]
      \textcolor{RedLine}{\textbf{This is not a theoretical edge case.}}\\[0.3em]
      F\_FULLFSYNC fcntl asks the drive to flush all buffered data to permanent storage.}
    \end{column}
  \end{columns}
  \mlsyscredit{Photo: Samsung SSD 860 Pro board, Michael Bemmerl, CC BY 3.0 de, Wikimedia Commons (labels added from the chip markings). Text: macOS 26.4 fsync(2) manual page, excerpt.}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Keyed recovery works only if the logged intent survived the crash, so failure-domain durability requires naming which faults an acknowledgment covers. A Samsung SSD 860 Pro circuit board shows why software calls mislead, because the controller buffers writes in volatile DRAM cache before committing them to persistent NAND flash (nonvolatile memory chips). The macOS fsync(2) manual page confirms that a returned fsync only hands bytes to the drive, whereas the F\_FULLFSYNC file-control call (fcntl) forces the drive to flush its buffers to permanent storage. Three tiers follow. The kernel page cache (host memory holding buffered writes) covers a process crash, an honored drive flush covers power or host loss with the volume intact, and a quorum (a majority confirming each write) across off-volume replicas covers volume loss, which the worksheet requires when a replacement worker starts on another machine after host and disk loss together.

    \notecue{Watch for}{Remoteness alone is not enough. An asynchronous replica (one updated in the background after the write returns) can lag behind the acknowledgment and lose committed intents.}

    \notecue{Next}{Slide 15 asks how much latency each acknowledgment tier adds to every dispatch.}
  }
\end{frame}

\begin{frame}{A missing intent proves non-dispatch only in a complete log}

\begin{frame}{Group commit shares one flush; each intent still waits for all of it}
  \centering
  \safeimg[width=0.88\textwidth,height=4.4cm,keepaspectratio]{groupcommit.pdf}\\[0.05cm]

    \mlsysnotemeta{1.5 min}{Core}%
    Transaction processing confronted this crash-ordering problem decades before agents. In his 1978 notes on database operating systems, Jim Gray established write-ahead logging for crash recovery and introduced two-phase commit (a protocol that prepares changes before committing them across participants). Mohan et al. (1992) turned that discipline into the ARIES recovery protocol, forcing log records to stable storage before modifying disk pages so restart can redo committed work and undo uncommitted changes because the database owns its pages. An agent runtime borrows the write-ahead ordering, not page ownership. Because remote endpoints rarely support two-phase commit, the runtime cannot undo an escaped call from its log; it must settle in-doubt calls and issue compensating actions (follow-up operations that offset unwanted effects, developed in Lecture 12). Helland (2007) reached the same conclusion for large services, using identified idempotent messages across ownership boundaries. Segment 2 thus establishes durable intent before dispatch under a named failure domain and explains why test\_r18 needed an operation ID.

\begin{frame}{A checkpoint binds record and files to one log position}
  \centering
  \mlsyssteps[width=\textwidth,height=5.85cm,keepaspectratio]{ckpt_step}{3}
  \mlsyscredit{After Durable Execution, \S11.4.1 (Explore: Checkpoint Binding on mlsysbook.ai; Chandy and Lamport 1985).}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    A log entry stating that an edit succeeded cannot restore modified files unless the control record and workspace bytes share one recovery boundary. Checkpoint binding ties a record snapshot (record\_R\_ckpt) and workspace snapshot (ws\_r18, made cheap by Lecture 8's copy-on-write workspace sharing unchanged blocks) to one committed log position $c$, so restore unpacks both and folds only the suffix after $c$ without calling the model. The runtime publishes a manifest (an index naming position $c$, integrity hashes, and reducer version) only after all artifact bytes are durable, keeping the prior checkpoint valid if capture crashes midway. In 1985, Chandy and Lamport defined a consistent distributed snapshot as a global state where every recorded receipt matches a recorded send. Copying files seconds after snapshotting the record while a tool still writes violates that rule, producing a torn state that never existed.

    \notecue{Watch for}{If the log references a workspace delta (an incremental file change) whose bytes are missing, fail and mark the run unrecoverable. Recomputing that change is new execution, not restoration.}

\begin{frame}{Full snapshots rewrite old state; deltas write it once}
  \centering
  \safeimg[width=0.88\textwidth,height=4.6cm,keepaspectratio]{snapshots.pdf}\\[0.05cm]
  {\small 500 turns, 128 KB of new state per turn: 50.5 times the bytes written}
  \mlsyscredit{Durable Execution, \S11.4.2, equation 3 and its worked numbers (illustrative). Derived.}

    \mlsysnotemeta{1.5 min}{Optional}%

\begin{frame}{Resume proves, owns, restores, reconciles, then admits}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.6cm,keepaspectratio]{resume_step}{3}\\[0.05cm]
  \uncover<3->{\small Resume protocol time $=$ ownership $+$ read $+$ fold $+$ restore $+$ reconcile $+$ prefill}
  \mlsyscredit{After Durable Execution, \S11.5 and equation 7.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    The resume protocol builds an authorized continuation in five ordered stages priced by equation 7 (ownership + read + fold + restore + reconcile + prefill), preventing split-brain writes (two workers acting as owner at once) and premature retries. Stage one proves that the authoritative log prefix and checkpoint artifacts are complete, reporting any gap as unavailable rather than empty. Stage two acquires a new owner epoch (a monotonically increasing ownership number, moving from 7 to 8) from a strongly consistent lease service (a replicated coordinator issuing a time-limited ownership grant to one agreed worker at a time). Stages three and four restore ws\_r18, fold the log suffix, and reconcile in-doubt test\_r18 by probing its logged operation ID while keeping reservations locked. Stage five admits new work under current limits, keeping a PAUSED run paused, checking prior approvals through Lecture 10's approval escrow, and re-running bounded-liability admission.

    \notecue{Watch for}{Acquiring epoch 8 does not license re-sending test\_r18. Reconciliation and prefill usually dominate resume latency, whereas log folding is cheap.}

\begin{frame}{A fencing token is checked at the resource on every write}
  \centering
  \mlsyssteps[width=\textwidth,height=5.0cm,keepaspectratio]{fence_step}{3}\\[0.05cm]
  \uncover<3->{\small A lease bounds how long a lost worker blocks recovery; only the epoch check excludes it.}
  \mlsyscredit{After Durable Execution, \S11.5.1 (fencing tokens; Kleppmann 2016; Burrows 2006).}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    A lease's expiration timeout bounds how long a dead or stalled worker blocks takeover, yet expiry alone never excludes it; every write boundary must check epoch 8. In 2006, Burrows introduced generation-stamped lock sequencers in the Chubby lock service so resources could reject stale holders, which Kleppmann (2016) framed as fencing tokens, monotonically increasing epoch numbers checked at the resource. Suppose worker A holds epoch 7 and stalls during a pause, a network partition (loss of connectivity), or a slow disk while its time-limited lease expires unnoticed. The lease service grants epoch 8 to worker B, whose writes to the log and dispatch gateway (the component sending tool calls) succeed. When worker A wakes with a write tagged with epoch 7, the log rejects it after seeing 8, supplying the check the DynamoDB DNS Enactor lacked.

    \notecue{Watch for}{Fencing stops new writes only at boundaries verifying the epoch (log, gateway, and checking resources). It does not cancel an earlier test\_r18 call already sent, which still requires reconciliation.}

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.3cm}
    \item Many tools offer no status query and no idempotency key. Should a runtime refuse them, wrap them, or escalate every in-doubt call to a person?
    \item A hosted model can change underneath a long run. How should a runtime record what it called, when the provider does not say?
    \item Recovery data is cheap to keep, but it holds prompts, outputs, and secrets that leaked into tools. Who decides how long it lives?
  \end{itemize}
  \note{%
    \mlsysnotemeta{1 min}{Optional}%
    Even when durable logging works as designed, three boundaries resist a single standard policy. First, when an endpoint offers neither status queries nor idempotency keys, should the runtime refuse it, wrap it, or escalate every in-doubt call under Lecture 7's settlement-before-retry rule? Second, how should a runtime record provider provenance (available model checkpoint, serving-stack, and configuration metadata, plus any gaps) when hosted models change silently during long runs? Third, cheap retention (about 1.5 cents per year) collides with privacy when logs capture prompts, outputs, and leaked credentials, a tradeoff Lecture 14 develops.
