  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Recall from Lecture 1 that the proposal boundary leaves a model call with zero ambient authority. Definition 2.1 formalizes model output as a proposal, and the architecture separates the handoff into three stages. First, the foundation model and its inference service, which hosts weights and samples tokens, emit only a text proposal, \cd{read\_file("src/pool.py")}. \begin{frame}{Admission counts the prompt and reserves the reply}
  \centering
  {\large Token-measured admission\qquad $S \;\le\; S_{\max} - K_{\max}$}\\[0.05cm]
  {\footnotesize $S$: serialized prompt tokens\quad $S_{\max}$: context window\quad $K_{\max}$: reserved output tokens}\\[0.1cm]
  \mlsyssteps[width=0.96\textwidth,height=4.7cm,keepaspectratio]{admit_step}{2}
  \mlsyscredit{The Foundation Model, equation 1, \S2.3.2 and \S2.3.3 (scenario values).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Counting the full serialized prompt is only half of admission, because a prompt that fills the context window leaves no room for the reply. Equation 1 therefore enforces $S \le S_{\max} - K_{\max}$, where $S$ is the serialized prompt, $S_{\max}$ is the context window, and $K_{\max}$ is the reserved output budget. In Chapter 2's scenario ($S_{\max} = 8{,}192$, $K_{\max} = 1{,}024$), the input ceiling is 7,168 tokens, leaving 1,168 spare tokens after a 6,000-token prompt. Attaching a dashboard screenshot, which a vision front-end encodes as 2,048 context positions inside that same budget, pushes demand to 9,072 tokens, 880 over the window, so admission rejects the request before sending it.

  \notecue{Watch for}{Reasoning models spend intermediate hidden reasoning tokens out of $K_{\max}$ before visible text, so a short answer can exhaust a generous reserve. Failed admission triggers compaction, file trimming, image downscaling, or a wider window. Lecture 5 prices the key-value (KV) cache memory holding saved attention state for admitted tokens.}

  \notecue{Next}{Test this admission rule on a proposed workaround that halves the reply reserve.}}
\end{frame}

At every step, the model scores all 151,936 vocabulary tokens with logits and applies temperature-scaled softmax (Equation 3), dividing logits by temperature before converting them into probabilities. Right after \cd{"path": "} at $T = 1$, the 0.5B run puts 34.6\% probability on \cd{path} (the invented prefix), 16.3\% on \cd{C}, and 11.3\% on \cd{src} (the requested directory).   \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Every check on the ladder inspects text after generation finishes, so syntax errors force a retry. Grammar-constrained decoding (Definition 2.3, Equation 5) prevents syntax failures in completed replies by compiling a flat schema into a finite-state automaton, a state machine tracking legal next transitions, that adds 0 to logits preserving a valid prefix and $-\infty$ to illegal tokens. Inside the real 0.5B call's JSON path string, all eight top candidates remain legal, including \cd{path} leading to the invented file; only control characters and invalid escapes are masked out. Masking pulls Layer 1 (syntax) into generation while leaving authorization, compilation, and testing untouched.

  \notecue{Watch for}{A masked call cut off mid-string is still \cd{TRUNCATED} and must never dispatch. Include an explicit ``unknown'' schema branch so that forced syntax does not compel the model to invent missing arguments.}

\begin{frame}{Every decode step reads all the weights from memory}
  \begin{columns}[c]
    \begin{column}{0.42\textwidth}
      \centering\safeimg[width=\textwidth,height=4.4cm,keepaspectratio]{fiji-hbm-package.jpg}\\[0.02cm]
      {\footnotesize Accelerator die (center) and four stacks of high-bandwidth memory (HBM).}
    \end{column}
    \begin{column}{0.55\textwidth}
      \small
      $\tau_{\text{prefill}} \approx \dfrac{2P}{R_{\text{peak}}} = \mathbf{71.35}\ \mu\text{s}$ per prompt token\\[0.2cm]
      $\tau_{\text{decode}} \ge \dfrac{P\,b}{BW} = \mathbf{21.075}$ ms per output token\\[0.25cm]
      \uncover<2->{{\large\bfseries\textcolor{mlsysaccent}{One output token $\approx$ 295 prompt tokens}}\\[0.1cm]
      {\footnotesize Reference: 70.6B parameters $P$, 8-bit ($b$ = 1 byte), $R_{\text{peak}}$ = 1,979 TFLOP/s, $BW$ = 3.35 TB/s.}}
    \end{column}
  \end{columns}
  \mlsyscredit{Photo: AMD Fiji package, C. Spille/pcgameshardware.de, CC BY-SA 4.0, Wikimedia Commons. Floors: The Foundation Model, equations 7 and 8, \S2.8.2.}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Prompt reading and output generation hit opposite limits on an accelerator package, where a central silicon compute chip (die) sits beside four high-bandwidth memory (HBM) stacks holding weights. Prefill processes the prompt in parallel, amortizing one weight read across thousands of tokens and performing about $2P$ floating-point operations per token (one multiply and one add per parameter). At the reference 70.6B-parameter 8-bit deployment ($R_{\text{peak}} = 1{,}979\text{ TFLOP/s}$, trillion floating-point operations per second), prefill takes $\tau_{\text{prefill}} \approx 2P/R_{\text{peak}} = 71.35\,\mu\text{s}$ per token. Unbatched decode emits one token per pass, streaming all 70.6 GB across 3.35 TB/s of memory bandwidth for $\tau_{\text{decode}} \ge Pb/BW = 21.075\text{ ms}$ per token. Equation 8 divides these floors, showing one output token costs roughly 295 prompt tokens, independent of model size. On the repair agent's first turn, 8,000 prompt tokens take 0.571 s while 200 output tokens take 4.215 s, making output 2.4\% of tokens yet 88.1\% of time.

  \notecue{Watch for}{These are unbatched latency floors. Batching concurrent requests amortizes weight reads across users, as derived in the Inference Cost Foundations appendix.}

  \notecue{Next}{See why client-observed time to first token exceeds server prefill time alone.}}
\end{frame}

\begin{frame}{Client time to first token exceeds server prefill}
  \centering
  \mlsyssteps[width=0.96\textwidth,height=4.7cm,keepaspectratio]{first_token_step}{3}\\[0.06cm]
  {\footnotesize Streamed latency adds client TTFT and $K - 1$ later intervals without double-counting token 1.}
  \mlsyscredit{The Foundation Model, \S2.8.1 (Explore: First-Token Accounting on mlsysbook.ai); schematic timeline, distances not to scale.}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Those hardware floors price only accelerator execution, whereas a caller waiting on a remote service also pays network transit and queueing. The timeline compares three views of a streamed request. First, server prefill alone processes the prompt and produces logits for token 1. Second, client time to first token (TTFT) spans the wider interval covering request upload, network transit, server queueing, prefill, first-token sampling, and first-token delivery. Third, only the remaining $K - 1$ tokens require later decode passes, so total streamed latency adds client TTFT and $K - 1$ intervals without double-counting token 1. Because gateways often buffer several tokens into one network chunk, client chunk arrivals do not reveal per-step server decode timing.

  \notecue{Watch for}{A sudden doubling of client TTFT on a fixed prompt does not prove that prefill slowed down. Server queue congestion can consume an entire deadline before prefill begins, so latency diagnosis requires server-side timestamps.}

  \notecue{Next}{Return to the hardware prefill-versus-decode floors and test that output-bound asymmetry against real CPU measurements and a production code-completion trace.}}
\end{frame}
