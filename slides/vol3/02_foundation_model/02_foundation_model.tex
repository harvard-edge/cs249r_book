\begin{frame}{Admission counts the prompt and reserves the reply}
  \centering
  {\large Token-measured admission\qquad $S \;\le\; S_{\max} - K_{\max}$}\\[0.05cm]
  {\footnotesize $S$: serialized prompt tokens\quad $S_{\max}$: context window\quad $K_{\max}$: reserved output tokens}\\[0.1cm]
  \mlsyssteps[width=0.96\textwidth,height=4.7cm,keepaspectratio]{admit_step}{2}
  \mlsyscredit{The Foundation Model, equation 1, \S2.3.2 and \S2.3.3 (scenario values).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Equation 1 states token-measured admission: $S \le S_{\max} - K_{\max}$, where $S$ is the serialized prompt, $S_{\max}$ is the context window, and $K_{\max}$ is the reserved output budget. First, in Chapter 2's scenario ($S_{\max} = 8{,}192$, $K_{\max} = 1{,}024$), the input ceiling is 7,168 tokens, leaving 1,168 spare tokens after a 6,000-token prompt. Second, attaching a dashboard screenshot adds 2,048 vision context positions, pushing total demand to 9,072 tokens (880 over the window), so admission rejects the request before sending it.

  \notecue{Watch for}{Reasoning models spend hidden reasoning tokens out of $K_{\max}$ before emitting visible text, so even a short answer can exhaust a generous reserve. When admission fails, the runtime compacts history, trims files, downscales images, or routes to a wider window (Lecture 5 prices the KV memory of admitted tokens).}

  \notecue{Next}{Test this admission rule directly on a proposed workaround: halving the reply reserve.}}
\end{frame}

Unbatched decode emits one token per pass, streaming all 70.6 GB across 3.35 TB/s: $\tau_{\text{decode}} \ge Pb/BW = 21.075\text{ ms}$ per output token. Step 2 reveals Equation 8: one output token costs roughly 295 prompt tokens independent of model size. On the repair agent's first turn (8,000 prompt tokens = 0.571 s; 200 output tokens = 4.215 s), output is 2.4\% of tokens yet 88.1\% of time.

  \notecue{Watch for}{These are unbatched latency floors; batching concurrent requests amortizes weight reads across users (derived in the Inference Cost Foundations appendix).}

  \notecue{Next}{See why client-observed time to first token exceeds server prefill time alone.}}
\end{frame}

\begin{frame}{Client time to first token exceeds server prefill}
  \centering
  \mlsyssteps[width=0.96\textwidth,height=4.7cm,keepaspectratio]{first_token_step}{3}\\[0.06cm]
  {\footnotesize Streamed latency adds client TTFT and $K - 1$ later intervals without double-counting token 1.}
  \mlsyscredit{The Foundation Model, \S2.8.1 (Explore: First-Token Accounting on mlsysbook.ai); schematic timeline, distances not to scale.}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Trace a streamed request end to end in three clicks. First, server prefill processes the prompt and emits logits for token 1. Second, client time to first token (TTFT) includes request upload, network transit, server queueing, prefill, first-token sampling, and first-chunk delivery. Third, only the remaining $K - 1$ tokens require subsequent decode steps, and gateways often coalesce multiple tokens into one network chunk without double-counting token 1.

  \notecue{Watch for}{A sudden doubling of client TTFT on a fixed prompt does not prove prefill slowed down: server queue congestion can consume an entire deadline before prefill begins, so latency diagnosis requires server-side timestamps.}

  \notecue{Next}{Validate this output-bound asymmetry against real CPU measurements and a production code-completion trace.}}
\end{frame}

  \mlsysnotemeta{2.5 min}{Core}%
  Napkin Math 2.3 compares two patch interfaces on an 8,000-token context against a 15 s deadline. Step 1: a whole-file rewrite adds 350 instruction tokens and generates 1,850 output tokens, taking 39.58 s at reference floors (98.5\% decode), missing the deadline by 24.6 s.
