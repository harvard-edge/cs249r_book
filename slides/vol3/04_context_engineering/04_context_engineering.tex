\begin{frame}{A working set is what the next step needs}
  \begin{columns}[c]
    \begin{column}{0.25\textwidth}
      \centering\safeimg[width=\textwidth,height=4.2cm,keepaspectratio]{denning.jpg}\\
      {\footnotesize Peter Denning, working-set model (1968)}
    \end{column}
    \begin{column}{0.42\textwidth}
      \centering\safeimg[width=\textwidth,height=4.2cm,keepaspectratio]{ibm360_67.jpg}\\
      {\footnotesize IBM System/360 Model 67, a paged virtual-memory machine}
    \end{column}
    \begin{column}{0.29\textwidth}\small
      An operating system \textbf{measures} a working set from page references.\\[0.25cm]
      A runtime must \textbf{predict} it before the call: the model reports no reference bits.
    \end{column}
  \end{columns}
  \mlsyscredit{Photos: Louis Fabian Bachrach, Attribution; Dave Mills, public domain (University of Michigan); both Wikimedia Commons. Denning 1968; Context Engineering, \S4.2.}
  \note{%
  \mlsysnotemeta{1.5 min}{Core}%
  Managing a small active window against a large backing store is an old systems problem. In 1968, Peter Denning studied early paged virtual-memory machines such as the IBM System/360 Model 67, where an operating system maps a large address space onto limited random-access memory (RAM) in fixed-size pages. Denning defined a program's working set as the pages it actively references over a time window; keeping those pages resident prevented thrashing, where the machine swaps pages instead of running code. An agent runtime faces the same residency choice when selecting task state for the next call, with one structural difference. An operating system measures page reference bits after execution, whereas a model call emits no reference bits showing which prompt tokens mattered, so the runtime must predict the working set beforehand from task state and domain rules.

  \notecue{Watch for}{Treating recency as relevance drops durable turn-1 constraints to keep a verbose 4,000-token log that contributed only one exit code.}

  \notecue{Next}{Next, turn that working-set decision into a role-based budget equation and see how handles protect task state from observation growth.}}
\end{frame}

\begin{frame}{Appending squeezes task state; selection keeps its share}
  \centering
  \mlsyssteps[width=\textwidth,height=4.5cm,keepaspectratio]{partition_step}{2}\\[0.05cm]
  {\small $S_{\text{system}} + S_{\text{tools}} + S_{\text{state}} + S_{\text{obs}} \le \Smax - \Kmax$}\\
  {\footnotesize Handle: a short reference to a stored record, read back on demand. Dashed: the input limit.}
  \mlsyscredit{Redrawn from Context Engineering, figure ``Selection Protects the State Budget'' and equation 1 (\S4.2).}
  \note{%
  \mlsysnotemeta{3 min}{Core}%
  Predicting the working set starts by dividing the input ceiling $\Smax - \Kmax$ (window limit minus output reserve) across four roles in Equation 1. Those roles are system instructions ($S_{\text{system}}$), tool declarations ($S_{\text{tools}}$), task state ($S_{\text{state}}$, holding constraints, progress record, and staged code), and observations ($S_{\text{obs}}$). Under append-only logging, growing observations squeeze out task state by turn $t+2$. Selection instead protects each role's share by storing older logs outside the prompt behind short handles that an authorized read tool fetches on demand; a payload behind a handle re-enters only through an explicit checked read. Across Lecture 1's four lighthouse workloads, repair stresses observation growth, research stresses untrusted text, remediation stresses staleness, and support repeats instructions and tools.

  \notecue{Watch for}{Equation 1 is a planning budget. The runtime must still tokenize the final serialized request because joining text segments lets the tokenizer merge characters across boundaries and alter the sum, and a 30,000-token tool catalog squeezes every other role.}

  \notecue{Next}{Next, price append-only logging against working-set selection across all 30 turns to see whether a larger window eliminates selection.}}
\end{frame}

\begin{frame}{Appending bills 2.1 times the input of selection}
  \centering
  \safeimg[width=0.92\textwidth,height=5.0cm,keepaspectratio]{bill.pdf}\\[0.1cm]
  {\small Even a window large enough for the final 159,000-token request leaves the bill at 2.1$\times$.}
  \mlsyscredit{Context Engineering, Napkin Math 4.1 (illustrative scenario values; cumulative sums).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Even if a larger window prevented overflow, Napkin Math 4.1 shows why appending still loses on spend across 30 turns. Appending sends 39,000 fixed tokens for instructions, tools, and state plus $4{,}000\,t$ tokens of logs on turn $t$, totaling 3,030,000 input tokens. Working-set selection sends the same 39,000 fixed tokens plus a bounded 8,000-token observation slot, or 47,000 tokens per call, totaling 1,410,000 tokens, which is 2.1$\times$ fewer. A wider window holding the 159,000-token final request (167,000 with the output reserve) still pays that 2.1$\times$ penalty. Cutting each result to a 2,000-token digest fits 40 appended turns inside 81,000 tokens and clears the 30-turn cap.

  \notecue{Watch for}{Extra input tokens raise the numerator of $C_{\text{eff}}$ on failed attempts as well as accepted ones. Budgeting therefore establishes that window capacity sets only a ceiling, never a working-set policy.}

\begin{frame}{Ordering by change rate keeps the longest prefix reusable}
  \centering
  \mlsyssteps[width=\textwidth,height=4.95cm,keepaspectratio]{zones_step}{3}\\[0.08cm]
  {\footnotesize Any change in the trunk forces fresh KV computation for every trailing token, even unchanged ones.}
  \mlsyscredit{Context Engineering, \S4.4.3 (Explore: Context Zones on mlsysbook.ai); assumes compatible cached state.}
  \note{%
  \mlsysnotemeta{3 min}{Core}%
  Because causal attention derives each token's KV state from every token before it, placing slowest-changing material first maximizes prefix reuse. Change-rate ordering divides the prompt into three zones. The root holds application instructions and tool declarations in 15,000 tokens. The trunk holds task constraints, the progress record, and staged r17 source in 24,000 tokens. The leaf holds the latest observation and next-step prompt in 8,000 tokens. Cold call $n$ prefills all 47,000 tokens. Call $n+1$ changes only the leaf, so the server reuses cached KV state across root and trunk. When a patch advances the workspace to r18 and updates the trunk, prefix reuse ends after the root and every trailing token must be prefilled again.

  \notecue{Watch for}{Correctness always overrides cache reuse. Never leave stale r17 source in the trunk or stale tool declarations in the root just to keep a prefix warm.}

  \notecue{Next}{Next, inspect real serving-engine code and tokenized requests to see why even one early token breaks prefix reuse.}}
\end{frame}

\begin{frame}{A cached block's key is the whole prefix before it}
  \centering
  \safeimg[width=\textwidth,height=4.2cm,keepaspectratio]{art_vllm.pdf}\\[0.15cm]
  {\small Change one early token and every later block hashes differently.}
  \mlsyscredit{vLLM v0.6.0, vllm/core/block/prefix\_caching\_block.py, lines 834 to 855 (github.com/vllm-project/vllm), exact text, docstring shortened.}
  \note{%
  \mlsysnotemeta{1.5 min}{Optional}%
  The three-zone layout showed that editing the trunk ends prefix reuse from that point on. Real serving code from vLLM v0.6.0, an open-source serving engine that introduced paged attention and prefix caching to share KV tensors across requests, shows why cache lookup matches exact token sequences rather than meaning. Each cached block hashes its own integer token IDs together with the hash of the preceding block, chaining back to token 0. Changing one early token alters every downstream block hash, whereas placing a volatile timestamp at the end leaves every earlier block reusable. Lecture 5 develops paged (block-based) and radix (tree-structured) prefix caches in full.
