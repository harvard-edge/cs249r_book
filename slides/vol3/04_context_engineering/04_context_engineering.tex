\begin{frame}{A working set is what the next step needs}
  \begin{columns}[c]
    \begin{column}{0.25\textwidth}
      \centering\safeimg[width=\textwidth,height=4.2cm,keepaspectratio]{denning.jpg}\\
      {\footnotesize Peter Denning, working-set model (1968)}
    \end{column}
    \begin{column}{0.42\textwidth}
      \centering\safeimg[width=\textwidth,height=4.2cm,keepaspectratio]{ibm360_67.jpg}\\
      {\footnotesize IBM System/360 Model 67, a paged virtual-memory machine}
    \end{column}
    \begin{column}{0.29\textwidth}\small
      An operating system \textbf{measures} a working set from page references.\\[0.25cm]
      A runtime must \textbf{predict} it before the call: the model reports no reference bits.
    \end{column}
  \end{columns}
  \mlsyscredit{Photos: Louis Fabian Bachrach, Attribution; Dave Mills, public domain (University of Michigan); both Wikimedia Commons. Denning 1968; Context Engineering, \S4.2.}
  \note{%
  \mlsysnotemeta{1.5 min}{Core}%
  In 1968 Peter Denning defined a program's working set on paged machines like the IBM System/360 Model 67 as the pages recently referenced, keeping those pages resident in RAM to prevent thrashing. An agent runtime makes an analogous working-set choice: selecting the bounded subset of task state needed for the next step. One critical difference separates them: an operating system measures page reference bits after execution, whereas a model call emits no reference bits showing which prompt tokens mattered. The runtime must therefore predict the working set before each call using task state and domain rules.

  \notecue{Watch for}{Treating recency as relevance drops durable turn-1 constraints to keep a verbose 4,000-token log that contributed a single exit code.}

  \notecue{Next}{Formalize role-based budgeting and show how handles protect task state from observation growth.}}
\end{frame}

\begin{frame}{Appending squeezes task state; selection keeps its share}
  \centering
  \mlsyssteps[width=\textwidth,height=4.5cm,keepaspectratio]{partition_step}{2}\\[0.05cm]
  {\small $S_{\text{system}} + S_{\text{tools}} + S_{\text{state}} + S_{\text{obs}} \le \Smax - \Kmax$}\\
  {\footnotesize Handle: a short reference to a stored record, read back on demand. Dashed: the input limit.}
  \mlsyscredit{Redrawn from Context Engineering, figure ``Selection Protects the State Budget'' and equation 1 (\S4.2).}
  \note{%
  \mlsysnotemeta{3 min}{Core}%
  Equation 1 partitions the input ceiling $\Smax - \Kmax$ across four roles: system instructions ($S_{\text{system}}$), tool declarations ($S_{\text{tools}}$), task state ($S_{\text{state}}$: constraints, progress record, staged code), and observations ($S_{\text{obs}}$). First, Panel A shows append-only logging: growing observations squeeze out task state by turn $t+2$. \begin{frame}{Ordering by change rate keeps the longest prefix reusable}
  \centering
  \mlsyssteps[width=\textwidth,height=4.95cm,keepaspectratio]{zones_step}{3}\\[0.08cm]
  {\footnotesize Any change in the trunk forces fresh KV computation for every trailing token, even unchanged ones.}
  \mlsyscredit{Context Engineering, \S4.4.3 (Explore: Context Zones on mlsysbook.ai); assumes compatible cached state.}
  \note{%
  \mlsysnotemeta{3 min}{Core}%
  Change-rate ordering arranges the prompt into three zones from slowest-changing to fastest-changing. Root holds application instructions and tool schemas (15,000 tokens); trunk holds task constraints, the progress record, and staged r17 source (24,000 tokens); leaf holds the latest observation and next-step prompt (8,000 tokens). First, cold call $n$ prefills all 47,000 tokens. Second, call $n+1$ modifies only the leaf, so the server reuses cached KV state across root and trunk. Third, applying a patch advances the workspace to r18 and updates the trunk, halting prefix reuse after the root and forcing fresh prefill for every trailing token.

  \notecue{Watch for}{Correctness always overrides cache reuse: never leave stale r17 source in the trunk or stale tool schemas in the root just to keep a prefix warm.}

  \notecue{Next}{Two optional artifacts inspect real engine hashing and tokenization to prove how fragile prefix boundaries are.}}
\end{frame}

\begin{frame}{A cached block's key is the whole prefix before it}

  \mlsyscredit{vLLM v0.6.0, vllm/core/block/prefix\_caching\_block.py, lines 834 to 855 (github.com/vllm-project/vllm), exact text, docstring shortened.}
  \note{%
  \mlsysnotemeta{1.5 min}{Optional}%

Changing a single early token changes every downstream block hash, whereas placing a volatile timestamp at the end preserves reuse across every block preceding it. Lecture 5 covers paged and radix prefix caches in full.
