\begin{frame}{In an agent, a runtime closes the loop a person used to close}
  \centering
  \mlsyssteps[width=0.97\textwidth,height=5.8cm,keepaspectratio]{loop_step}{2}
  \mlsyscredit{Redrawn from Introduction, figure 1.}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  That code loop shifts control compared with earlier machine learning deployments. Predictive machine learning services mapped one input to one score with no loop at all. In a conversational assistant (panel A), the model suggests text while a human developer runs commands, reads errors, and copies results back, closing the loop and holding memory. In an agentic system (panel B), a software runtime replaces the person. It assembles context, receives a proposal across the dashed boundary, dispatches only authorized actions inside a sandbox, and collects evidence from external verifiers such as tests and linters, which check code rules without running the program, rather than trusting the model's self-report.

  \notecue{Watch for}{Only the sandbox can modify files, and only when the runtime dispatches an action. Improving model weights produces better proposals, yet it never moves permissions, isolation, persistence, or checks out of the runtime.}

  \notecue{Next}{A computer-architecture analogy next clarifies what an agent shares with a classical computer and where that analogy breaks.}}
\end{frame}

  \note{%
  \mlsysnotemeta{3 min}{Core}%
  In 1945, John von Neumann's \textit{First Draft of a Report on the EDVAC} organized the stored-program computer into arithmetic, control, memory, and input/output (I/O) organs, with central control holding authority to fetch and execute every instruction. Mapping an agent onto those classical parts clarifies how its pieces fit. The foundation model corresponds to the processor, context and stores to memory, tools to I/O, the runtime to the operating system (OS), learning to recompiling, and multi-agent systems to scaling out across machines. The red boundary marks where the analogy breaks. Unlike a deterministic processor, a foundation model only samples proposals that can be fluent yet wrong, so authority inverts. The runtime decides what executes, and context is only a lossy view of real state in files and databases.

  \notecue{Watch for}{Classical OS guarantees such as access control and logging survive only because the runtime enforces them. Refer to each component by its own name rather than calling the model a processor.}

  \notecue{Next}{Engineering that closed loop quantitatively requires a formal record of one complete task, which is the trajectory.}}
\end{frame}

\begin{frame}{A trajectory records proposals, decisions, and observations}
  \centering
  {\normalsize$\tau = (s_0, a_0, o_1, s_1, a_1, o_2, \dots, s_H)$}\quad{\footnotesize state $s$, proposed action $a$, observation $o$; $H$ turns}\\[0.06cm]
  \mlsyssteps[width=0.96\textwidth,height=5.05cm,keepaspectratio]{traj_step}{3}
  \mlsyscredit{Verbatim excerpts, turns 11 to 16 of the astropy\_\_astropy-14995 trajectory (SWE-bench experiments, mini-swe-agent 1.0.0, Claude 4 Sonnet). Notation: Introduction, Definition 1.2.}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Definition 1.2 defines a trajectory $\tau = (s_0, a_0, o_1, \dots, s_H)$ as the ordered record of states, proposed actions, runtime decisions, and observations across $H$ turns from initial context to acceptance, stop, or escalation. Turns 11 to 16 of the real \texttt{astropy} run illustrate this record. Turn 11 reproduces the crash, and turn 13 applies a one-line \code{sed} text-editor change inside the isolated container. Turn 14 then reports an \code{IndentationError} caused by that edit, so turn 16 rolls the file back with \code{git checkout}. The full trajectory preserves this failed detour alongside the final fix.

  \notecue{Watch for}{A trajectory is broader than a token transcript. Keeping only the final code diff discards the cost of turns 13 to 16, the error history, and the runtime decisions needed for auditing and acceptance.}

  \notecue{Next}{Next, examine how widely trajectory lengths vary across all 500 real repairs in the same SWE-bench Verified cohort.}}
\end{frame}

\begin{frame}{Three axes measure how far a task departs from one call}
  \centering
  \mlsyssteps[width=0.97\textwidth,height=5.9cm,keepaspectratio]{hsa_step}{3}
  \mlsyscredit{Redrawn from Introduction, figure 3; positions are illustrative task configurations.}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Lecture 0 previewed horizon, state, and authority as signposts, and Definition 1.3 now formalizes the H$\cdot$S$\cdot$A exposure space. At the origin sits a single stateless, read-only model call. The horizon axis $H$ counts turns, and every additional turn adds another chance to act on stale or wrong observations. The state axis runs from $S_0$ (stateless) and $S_1$ (prompt context and serving state such as the attention KV cache) to $S_2$ (task-local working copy) and $S_3$ (durable shared state). The authority axis runs from $A_0$ (read-only) to $A_3$ (irreversible). Placing the four lighthouses from Lecture 0 in this space contrasts their footprints directly. The repair agent runs around 100 turns at $S_2, A_1$, whereas the infrastructure remediation agent runs roughly 20 turns yet reaches $S_3, A_3$.

  \notecue{Watch for}{The H$\cdot$S$\cdot$A coordinate measures a task's inherent exposure, not its defense. Closure is the software boundary the runtime builds in response.}

  \notecue{Next}{Examine the authority axis closely to see why consequence in the environment, rather than command syntax, determines the level.}}
\end{frame}

\begin{frame}{The consequence in its environment sets an action's authority}
  \centering
  \safeimg[width=0.92\textwidth,height=5.4cm,keepaspectratio]{authority.pdf}
  \mlsyscredit{Introduction, \S1.4 and Example 1.1; Lighthouse 1.4 for the seat hold and refund.}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Authority follows whether an action's effect in its environment can be undone, separating four side-effect classes. Level $A_0$ only reads data, although reading a secret can still leak it through model output. Level $A_1$ modifies a disposable workspace where tearing down the copy undoes every edit. Level $A_2$ modifies external systems paired with a compensating action, an executable step that reverses the change under checked preconditions, such as releasing a support seat hold. Level $A_3$ has no automated reversal, such as paying out a refund or deleting unversioned production records. That resolves the opening cleanup puzzle, because the same delete command is $A_1$ in a clone and $A_3$ on a workspace without a backup.

  \notecue{Watch for}{Classify actions by consequence in the target environment rather than by command verb. Even \code{git push} shifts between $A_2$ and $A_3$ depending on whether repository rules permit rewriting branch history and whether others have pulled the commit.}

  \notecue{Next}{Inspect two launch classes in real \texttt{mini-swe-agent} code that turn the difference between $A_1$ and $A_3$ into concrete Python.}}
\end{frame}

\section{Closure}

\begin{frame}{A fail-plausible fault looks like a success}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.0cm,keepaspectratio]{faults_step}{3}
  \mlsyscredit{After Introduction, \S1.5.1 margin figure; Schlichting and Schneider 1983; Lamport et al. 1982; Avizienis et al. 2004.}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Classical distributed systems handle two fault models that break down for foundation models, leaving a third category for agents. In 1983, Schlichting and Schneider formalized fail-stop components, which halt cleanly before corrupting state so supervisors detect failure from missing heartbeats or nonzero exit codes. In 1982, Lamport, Shostak, and Pease showed that tolerating $f$ Byzantine components sending arbitrary, conflicting messages requires $3f+1$ replicas to agree. Agents instead exhibit fail-plausible faults, which Avizienis et al. (2004) classify in their dependability taxonomy as unsignaled content failures where the result is wrong and nothing announces it. For example, a patch compiles after deleting a thread-safety lock, or a test exits 0 because its assertion was removed. The process never crashes, and repeated samples from one model share blind spots.

  \notecue{Watch for}{Sampling the same model multiple times does not provide independent fault tolerance. Catching a deleted lock requires an external concurrency stress test that the agent cannot modify.}

  \notecue{Next}{Measure how often fail-plausible self-reports occurred across the 500 real SWE-bench Verified runs.}}
\end{frame}

\begin{frame}{Five evidence levels support five different claims}
  \centering
  \mlsyssteps[width=0.97\textwidth,height=5.7cm,keepaspectratio]{ladder_step}{2}

  \mlsysnotemeta{2.5 min}{Core}%

\mlsysnote{%
  \mlsysnotemeta{1.5 min}{Core}%
  Invariant closure, previewed in Lecture 0, is the central principle of Volume III, stating that constraints never rest on the model. Two independent layers surround it. Below the model, between proposal and environment, the runtime enforces mechanical bounds such as path checks, containers, and explicit capability grants specifying which tools and resources a task may touch (Lecture 8), blocking unauthorized actions.   \mlsyscredit{Introduction, \S1.6.1.}
  \note{%
  \mlsysnotemeta{1.5 min}{Optional}%
  The same $C_{\text{eff}}$ ratio decides when a task needs a model-directed loop rather than a fixed workflow. A fixed workflow still supports branches, retries such as rerunning a test known to fail intermittently, and parallelism, yet its control graph of steps and branches is fixed in advance. Deterministic setup steps such as cloning a repository, installing dependencies, and running a code linter belong in a workflow with zero token cost. A model-directed loop earns its place only on uncertain diagnostic work where $C_{\text{loop}}/p_{\text{loop}} < C_{\text{workflow}}/p_{\text{workflow}}$ under the identical contract.

  \notecue{Watch for}{Always compare workflows and loops under the same acceptance checks, and keep approval policy separate from control structure. A workflow can require human approval, and a loop can run autonomously inside a sandbox.}

  \notecue{Teach}{In a 50-minute class, skip this slide and state on the previous slide that horizon multiplies risk while acceptance divides cost.}

\end{frame}

\section{One Turn}

\begin{frame}{Every turn passes six phases, and the model owns one}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.9cm,keepaspectratio]{sixphase_step}{3}
  \mlsyscredit{Redrawn from Introduction, figure 5. Explore: Execution Lifecycle (mlsysbook.ai).}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Inside one turn, the runtime separates generation from execution across six phases. First, it assembles context within token and dollar budgets, invokes the model (the only phase the model owns, quarantining truncated or malformed replies), and validates the proposal against tool schemas (allowed format and arguments) and capability grants. Next, authorized calls run inside isolated tools with timeouts, outcomes record as evidence, and the runtime checks completion against the contract. When a timed-out call loses its reply, the remote service may already have acted; Lecture 7 shows how to settle that unknown outcome before retrying. Rejected proposals return as errors without touching tools, while waiting on long tests either holds KV-cache memory idle or drops it and forces recomputation, the tool-wait problem (Lecture 5). Every run ends accepted, failed, unresolved (including budget exhaustion), or escalated.

  \notecue{Watch for}{Phase 3, validation and authorization, is the boundary that would have stopped the destructive cleanup in the opening hook.}

  \notecue{Next}{Trace the recorded \texttt{astropy} trajectory to see these six phases in real tool logs.}}
\end{frame}
