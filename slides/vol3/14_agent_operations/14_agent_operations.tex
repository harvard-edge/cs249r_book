\begin{frame}{A trace ties every span of one request to its parent}
  \begin{columns}[c]
    \begin{column}{0.66\textwidth}
      \centering\safeimg[width=\textwidth,height=5.9cm,keepaspectratio]{dapper_fig2.png}
    \end{column}
    \begin{column}{0.31\textwidth}
      \small A \textbf{span}: one unit of work with an id, a parent id, a start, and an end.\\[0.2cm]
      Children can overlap; the parent encloses them.\\[0.2cm]
      \textcolor{mlsysaccent}{\textbf{In an agent:}} each model call, tool run, and check is a span of one trial.
    \end{column}
  \end{columns}
  \mlsyscredit{Sigelman et al., ``Dapper, a Large-Scale Distributed Systems Tracing Infrastructure,'' Google Technical Report dapper-2010-1, 2010, Figure 2.}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Aggregate trial totals hide where a multi-step run spent its time across hosts. In 2010, Sigelman and colleagues at Google published Dapper (Figure 2), demonstrating that distributed tracing could run continuously at production scale. Its model was carried forward by OpenTelemetry, an open standard for telemetry collection that captures nested calls in span trees and asynchronous interactions through trace links. Here, one front-end request expands into five spans across servers, each recording a name, span ID, parent ID, and timestamps. Span 3, Backend.DoSomething, runs from 24 to 30 while invoking Span 4 for 3 units and Span 5 for 4 units concurrently, so summing those child durations exceeds its 6-unit wall time. In an agent, every model call, tool run, and check is a span of one trial.

    \notecue{Watch for}{Cross-host timestamps need clock alignment. Apparent overlap can reflect clock skew (time offset between machine clocks) rather than concurrency, so causal happened-before order comes from parent and dispatch links instead of raw timestamps.}

    \notecue{Next}{Slide 7 replays Napkin Math 14.1 through the real OpenTelemetry Python SDK to isolate the critical path.}
  }
\end{frame}

\begin{frame}{Three records carry three different guarantees}
  \centering
  \mlsyssteps[width=0.96\textwidth,height=5.7cm,keepaspectratio]{records_step}{3}
  \mlsyscredit{Operating Agents, \S14.2.1, Systems Perspective 14.1, \S14.2.2, and \S14.3.1.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Because a trace already carries timings and operation IDs, teams are tempted to reuse it for crash recovery or pass-rate counting, yet one runtime event often writes to three distinct records with different guarantees. First, the diagnostic trace supports timing and debugging, so it may legitimately sample, truncate payloads, or drop spans under load. Next, Lecture 11's trajectory log records acknowledged transitions and is never sampled, because dropping entries corrupts crash recovery. Finally, the accounting record lists every admitted trial, configuration, criteria, verdict status, spend, and drop; because it is never sampled, all population rates come from it. A green span never proves task acceptance, since a test can exit 0 with failed assertions, and a trace ID correlates events without authorizing calls. Segment 1 separates three duties, tracing to explain, logging to recover, and accounting to count, leaving diagnostic traces as the one stream retention can sample.

\begin{frame}{Tracing every request cost Google search 16\% in latency}
  \centering
  \safeimg[width=0.88\textwidth,height=4.4cm,keepaspectratio]{dapper_bars.pdf}\\[0.1cm]
  {\small Dapper's first production version kept about 1 trace in 1,024 requests.}
  \mlsyscredit{Sigelman et al., ``Dapper,'' Google Technical Report dapper-2010-1, 2010, Table 2 (web search cluster; measurement error 2.5\% for latency) and \S4.4.}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Keeping every trace sounds safest for debugging, yet production measurements show why full tracing breaks overhead budgets. On its web search cluster, Google measured Dapper's overhead across sampling rates (Sigelman et al. 2010, Table 2). Tracing every request added 16.3 percent to average latency, and sampling 1 in 16 added 2.12 percent. At 1 in 1,024, latency shifted by $-0.20$ percent, inside the 2.5 percent measurement error, while throughput stayed within 1.48 percent. Early Dapper therefore kept roughly 1 trace in 1,024. That rate worked for high-volume search where bugs recurred thousands of times, yet it misses rare failures in an agent fleet running only a few thousand trials per day.

    \notecue{Watch for}{Unlike 2010 web remote procedure calls (RPCs), agent traces carry large prompts and tool outputs, so storage capacity usually limits retention before CPU overhead does.}

    \notecue{Next}{Slide 12 computes how often 5 percent head sampling misses a failure occurring 20 times.}
  }
\end{frame}

\begin{frame}{Estimate: does a 5\% sample keep a rare failure?}
  \mlsysactivity{Estimate}{2 min}
  \begin{columns}[c]
    \begin{column}{0.36\textwidth}
      \small \textbf{Head sampling} decides at the start of a trial, before its outcome.\\[0.15cm]
      P(no trace of a mode seen $n$ times)\\[0.05cm]
      $= (1-p)^{n}$\\[0.2cm]
      {\normalsize A mode occurs 20 times at $p = 5\%$.}\\[0.15cm]
      \uncover<2->{$0.95^{20} = \mathbf{\textcolor{mlsysaccent}{36\%}}$ chance of no trace}
    \end{column}
    \begin{column}{0.62\textwidth}
      \centering\mlsyssteps[width=\textwidth,height=5.2cm,keepaspectratio]{miss_step}{2}
    \end{column}
  \end{columns}
  \mlsyscredit{Operating Agents, \S14.3.1, Purpose, and Checkpoint 14.2. Derived.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Dapper's uniform strategy, called head sampling, chooses independently with probability $p$ at trial start before the outcome is known, missing a failure mode occurring $n$ times with probability $(1-p)^{n}$. The plot marks two anchors. At 1 percent, a mode seen 10 times leaves zero traces 90 percent of the time. At 10 percent, a mode seen 5 times leaves nothing 59 percent of the time, and falling to 0.5 percent requires 50 occurrences. Before reading on, solve Checkpoint 14.2 for $p = 5\%$ and $n = 20$ to find the chance of zero traces.

    \notecue{Check}{Evaluating $(1-0.05)^{20}$ gives $0.95^{20} = 36\%$. A tempting guess underestimates that risk across 20 occurrences, yet over a third of the time uniform pre-outcome sampling still leaves engineers with zero examples of a recurring failure.}

    \notecue{Watch for}{Head sampling stays valid for population means when each kept trace logs its inclusion probability, its chance of being selected, yet it misses the rare incidents postmortems need.}

    \notecue{Teach}{Give two minutes to compute the miss probability before revealing the curve.}

    \notecue{Next}{Slide 13 introduces tail selection, which buffers traces until the verdict arrives.}
  }
\end{frame}

\begin{frame}{Tail selection waits for the verdict before it keeps a trace}
  \centering
  \mlsyssteps[width=0.96\textwidth,height=5.6cm,keepaspectratio]{tail_step}{3}
  \mlsyscredit{Redrawn from Operating Agents, fig.~1 and Table 3 (\S14.3.2; Explore: Tail Sampling Pipeline on mlsysbook.ai).}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    To keep rare failures without storing every routine run, tail selection defers the retention decision until task verdicts arrive. Ingestion splits into two paths. Every admitted trial enters the accounting record directly, protecting the denominator, while trace bodies wait in a staging buffer across the verdict window, which can span hours for slow regressions. The selector then applies strict precedence so no trace is saved twice. It keeps failed criteria and policy violations first, pending trials provisionally, slow or costly outliers next, and a 2 percent random control sample of ordinary trials. Under burst pressure, the buffer evicts ordinary bodies from the bottom first while logging early drops in the accounting record. Because kept traces enrich failures, population rates still come from the accounting record or from inverse-probability weights, which scale each kept trace by the inverse of its sampling chance.

    \notecue{Watch for}{Size staging buffers for outage bursts of long, tool-heavy runs rather than steady averages.}

    \notecue{Next}{Slide 14 maps this pipeline onto real OpenTelemetry Collector tail-sampling configuration.}
  }
\end{frame}

\begin{frame}{A real tail sampler decides after a fixed wait}
  \raggedright{\footnotesize\textbf{Collector configuration (excerpt)}}\par\vspace{0.1cm}
  \renewcommand{\arraystretch}{1.25}
  \begin{tabular}{@{}p{6.2cm}p{7.6cm}@{}}
    \begin{logblock}[9.5]decision\_wait: 10s\end{logblock} & \small$\leftarrow$ the verdict window: decide after 10 s\\
    \begin{logblock}[9.5]status\_codes: [ERROR, UNSET]\end{logblock} & \small$\leftarrow$ span status, which carries no task verdict\\
    \begin{logblock}[9.5]num\_traces: 100\end{logblock} & \small$\leftarrow$ the buffer; when full, it drops traces:\\
    & \begin{logblock}[8.5]sampling\_trace\_dropped\_too\_early\end{logblock}
  \end{tabular}\par\vspace{0.18cm}
  \uncover<2->{\small\textcolor{mlsysaccent}{\textbf{For an agent:}} feed the verdict back as an attribute, and set the wait past the slowest grader.}
  \mlsyscredit{OpenTelemetry Collector Contrib, processor/tailsamplingprocessor/README.md, commit b123684 (example policies abridged; FAQ).}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Production telemetry tools already implement this buffered selector, yet typical web-service configurations assume short requests rather than slow agent graders. The OpenTelemetry Collector, OpenTelemetry's telemetry-processing pipeline, provides tail selection through its Contrib tailsamplingprocessor. Its decision\_wait setting, 10 s here, fixes the verdict window, while num\_traces, 100 here, caps the in-memory staging buffer and increments sampling\_trace\_dropped\_too\_early on overflow. Its status\_codes policy, [ERROR, UNSET], filters on span status alongside latency and probabilistic control rules. For a repair agent whose verdict from sealed tests arrives minutes or hours later, a 10-second wait decides solely on span status rather than task acceptance. Supporting agents therefore requires writing the verdict back as a span attribute, a structured key-value field on the span, or a timed event when it arrives, and sizing the wait and buffer for the slowest grader.

  }
\end{frame}

Failed plus pending trials set a 16.8 GB/day floor, which triples if failed and pending rates triple during an outage, and each percentage point of control sampling adds 3.2 GB/day.

\mlsysnote{%
  \mlsysnotemeta{1.5 min}{Core}%
  To turn that decision record into an auditable promotion rule, the release check is declared in advance as a conjunction of four separate conditions. First, the paired acceptance lower limit $L$ must exceed $-\delta$. Second, candidate trajectory goodput $\mathcal{G}_{\text{cand}}$, meaning accepted tasks per hour on matched load (developed in Lecture 19), must stay within relative tolerance $\rho$ of baseline. Third, 99th-percentile completion time $T_{99}$ must meet cohort deadline $D$. Fourth, verified violations $V$ must equal zero. Because the rule is a logical AND, no strong latency score can buy back an inconclusive acceptance interval.

  \notecue{Watch for}{The release check enforces only these four terms. A shadow alarm for tool-mix drift routes to human review without failing the check alone.}

  \notecue{Next}{Slide 34 applies this conjunction to candidate\_v2 and accounts for multiple-testing error.}
