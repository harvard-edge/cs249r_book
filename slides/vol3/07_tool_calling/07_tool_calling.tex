\begin{frame}{Every call passes four runtime stages before and after it acts}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=5.15cm,keepaspectratio]{loop_step}{4}\\[0.05cm]
  \uncover<4->{\small Complete mediation: every call, reads included, passes the check.}
  \mlsyscredit{After Tool Calling, \S7.2.1, figure 1 (redrawn).}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Suppose one model turn proposes three calls, refining the validate, execute, and observe phases from Lecture 1. First, Step 1 validates structure against tool schemas, rejecting \texttt{call\_3} with a structured error the model can fix. Second, Step 2 authorizes resolved targets against session grants, rate limits, and concurrency caps for reads as well as writes, rejecting \texttt{call\_2}. Third, Step 3 dispatches \texttt{call\_1}, tracks completion, and shapes the bounded response matched to its call ID. Fourth, Step 4 delivers one observation per call ID, errors included, achieving complete mediation on both outbound requests and inbound observations.

  \notecue{Watch for}{Only shaping runs after execution; prose rules like ``never delete production data'' sit inside the prompt rather than in these four stages, so the runtime must refuse disallowed proposals mechanically.}

  \note{%
  \mlsysnotemeta{1.5 min}{Core}%
  James Anderson's 1972 U.S. Air Force study coined the reference monitor with three non-negotiable properties: tamper-proof (model tokens and tool outputs cannot alter policy), always invoked (no bypass route exists), and small enough to verify deterministically (risk classifiers may advise, but deterministic code decides). In an agent system, the runtime's validation and authorization path serves as the first reference monitor, backed by each endpoint's own access check.

  \notecue{Watch for}{Adding an unrestricted shell or ``convenient'' \texttt{run\_python} tool alongside a checked file adapter violates Principle B (always invoked) because one unmediated bypass invalidates every check on the mediated path.}

\begin{frame}{A timeout leaves three outcomes open}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=5.0cm,keepaspectratio]{worlds_step}{3}\\[0.05cm]
  \uncover<3->{{\footnotesize\ttfamily \{"transport\_status": "timeout", "effect\_status": "unknown"\}}}
  \mlsyscredit{Tool Calling, \S7.1, \S7.2 listing 1, and \S7.5 (Definition 7.4).}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Suppose the remediation agent sends \texttt{POST /containers/srv-stage-04/restart} and its 2 s client timeout fires. Walk through all three worlds: Step 1, the request dropped before arrival (no effect); Step 2, the restart executed and the reply dropped; Step 3, the request remains in flight or executing and will commit later. Echoing Birrell and Nelson (1984), a timeout proves only that the caller stopped waiting, leaving \texttt{effect\_status: "unknown"}. Definition 7.4 keeps uncertain effects unsettled until deduplication, a reconciliation query, or an authorized decision resolves them.

  \notecue{Watch for}{Recording a timeout as ``failed'' is the root mistake that triggers blind retries in Worlds 2 and 3, duplicating a live mutation.}

  \mlsysnotemeta{3.5 min}{Core}%
  Work Napkin Math 7.1: 2\% request loss, 2\% reply loss, one blind retry per timeout, and 200,000 mutating calls per day (50 workers $\times$ 4,000 calls). Step 2 derives both rates: timeouts happen $1 - 0.98^2 = 3.96\%$ of the time, while a duplicate requires first delivery (0.98), lost reply (0.02), and retry delivery (0.98), totaling $1.9208\%$ or roughly 3,842 duplicate restarts per day. \begin{frame}{An unchanged probe cannot rule out an attempt still in flight}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=6.0cm,keepaspectratio]{delayed_step}{3}
  \mlsyscredit{After Tool Calling, \S7.5.1 figure (redrawn) and \S7.5.4.}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Walk through the delayed-packet race in three steps. First, Attempt A stalls in the network and times out. Second, the runtime probes the container and observes it unchanged, an accurate report of the present instant. Third, trusting that probe, the runtime dispatches Attempt B, restarting the container just before delayed Attempt A arrives and restarts it a second time. Settlement before retry permits repeating an uncertain mutation only when the operation is idempotent, the endpoint deduplicates, or evidence rules out in-flight attempts (such as expiry); otherwise mark the effect unsettled, block dependent work, and escalate (using pre-dispatch baselines and Lecture 12 compensation where deduplication is absent, with intent logged durably in Lecture 11).

  \note{%
  \mlsysnotemeta{3 min}{Core}%
  Trace the three-step IETF \texttt{Idempotency-Key} contract. First, Step 1 mints one operation ID when admitting intent (never by hashing tool name plus arguments, which would block an intentional second restart an hour later) and a fresh attempt ID per network send, reusing the operation ID on retry until attempts exhaust as \texttt{unresolved}. Second, Step 2 looks up the operation ID bound to caller, scope, and arguments at the endpoint: completed returns the stored result, in-progress returns pending (HTTP 409), and absent executes and stores both effect and result atomically inside one transaction. Third, Step 3 rejects reusing a key with altered arguments (422 in the IETF draft; 409 in the chapter).
