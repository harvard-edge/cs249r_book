\begin{frame}{Every call passes four runtime stages before and after it acts}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=5.15cm,keepaspectratio]{loop_step}{4}\\[0.05cm]
  \uncover<4->{\small Complete mediation: every call, reads included, passes the check.}
  \mlsyscredit{After Tool Calling, \S7.2.1, figure 1 (redrawn).}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  If a runtime sent proposed calls straight to tools, any invalid or unauthorized proposal would act directly. Follow three calls from one model turn through four runtime stages that refine the validate, execute, and observe phases of Lecture 1's six-phase turn lifecycle. First, validation checks structure against tool schemas and rejects \texttt{call\_3} with a structured error the model can repair. Next, authorization checks resolved targets against session grants, rate limits, and concurrency caps for reads and writes alike, rejecting \texttt{call\_2}. The runtime then dispatches \texttt{call\_1}, tracks and settles its outcome, and shapes a bounded observation matched to its call ID, delivering one observation per call ID, errors included. Recall from Lecture 1 that complete mediation checks every access; here the runtime extends it to both outbound calls and inbound observations.

  \notecue{Watch for}{Only shaping runs after execution. Prose instructions such as ``never delete production data'' sit inside the prompt rather than in these four runtime stages, so the runtime must refuse disallowed proposals mechanically.}

\begin{frame}{A reference monitor is tamper proof, always invoked, and small}
  \begin{columns}[c]
    \begin{column}{0.25\textwidth}
      \centering\safeimg[width=\textwidth,height=4.6cm,keepaspectratio]{anderson_cover.png}
    \end{column}
    \begin{column}{0.72\textwidth}
      \centering\safeimg[width=\textwidth,height=2.4cm,keepaspectratio]{anderson_rvm.png}\\[0.3cm]
      \raggedright\small An unrestricted shell beside a checked file tool breaks B: the file checks become advisory.
    \end{column}
  \end{columns}
  \mlsyscredit{J. P. Anderson, Computer Security Technology Planning Study, ESD-TR-73-51, Vol.~II, U.S. Air Force, October 1972, cover and p.~25 (NIST CSRC archive). Tool Calling, \S7.2.2, Definition 7.2.}
  \note{%
  \mlsysnotemeta{1.5 min}{Core}%
  Stating complete mediation as a policy does not ensure every tool route honors it. Half a century ago, operating systems faced the same problem when untrusted programs requested operations they could not perform directly. In an October 1972 computer security study for the U.S. Air Force, J. P. Anderson formalized the reference monitor, the non-bypassable enforcement component turning policy into a checkable boundary, around three properties. It must be tamper-proof, so model tokens and tool outputs cannot alter rules; always invoked, leaving no bypass route; and small enough to verify deterministically, meaning learned classifiers that score operational risk may advise while deterministic code decides. In an agent system, host validation and authorization form the first monitor, backed by each endpoint's own access check.

  \notecue{Watch for}{Adding an unrestricted shell or a ``convenient'' \texttt{run\_python} tool beside a checked file adapter violates Principle B (always invoked), because one unmediated bypass invalidates every check on the mediated path.}

  \notecue{Next}{Next, examine what each check layer inside that monitor proves and what it leaves unchecked on the repair agent's edit tool.}}
\end{frame}

  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Enforcing a reference monitor in code begins with a machine-checkable tool contract, yet syntax alone settles only the first of four layers. In the JSON schema for \texttt{conditional\_replace\_file}, \texttt{path}, \texttt{expected\_version}, and \texttt{replacement} are required, while \texttt{additionalProperties: false} blocks invented flags such as \texttt{force}. Across the four check layers, structure catches a numeric path yet leaves permission and freshness open; authority leaves rate limits open; limits leave action-time state open; and passing preconditions proves only a clean write, not task acceptance. Because a symbolic link (symlink) can be swapped between check and use in a time-of-check to time-of-use (TOCTOU) race, the tool must resolve paths inside the workspace, operate on the resolved handle, and return one of four contract outcomes (new revision, version conflict, client error, or timeout).

  \notecue{Watch for}{Grammar-constrained decoding (Lecture 2) eliminates syntax failures before generation finishes, yet it can neither resolve filesystem paths nor verify current file versions.}

\end{frame}

\begin{frame}{An action-time precondition commits with the write}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=6.0cm,keepaspectratio]{cas_step}{3}
  \mlsyscredit{Tool Calling, \S7.3.3 (conditional update; the storage form of compare-and-swap).}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Recall from Lecture 6's memory-write policy that compare-and-swap conditions an update on the expected prior version. Applying that mechanism to \texttt{src/pool.py} shows why checking freshness at the host is too early. Suppose the repair agent reads r17 and spends seconds generating a patch while a teammate commits r18. An unconditional write silently overwrites r18 with zero error. Passing \texttt{expected\_version: r17} to \texttt{conditional\_replace\_file} instead lets the storage endpoint resolve the file, check the current version, and write inside one atomic boundary, rejecting the stale write with a version conflict so the runtime triggers a fresh read and a new proposal.

  \notecue{Watch for}{Checking the version in a separate read call before writing leaves a race window. A dry run that only tests whether the edit applies against r17 acquires no lock, and even a clean conditional write still requires tests to prove the bug is fixed.}

\begin{frame}{A timeout leaves three outcomes open}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=5.0cm,keepaspectratio]{worlds_step}{3}\\[0.05cm]
  \uncover<3->{{\footnotesize\ttfamily \{"transport\_status": "timeout", "effect\_status": "unknown"\}}}
  \mlsyscredit{Tool Calling, \S7.1, \S7.2 listing 1, and \S7.5 (Definition 7.4).}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Suppose the remediation agent sends \texttt{POST /containers/srv-stage-04/restart} and its 2 s client timeout fires, leaving three indistinguishable outcomes. In World 1, the request dropped before arrival, causing no effect. In World 2, the restart executed and the reply dropped. In World 3, the request remains in flight or executing and will commit later. Recall from Lecture 2 that Birrell and Nelson's 1984 remote procedure call (RPC) paper established that a timeout proves only that the caller stopped waiting, leaving \texttt{effect\_status: "unknown"}. Definition 7.4 keeps uncertain effects unsettled until endpoint deduplication (suppressing re-execution of a repeated operation ID), a reconciliation query checking target state, or an authorized decision resolves them.

  \notecue{Watch for}{Recording a timeout as ``failed'' is the mistake that triggers blind retries in Worlds 2 and 3, duplicating a live mutation.}

  \notecue{Next}{Next, calculate and measure how often one blind retry turns a 2\% packet drop into thousands of duplicate actions.}}
\end{frame}

\begin{frame}{An unchanged probe cannot rule out an attempt still in flight}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=6.0cm,keepaspectratio]{delayed_step}{3}
  \mlsyscredit{After Tool Calling, \S7.5.1 figure (redrawn) and \S7.5.4.}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  After a timeout, checking target state before retrying looks safe, yet World 3 breaks that intuition. Suppose Attempt A stalls in the network and times out. The runtime probes the container and observes it unchanged, which holds at that instant. Trusting that probe, it dispatches Attempt B, restarting the container moments before delayed Attempt A arrives and restarts it again. Settlement before retry permits repeating an uncertain mutation only when the operation is idempotent, the endpoint deduplicates, or evidence such as request expiry rules out in-flight attempts. Otherwise, the runtime marks the effect unsettled, blocks dependent work, and escalates. When deduplication is unavailable, recovery relies on initial state baselines recorded before dispatch, durable intent logs recording planned actions ahead of dispatch (developed in Lecture 11), and compensating actions (developed in Lecture 12).

  \notecue{Watch for}{Even observing the desired state on a probe does not prove your attempt caused it rather than another actor. An operation-specific receipt provides stronger proof.}

\begin{frame}{Operation identity across attempts makes a retry harmless}
  \centering
  \mlsyssteps[width=0.98\textwidth,height=4.6cm,keepaspectratio]{opid_step}{3}\\[0.05cm]
  \uncover<3->{\footnotesize IETF draft: {\ttfamily Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"}\\
  Same key, other payload: \textbf{422}; still running: \textbf{409}.}
  \mlsyscredit{After Tool Calling, \S7.5.3 fig.~2 (Explore: Idempotency Flow on mlsysbook.ai). IETF draft-ietf-httpapi-idempotency-key-header-07 (2025).}
  \note{%
  \mlsysnotemeta{3 min}{Core}%
  For event-producing operations that cannot retry safely on their own, the Internet Engineering Task Force (IETF), the standards body behind HTTP, defines an \texttt{Idempotency-Key} header contract. The runtime mints one operation ID when admitting intent and a fresh attempt ID per send. It never hashes tool name plus arguments, which would block an intentional second restart an hour later, and reuses that operation ID across retries until attempts exhaust as \texttt{unresolved}. The endpoint looks up the operation ID bound to caller, scope, and arguments. Completed entries return the stored result, in-progress entries return pending (HTTP 409), and absent entries execute and record both effect and result inside one atomic transaction. Reusing a key with altered arguments is rejected, returning 422 in the IETF draft and 409 in the chapter.

  \notecue{Watch for}{Key retention lifetime is part of the contract. Once keys expire, an old operation ID runs anew, and a stalled prior worker claiming ownership needs fencing tokens (increasing ownership numbers checked before commit, Lecture 11).}

\end{frame}

Structured tools cost \$1.20/attempt ($p_{\text{acc}} = 0.80$, per-attempt unconfined-change probability 0.001); the shell has $p_{\text{acc}} = 0.78$ and probability 0.004.   \thumbline{thumb_headtail_step3.pdf}{An observation states what it measured, what it dropped, and what is still running.}\\[0.12cm]
  \thumbline{thumb_catalog_step3.pdf}{A toolkit is a token budget judged by cost per accepted task.}
  \note{%
  \mlsysnotemeta{1 min}{Core}%
  Validate, authorize, dispatch, and shape every call, reads included, because schemas and tool lists grant nothing. Execute state preconditions atomically with writes at the endpoint. Treat timeouts as unknown outcomes settled through safe repeat behavior, deduplication, or evidence. Bound observations honestly with omission counts and pending states, and judge toolkits by cost per accepted task ($C_{\text{eff}}$).

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.3cm}
    \item Tool servers publish descriptions and hints that clients must not trust. What would a trustworthy descriptor need: a signature, a test suite, an audit?
    \item An agent that clicks through an interface cannot make a click atomic. Which actions should an agent never take through pixels?
    \item Who should set a task's grants: the user, the runtime, or a policy the model drafts and a human approves?
  \end{itemize}
  \note{%
  \mlsysnotemeta{1 min}{Optional}%
  Even with those five rules in place, three practical boundaries remain active research problems. First, consider what cryptographic signatures, test suites, or audits could make third-party MCP descriptors trustworthy. Second, consider which high-consequence actions should never run through non-atomic pixel clicks (\S7.10). Finally, consider how users, runtimes, and human-reviewed drafts should divide authorship of per-task grants.
