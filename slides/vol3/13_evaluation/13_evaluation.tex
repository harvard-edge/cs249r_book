\begin{frame}{Pending and unknown trials stay in the denominator}
  \begin{columns}[c]
    \begin{column}{0.36\textwidth}
      \small
      \textbf{\textcolor{figgreen}{pass}}: evidence meets the criterion\\[0.08cm]
      \textbf{\textcolor{figred}{fail}}: evidence shows a violation\\[0.08cm]
      \textbf{pending}: check still running\\[0.08cm]
      \textbf{unknown}: no evidence at the cutoff\\[0.25cm]
      Accept only if every mandatory criterion passes. Any fail ends it.
    \end{column}
    \begin{column}{0.62\textwidth}
      \centering\mlsyssteps[width=\textwidth,height=3.6cm,keepaspectratio]{verdicts_step}{2}\\[0.05cm]
      {\footnotesize 100 trials: 60 accepted, 25 failed, 15 unresolved (illustrative)}
    \end{column}
  \end{columns}
  \mlsyscredit{Agent Evaluation, \S13.2.3, the four-verdict rule. Counts illustrative; rates (derived).}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Forcing an unfinished check into pass or fail either credits missing work or invents a violation. Instead, each mandatory criterion resolves to one of four verdicts (pass, fail, pending, or unknown), kept separate from trajectory runtime states. Aggregation short-circuits so that any mandatory fail rejects the trial, every mandatory pass accepts it, and any other case remains pending or unknown. Across 100 illustrative trials (60 accepted, 25 failed, and 15 unresolved), the default rule counts unresolved trials as not accepted, giving a 60 percent acceptance rate with bounds $[60\%, 75\%]$. Dropping those 15 unresolved trials creates survivorship bias, inflating the rate to 70.6 percent because hard tasks time out most often while artificially lowering cost per accepted task.

    \notecue{Watch for}{Under Lecture 10's bounded-liability admission, which reserves worst-case liability before dispatch, outstanding resource reservations stay separate from settled charges because an evaluation cutoff does not cancel a running cloud job.}

    \notecue{Next}{To see how easily real evaluation code breaks this rule, Slide 11 inspects SWE-bench grader code where missing test evidence once defaulted to pass.}
  }
\end{frame}

  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Default branches in real harnesses violate the four-verdict rule when absent evidence defaults to success. In grading.py (commit 02e7a74) of the SWE-bench repository-repair benchmark, the harness evaluates two test lists, FAIL\_TO\_PASS (tests reproducing the bug, which must turn green) and PASS\_TO\_PASS (regression guards, which must stay green), requiring both pass rates to equal 1. In the red branch, if total == 0 returned 1, turning zero executed tests into a perfect score. In the purple fix, adding SKIPPED to test\_failed, paired with August 2026 commits rejecting runs with no test results, closed the loophole where a patch causing required tests to skip scored as resolved. Under the four-verdict rule, a skipped required test is fail or unknown, never pass.

\begin{frame}{Grader isolation keeps the grader outside the agent and its code}

\begin{frame}{Model judges change verdicts when two answers swap places}

    \mlsysnotemeta{1.5 min}{Core}%

\begin{frame}{New tasks shrink both variance terms; repeats shrink one}
  \centering
  {\small $\operatorname{Var}(\hat{p}) = \dfrac{\sigma_{\text{task}}^2}{N} + \dfrac{\sigma_{\text{run}}^2}{N\,r}$\qquad
  {\footnotesize $N$ tasks, $r$ runs each; pilot: $\sigma_{\text{task}}^2 = 0.08$, $\sigma_{\text{run}}^2 = 0.16$; budget 600 runs}}\\[0.2cm]
  \only<1|handout:0>{\safeimg[width=0.82\textwidth,height=3.9cm,keepaspectratio]{designs_step1.pdf}\\[0.1cm]{\small New tasks free: one run each wins}}%
  \only<2->{\safeimg[width=0.82\textwidth,height=3.9cm,keepaspectratio]{designs_step2.pdf}\\[0.1cm]{\small A new fixture costs 10 runs: 5 runs each wins}}
  \mlsyscredit{Agent Evaluation, \S13.5.1, equation 1; numbers from exercise 1 (hypothetical). Standard errors (derived).}
  \note{%
    \mlsysnotemeta{2.5 min}{Optional}%
    Should an evaluation budget buy fresh tasks or repeats? Equation 1 splits acceptance-rate variance across $N$ tasks and $r$ runs each into task ($\sigma_{\text{task}}^2/N$) and run ($\sigma_{\text{run}}^2/(Nr)$) terms; repeats shrink only run variance, while new tasks shrink both. Exercise 1's pilot has mean $p = 0.6$ and $\sigma_{\text{task}}^2 = 0.08$; subtracting $\sigma_{\text{task}}^2$ from total binary variance $p(1 - p) = 0.6 \times 0.4$ leaves $\sigma_{\text{run}}^2 = 0.16$ for a 600-run budget. With free fixtures, 600 tasks $\times$ 1 run reaches a 2.00-point standard error, beating 200$\times$3 (2.58) and 100$\times$6 (3.27). At $r = \sigma_{\text{run}}^2/\sigma_{\text{task}}^2 = 2$, the run term matches the task term, past which task variance dominates; pricing each new fixture at 10 runs makes repeats pay off, so 40 tasks $\times$ 5 runs wins at 5.29 points versus 54$\times$1 at 6.67.

    \notecue{Watch for}{Running 20 tasks 10 times yields 200 trials but only 20 independent tasks, and tasks from one repository cluster further.}

\begin{frame}{Zero failures in 50 tasks still allows a 7\% failure rate}
  \centering
  \safeimg[width=0.88\textwidth,height=4.5cm,keepaspectratio]{wilson.pdf}\\[0.05cm]
  {\small Wilson centers on $\dfrac{x + z^2/2}{n + z^2}$, uses the hypothesized rate in its variance, and never leaves $[0, 1]$.}

    \mlsysnotemeta{1.5 min}{Optional}%

Over those same runs, per-task curves place candidate pass@8 at 91.7 percent and $\text{pass}^8$ at 50.0 percent for both configurations, flattening quickly because most tasks are all-or-nothing for this 7B model.

    \notecue{Watch for}{Because the 96 run pairs correlate by clustering inside only 12 tasks, this interval is narrower than true task-level uncertainty. Retries also helped only where visible tests caught the bug.}

    \notecue{Next}{Seeing pass@$k$ and $\text{pass}^k$ diverge on the same runs raises which quantifier a deployment needs; Slide 29 maps each of the four lighthouse workloads to its matching metric.}

\end{frame}

Because $\text{pass@}k$ measures pool availability before selection (Lecture 3), workloads with a pre-delivery checker report priced selected acceptance instead of raw $\text{pass@}k$. Repair agents (sealed tests on the exact artifact) and research agents (calibrated judge with citation checks) verify before delivery and retry failures, so they report selected acceptance; our retrying candidate\_v2 fits here, up to checker coverage. Support agents (policy rubric, first reply read immediately) and remediation agents (replica checks plus hard production limits that statistics alone cannot supply) cannot hide failures behind retries, so they require $\text{pass}^k$.
