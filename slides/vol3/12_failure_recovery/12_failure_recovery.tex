    To see why timeouts never prove non-execution in practice, trace a provisioning call to Amazon EC2, Amazon's cloud virtual-machine service. \begin{frame}{Compensation restores only the predicates it declares}
  \centering
  {\normalsize Compensation: a \textbf{new forward action} that re-establishes declared conditions.}\\[0.15cm]
  {\large $S_{\text{comp}} \equiv_{P} S_{\text{pre}} \iff \phi(S_{\text{comp}}) = \phi(S_{\text{pre}})\ \text{for every}\ \phi \in P$}\\[0.1cm]
  \vspace{0.2cm}
  \uncover<2->{\safeimg[width=0.92\textwidth,height=3.35cm,keepaspectratio]{comp_states.pdf}}\\[0.1cm]
  \uncover<3->{\footnotesize Restoring the snapshot \op{ws\_r18} resets local files; it never releases the remote environment.}
  \mlsyscredit{Failure Recovery, \S12.3.2, equation 2 and Definition 12.2.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Once a remote effect like env\_r18\_01 is established, no all-or-nothing distributed transaction spans the runtime log and external services, so local rollback cannot reverse it. Definition 12.2 and equation 2 therefore define compensation as a separately committed forward operation that restores declared predicates (true-or-false conditions about the world) in a set $P$, yielding $S_{\text{comp}} \equiv_P S_{\text{pre}}$. For env\_r18\_01, two predicates in $P$, allocated and depended on by an admitted test, toggle from false to true and back to false while billing charges and audit records stay outside $P$. Restoring local snapshot ws\_r18 resets files on disk without releasing the remote billed VM, and if a peer workflow attaches to env\_r18\_01, live admission checks on active dependencies block release.

    \notecue{Watch for}{Compensation is not a guaranteed undo. It is new forward work that can itself fail and require settlement.}

    \notecue{Next}{Slide 10 tests when cleanup must be registered using a real workflow example.}
  }
\end{frame}

\begin{frame}{Recovery chooses by evidence, then admission, then cost}
  \centering
  \mlsyssteps[width=0.97\textwidth,height=5.75cm,keepaspectratio]{decide_step}{3}
  \mlsyscredit{Redrawn from Failure Recovery, figure 2 and table 2 (\S12.4.1 to \S12.4.3).}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    Why must evidence govern recovery before cost? Recall from Lecture 2 that intrinsic self-review without new evidence lowered accuracy while external checks raised it. Comparing code repair against fresh resampling under matched budgets, Olausson et al. (2024) likewise found modest, variable gains unless strong external feedback was supplied, so repair success rate $p$ must be measured per failure class and feedback source. Recovery therefore runs in three stages. First, evidence class separates an unknown outcome, which requires settlement or a verified repeat contract (Lecture 7's safe repeat behavior or endpoint deduplication), from established outcomes that allow repair or compensation. Next, Lecture 10's admission rules apply without exemption (authority, budget with finalization reserve, deadline), holding or escalating if nothing qualifies. Finally, surviving options are ranked by future expected cost alone, ignoring sunk cost.

    \notecue{Watch for}{Cost must come last. An inexpensive repair that uses an expired grant or breaches the worst-case dollar cap must never run.}

    \notecue{Next}{Slide 15 tests this decision order across three failures that all tempt a simple retry.}
  }
\end{frame}

\begin{frame}{Reversibility depends on the subsystem and the grant}
  \centering
  \safeimg[width=0.96\textwidth,height=4.9cm,keepaspectratio]{contracts.pdf}\\[0.2cm]
  {\small A \textbf{pivot} is the one step in a plan region after which the region cannot be restored.}
  \mlsyscredit{Failure Recovery, \S12.5.1 table 3 and Definition 12.3; Mehrotra et al., ICDCS 1992.}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Because reversibility belongs to the external effect under a specific grant, the runtime checks three properties before acting, namely the target state, the recovery permitted by the grant, and the confirming evidence. Three recovery contracts result. A local snapshot restores tracked files without touching remote effects or charges. \begin{frame}{Takeaways}
  \thumbline{thumb_settle.pdf}{An outcome is established, absent, or unknown; cleanup is registered before the effect exists and ordered as a graph.}\\[0.14cm]
  \thumbline{thumb_repair.pdf}{Choose by evidence, then admission, then cost; one repair pays when $p > C_{\text{repair}}/C_{\text{fallback}}$.}\\[0.14cm]
  \thumbline{thumb_pivot.pdf}{Checks before the pivot cut expected loss 3.6$\times$; what passes the pivot stays owned.}\\[0.14cm]
  \thumbline{thumb_loop.pdf}{A loop's input grows with the square of its turns, so detection latency sets its cost.}\\[0.14cm]
  \thumbline{thumb_contain.pdf}{One retry owner, scoped breakers, and caps contain shared failures; holds stop model work while cleanup runs.}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Together, these five takeaways answer today's driving question, showing why a durable log never reverses remote state and what closes the gap. First, classify outcomes as established, absent, or unknown and register acyclic cleanup before dispatch. Second, choose recovery by evidence, admission, then cost with repair threshold $p > C_{\text{repair}}/C_{\text{fallback}}$. Third, hoist checks before the pivot (cutting expected loss 3.6 times) and keep post-pivot duties owned. Fourth, bound quadratic loop cost through detection latency. Fifth, combine dependency containment with holds that halt model work while cleanup runs.
