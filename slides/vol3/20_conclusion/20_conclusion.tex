\begin{frame}{Write the intent first; then a lost reply has an owner}

  \mlsyssteps[width=0.95\textwidth,height=3.8cm,keepaspectratio]{lostreply_step}{3}\\[0.15cm]

    \end{quoteblock}}
  \end{minipage}
  \mlsyscredit{Conclusion, \S20.3.1 and \S20.6. Stripe, ``Idempotent requests,'' docs.stripe.com/api/idempotent\_requests.}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    Even after approval and dispatch checks pass, a dropped reply leaves op\_42 uncertain unless intent is written before dispatch. First, the runtime writes a durable intent record (Lecture 11) with a recovery descriptor (corrective action and preconditions) naming operations\_owner\_42 under Lecture 12's trajectory saga pattern, then dispatches expecting config\_v7. Next, the endpoint applies config\_v8, and the reply drops. A timeout leaves three possibilities open, namely a lost request, an active request, or a committed write, so status stays unknown. The runtime then queries the read-only operation registry for op\_42 and receives applied, config\_v8, following Lecture 7's settlement-before-retry rule. Stripe's payment API reference states this same idempotency contract, assuring callers that repeating a request after a connection error will not apply an update twice. If lookup finds no record, status stays unknown with operations\_owner\_42 because the request may still be in flight.

    \notecue{Watch for}{Unknown is an owned state. Clearing it as a routine error drops accountability for a live mutation.}

In his 1987 essay ``No Silver Bullet,'' Fred Brooks separated accidental difficulty, such as formatting a valid configuration payload, from essential difficulty, such as deciding which service behavior counts as recovery and what risk is acceptable. Applying Lecture 18's Amdahl bound to one human and one model shows the consequence. If half the effort stays human specification and review, total speedup caps at $1/0.5 = 2\times$ regardless of model speed. That yields the specification boundary, invariant closure applied to contracts. An agent may draft requirements or tests, yet only the owner adopts contracts and sets acceptance criteria. Segment 4 thus bounds every claim to its evidence and keeps ownership human.

    \notecue{Watch for}{Tests generated alongside an implementation can share the exact same mistaken assumption and never serve as independent verification.}
