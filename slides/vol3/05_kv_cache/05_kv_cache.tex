\begin{frame}{Every context token becomes keys and values at all 80 layers}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=6.1cm,keepaspectratio]{zones_step}{2}
  \mlsyscredit{KV Cache Management, \S5.2 and its context figure (zone sizes); 10.7 GB computed in images/calcs.py.}
  \note{[2 min] [CORE] LINK: Lecture 4's zones, now as the serving engine sees them. The first three, 14,336 tokens or 43.8 percent, form the shared invariant prefix. Step 2: none of that structure survives into memory. Every token, whatever zone it came from, leaves a key vector and a value vector in every layer, so that later tokens can attend to it without recomputing them. ENGAGE: does a request reach its peak footprint at prefill or at the end of generation? (Expected: at the end; every output token appends its own keys and values.) \begin{frame}{Reservation strands slots inside; contiguity strands gaps outside}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.6cm,keepaspectratio]{frag_step}{2}
  \mlsyscredit{KV Cache Management, \S5.3.2 and table 2 (illustrative extents); Randell, CACM 1969.}
  \note{[1.5 min] [OPTIONAL] Step 1: internal fragmentation. A full-cap reservation locks 32,768 slots at admission; a request that ends at 2,048 leaves 30,720 slots that no other request can use. Step 2: external fragmentation. Three free extents of 256 slots sit between live allocations: 768 free slots in all, yet a new request for 512 contiguous slots fails. The contiguity requirement causes the failure; the pool has enough free memory. Standard attention kernels find a token's keys by a fixed stride from one base pointer, so each sequence needs one unbroken span; the restriction is in software. Each loss has its own remedy: allocate on demand to stop reservation slack; make every allocation the same size so any free unit fits any request. Randell named the two losses in 1969. ENGAGE: which of the two would knowing every final length remove? (Expected: reservation slack; the external gaps remain.) FLEX: [OPTIONAL]; the measured bars on the previous slide carry the point.}
\end{frame}

\begin{frame}{A block table maps token positions to blocks anywhere in HBM}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=6.0cm,keepaspectratio]{blocktable_step}{3}
  \mlsyscredit{KV Cache Management, \S5.4.1 and its block-table figure (4-token blocks for illustration; 16 is a common default). After Kwon et al., SOSP 2023.}
  \note{[2.5 min] [CORE] Step 1: a ten-token prefix in logical blocks of 4 tokens: block 0 holds positions 0 to 3, block 1 positions 4 to 7, block 2 positions 8 and 9 with two empty slots. Step 2: the sequence's block table says where each logical block lives: 3, 7, 9. Those physical blocks sit anywhere in one shared pool, between other requests' blocks. A growing sequence takes any free block and appends its number; nothing is copied or reserved ahead. Step 3: how the kernel reads position 9: logical block 9 // 4 = 2, table entry 2 says physical block 9, slot 9 mod 4 = 1. ENGAGE: what does a request waste at most? \end{frame}

  \note{[2.5 min] [CORE] LINK: Lecture 3 sampled several candidate repairs from one prompt (the breadth axis). \begin{frame}{A radix tree finds the longest retained prefix and evicts leaves}

  \note{[2.5 min] [CORE] Each node holds a run of tokens and the KV blocks for them; a request's cached state is the path from the root to its node.           evict_callback: Callable):
    leaves = self._collect_leaves()
\hl{    heapq.heapify(leaves)}
    num_evicted = 0

\begin{frame}{Pool telemetry counts every block once, in exactly one state}
  \centering\small
  \begin{tabular}{@{}P{3.6cm}P{8.2cm}@{}}\toprule

    Active or pinned & blocks a request or transfer still uses, once even if shared \\
    Reserved or in flight & blocks being filled, copied, or promised to growth \\
    Reclaimable dormant & cached blocks no one needs now; evicting loses future reuse \\
    Free & blocks ready to allocate \\\bottomrule
  \end{tabular}\\[0.35cm]
  {\small Cache churn (evict, then reload or recompute soon after) with rising tail latency means the working set exceeds memory.}
  \mlsyscredit{KV Cache Management, \S5.8.3 and table 6; Denning, AFIPS 1968 (thrashing).}
  \note{[1 min] [OPTIONAL] Two runs can both show 90 percent occupancy: one full of dormant prefixes it can drop at once, one full of pinned active state with no room to grow. A single occupancy number cannot tell them apart; these four states can, if every physical block is in exactly one and shared blocks count once. While a paused trajectory copies out, its source blocks stay pinned until the copy lands. The failure to watch for is churn, evicting blocks and soon reloading or recomputing them, together with rising tail latency under steady load. That is thrashing, which time-sharing systems met in the 1960s; Denning's remedy was admission control, admitting fewer programs until their working sets fit, rather than paging faster. ENGAGE: which metrics would distinguish useful eviction from churn? (Expected: recomputed tokens and reloads per eviction, with p99 latency.) FLEX: [OPTIONAL].
