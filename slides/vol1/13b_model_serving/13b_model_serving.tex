\begin{frame}{Prefill spends arithmetic; decode spends a weight read}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.2cm,keepaspectratio]{phases_step}{4}\\[0.05cm]
  \uncover<2->{\footnotesize Measured (Splitwise, BLOOM-176B): a 1,500-token prompt takes as long as 6 output tokens.}
  \mlsyscredit{Model Serving, \S13.9.2 and \S13.10.3 (modeled). Patel et al., ``Splitwise,'' ISCA 2024, \S III-C.}
  \note{[3.5 min] [CORE] Step 1: prefill. GPT-2 XL's 512-token prompt is about 1.5 TFLOP (trillion floating-point operations); at 40 percent of the H100's 16-bit peak it takes 3.9 ms. Llama 3 8B's 1,000-token prompt takes 41.9 ms. Prefill time grows with prompt length: it sets TTFT. Step 2: decode. Each step reads every weight to make one token. GPT-2 XL's 3 GB at 3.35 TB/s cannot take less than 0.9 ms. Llama 3 8B with 4-bit (INT4) weights reads 4 GB: a floor of 1.2 ms, 1.57 ms with the remaining kernel-launch cost. The measured line says the same: 1,500 prompt tokens cost as much time as 6 output tokens. Step 3: issued kernel by kernel from Python, one GPT-2 XL step spends 8.6 ms launching 576 kernels; servers capture the step as one CUDA graph, a recorded kernel sequence the GPU replays with one launch. Step 4: the case study allows 20 ms per token. One step uses 1.57 ms; 18.4 ms is room to share this weight read with other conversations. LINK: Lecture 6b placed decode at 1 FLOP per byte against the H100's ridge near 295; Lecture 7 owns graph capture; Lecture 10b owns INT4 weights.}
\end{frame}

\begin{frame}{Paging stores a growing cache in fixed blocks anywhere}
  \begin{columns}[c]
    \begin{column}{0.72\textwidth}
      \centering\mlsyssteps[width=\textwidth,height=5.6cm,keepaspectratio]{paging_step}{4}
    \end{column}
    \begin{column}{0.26\textwidth}
      \uncover<5->{\begin{mlsyscard}{GreenLine}\small\textbf{Measured, vLLM}\\[0.05cm]OPT-13B, one A100:\\ average batch 13.6 $\rightarrow$ \textbf{30.4}, 2.2$\times$\end{mlsyscard}}
    \end{column}
  \end{columns}
  \mlsyscredit{After Kwon et al., ``PagedAttention'' (vLLM), SOSP 2023, \S4.3 and Fig.~6 (block size 4 here; 16 by default). Bars: Fig.~13a, OPT-13B, ShareGPT.}
  \note{[3 min] [CORE] PagedAttention borrows the operating system's paging (first built on the Atlas computer, 1962). The cache lives in fixed-size blocks, and a block table maps each request's logical blocks to physical blocks anywhere in memory. Step 1: a 7-token prompt fills logical block 0 and three slots of block 1; the table maps them to physical blocks 7 and 1. One slot is free. Step 2: decode makes ``fathers''; it fills the free slot, and the table's count goes to 4. Step 3: the next token needs a new block; any free block will do, here 3. Step 4: request B's blocks interleave in the same pool. No region is reserved ahead, no hole is too small, and each sequence wastes at most its last, partly filled block. The attention kernel reads the blocks through the table directly. Step 5: measured: the average batch on the same GPU grew from 13.6 requests (Orca with Oracle) to 30.4, 2.2 times. ENGAGE: what happens to a request's blocks when it ends? (Expected: they return to the free pool for the next step.) WARN: paging decides where blocks live, not how many a sequence needs. FLEX: [CORE].}
\end{frame}

\begin{frame}{A GPU running both phases serves fewer requests than either alone}
  \centering

  \note{[2.5 min] [CORE] Goodput is the rate of requests that meet both deadlines, here at 90 percent attainment. DistServe measured a 13-billion-parameter model on one A100. Running both phases on one GPU, it sustains 1.6 requests per second. The same GPU doing only prefill sustains 5.6; doing only decode, 10. The phases interfere: a prefill stalls decode (the last segment), and decode steps delay the next prefill, so the colocated GPU must run lightly loaded to keep both deadlines. They also want different settings: prefill is efficient at small batches and benefits from splitting a layer across GPUs, while decode wants large batches. ENGAGE: if both phases fit on one GPU, why is the colocated number below both? (Expected: each phase's deadline is hurt by the other's work, so the GPU is kept far from full.) \begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.3cm}
    \item Reasoning models choose to spend more tokens per question. Each costs decode time, cache memory, and joules. Where should a service cap that spending, and who sets the cap?

  \end{itemize}
