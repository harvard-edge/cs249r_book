\begin{frame}{Learning Objectives}
\note{

\small
By the end of this lecture you should be able to:
\begin{enumerate}\setlength{\itemsep}{0pt}
  \item \textbf{Explain} why one training run costs orders of magnitude more than one inference.
  \item \textbf{Calculate} run time, energy, and memory with the \textbf{training-time law} and the \textbf{four-term memory budget}.
  \item \textbf{Compare} SGD, momentum, and Adam by the memory each optimizer adds.

\section{Run Cost}

\begin{frame}{One training run repeats one step millions of times}
\note{
[3 min]
% -- LINK
Students traced one training step for a small MNIST classifier when they
studied neural computation. Today the same step meets a 1.5B-parameter model.
% -- NARRATE
Walk the table row by row. The step is the same algorithm; only the scale
changes, and the run multiplies every byte and millisecond of the step.
% -- ENGAGE
Ask: ``The GPT-2 XL step is 15 million times more arithmetic. Is that the
biggest problem?'' [Expected: no; 24 GB of state before any activation is
the first wall, as the memory section shows.]
% -- WARN
Students read the GPT-4 figure as a disclosed bill. It is an industry
estimate; the point is the three-order-of-magnitude gap, not the digits.
% -- FLEX
[CORE]
}

\small
Each step reads a batch, runs forward, computes a loss, runs backward, and updates every parameter. A run repeats that until the model reaches its quality target.

\vspace{0.15cm}
\centering
\begin{tabular}{@{}lrr@{}}
  \toprule
  & \textbf{MNIST classifier} & \textbf{GPT-2 XL} \\
  \midrule
  Parameters & 101,770 & 1.5 billion \\
  Work per step (batch 32) & 19.5 MFLOP & 295 TFLOP \\
  Weights + gradients + optimizer state & 1.6 MB & 24 GB \\
  \bottomrule
\end{tabular}

\vspace{0.15cm}
\raggedright\footnotesize
Training a GPT-2-scale model cost about \$50,000 of compute in 2019; a GPT-4-class run is estimated at \$100M.

\bottomline{The questions of this lecture are how long a run takes, whether its step fits in memory, and whether the accelerator is fed.}
\end{frame}

\begin{frame}{Two running cases and one reference machine}
\note{
[2 min]
% -- NARRATE
GPT-2 XL carries the time and memory story; ResNet-50 carries the input
pipeline. Both leave their ``home'' regime when they train: GPT-2 is
bandwidth-bound when it generates tokens one at a time, but a training batch
reuses each weight thousands of times. ResNet-50 is compute-bound by nature,
but an H100 eats images faster than the host can decode them.
% -- WARN
Students assume a model has one fixed bottleneck. The regime belongs to the
workload on a machine, not to the model.
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{mlsyscard}{bookorange}
\textbf{GPT-2 XL} (1.5B parameters, 48 layers, width 1,600)\\[2pt]
Leaves its bandwidth-bound inference regime: a batch of long sequences presses on \textbf{arithmetic} and, through state and activations, on \textbf{memory capacity}.
\end{mlsyscard}
\end{column}
\begin{column}{0.48\textwidth}
\begin{mlsyscard}{bookgreen}
\textbf{ResNet-50} (25.6M parameters, 24.6 GFLOP per training image)\\[2pt]
Leaves its compute-bound regime: every image must be read, decoded, and augmented on the host, so the \textbf{input pipeline} binds.
\end{mlsyscard}
\end{column}
\end{columns}

\vspace{0.3cm}
\small
\textbf{Reference machine:} one NVIDIA H100: 80 GB HBM at 3.35 TB/s, 989 TFLOP/s dense 16-bit peak, 700 W. Successors change the constants, not the reasoning.

\bottomline{The same model can be bound by different resources in training and in inference.}
\end{frame}

\begin{frame}{Each token costs about $6P$ FLOPs: $2P$ forward, $4P$ backward}
\note{
[3 min]
% -- LINK
Backprop through a linear layer was derived in neural computation. Here we
only count its matrix products.
% -- NARRATE
Forward: each parameter does one multiply-accumulate per token, 2 FLOPs.
Backward: two products per layer, one sends the error upstream, one builds
the weight gradient. Each costs as much as the forward product.
% -- ENGAGE
Have students compute $6 \times 1.5\times10^9 \times$ tokens for $1.5\times10^{21}$
FLOPs. [Answer: about 167 billion token evaluations.]
% -- WARN
Students think backward is ``the same work in reverse'', so 2$\times$ the
forward step total. It is two products, so 3$\times$ in total.
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.56\textwidth}
\small
For a linear layer $Z = AW$, backpropagation evaluates two matrix products:
\begin{itemize}\setlength{\itemsep}{2pt}
  \item activation gradient $\nabla_A L = (\nabla_Z L)\,W^{T}$ carries the error upstream;
  \item weight gradient $\nabla_W L = A^{T}(\nabla_Z L)$ feeds the optimizer.
\end{itemize}
Each costs about as much as the forward product, so a full step costs about three forward passes.
\end{column}
\begin{column}{0.40\textwidth}
\begin{mlsyscard}{bookorange}
\centering
$\underbrace{2P}_{\text{forward}} + \underbrace{4P}_{\text{backward}} = 6P$ FLOPs per token\\[6pt]
$O \approx 6 \cdot P \cdot D$\\[6pt]
\footnotesize GPT-2 XL on WebText:\\ $O \approx 1.5 \times 10^{21}$ FLOPs
\end{mlsyscard}
\end{column}
\end{columns}

\bottomline{Training work is predictable before any code runs: about six FLOPs per parameter per token.}
\end{frame}

\mlsysfocus{The Training-Time Law}{%
$\Ttrain = \dfrac{O}{\Rpeak \times \etahw}$\\[0.4cm]
\normalsize work $O$ \;$\cdot$\; peak rate $\Rpeak$ \;$\cdot$\; utilization $\etahw$ (end to end, from 0 to 1)%
}

\begin{frame}{Three levers move run time; memory is a gate, not a term}
\note{
[3 min]
% -- LINK
This is the iron law from the introduction, specialized to training and
written in its \DAM{} product form.
% -- NARRATE
Map each factor to \DAM{}: data and algorithm set $O$, the machine sets
$\Rpeak$ (including the number format), and the pipeline sets $\etahw$.
Then point at the empty space: memory does not appear. A step that does not
fit runs at no speed at all.
% -- WARN
Common error: ``utilization is a property of the GPU.'' It is a property of
the whole pipeline; you only learn it by profiling.
% -- FLEX
[CORE]
}

\small
\begin{tabular}{@{}L{0.17\textwidth}L{0.36\textwidth}L{0.38\textwidth}@{}}
  \toprule
  \textbf{Factor} & \textbf{Set by} & \textbf{Moved by} \\
  \midrule
  \textcolor{bookgreen}{\textbf{Work $O$}} & tokens $D$ and FLOPs per token & data selection, smaller or compressed models \\
  \textcolor{bookorange}{\textbf{Peak $\Rpeak$}} & hardware and number format & newer accelerators, BF16/FP8 tensor paths \\
  \textcolor{bookblue}{\textbf{Utilization $\etahw$}} & everything that is not useful math & overlap, fusion, IO-aware kernels \\
  \bottomrule
\end{tabular}

\vspace{0.2cm}
$\etahw$ absorbs data stalls, communication, synchronization, launch overhead, and inefficient kernels. Large runs sustain roughly 30--50\%.

\bottomline{Memory is missing from the law because it is a feasibility gate: a step whose state does not fit runs at no speed at all.}
\end{frame}

\begin{frame}{GPT-2 XL on one H100: about 35 days and 590 kWh}
\note{
[3 min]
% -- NARRATE
Do the arithmetic live: $1.5\times10^{21} / (989\times10^{12}\times0.5)
\approx 3.0\times10^6$ s, about 35 days. Energy is power times time.
Then scale up: the same law prices a 70B model on 1,024 H100s.
% -- ENGAGE
Ask: ``If utilization rises from 50\% to 60\% at the same power, what
happens to the energy bill?'' [Falls in the same proportion, about 17\%.]
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.52\textwidth}
\small
\textbf{Worked estimate} (BF16 peak, $\etahw = 0.5$)
\[
\Ttrain = \frac{1.5\times10^{21}}{989\times10^{12} \times 0.5} \approx 3.0\times10^{6}\ \text{s} \approx 35\ \text{days}
\]
That is about 5.1 million steps of 0.60 s, each over 32 sequences of 1,024 tokens.

\vspace{0.1cm}
Energy at 700 W: $E = P \times T \approx$ \textbf{590 kWh} at the accelerator, about 417 J per step.
\end{column}
\begin{column}{0.44\textwidth}
\begin{mlsyscard}{bookviolet}
\footnotesize\textbf{Same law, frontier scale}\\[3pt]
Llama 2 70B on 2T tokens, 1,024 H100s, same utilization: about \textbf{19.2 days} and \textbf{\$1.89M} of rented time.\\[3pt]
Buying that cluster costs as much as about 16 such runs, before networking, facilities, power, and staff.
\end{mlsyscard}
\end{column}
\end{columns}

\bottomline{At constant power, every point of utilization recovered removes time, energy, and dollars in the same proportion.}
\end{frame}

\begin{frame}{Predict: double the peak rate, or double the utilization?}
\note{
[3 min] Predict, then reveal.
% -- NARRATE
Give 60 seconds for a written answer. Then reveal. The law is symmetric in
the two factors, so both halve the run. The engineering is not symmetric.
% -- WARN
Students will pick ``peak'' because hardware is marketed on TFLOP/s, or
``utilization'' because it sounds free. Neither is the answer; the answer is
that they cost different things.
% -- FLEX
[CORE]
}

\centering
\vspace{0.4cm}
{\Large\bfseries A frontier run needs about $10^{23}$ FLOPs at $\etahw$ well below 1.}\\[0.4cm]
{\normalsize Which shortens wall-clock time more: doubling $\Rpeak$ or doubling $\etahw$?}\\[0.2cm]
{\small\textcolor{midgray}{Write your answer and one reason. 60 seconds.}}

\pause
\vspace{0.5cm}
\raggedright
\begin{mlsyscard}{crimson}
\small Both halve $\Ttrain$; the law treats them symmetrically. They differ in \textbf{cost and reachability}: doubling $\Rpeak$ means new hardware or a lower-precision format with numerical risk; doubling $\etahw$ means engineering the pipeline, and it is capped at 1.
\end{mlsyscard}
\end{frame}

\section{Memory}

\begin{frame}{Training holds four kinds of state; only activations grow with batch}
\note{
[3 min]
% -- LINK
The four kinds of state were met on a small network in neural computation.
Here we price them at scale.
% -- NARRATE
Weights, gradients, and optimizer state are fixed by the model. Activations
are the forward values each backward rule must read, so they are kept alive
until the backward pass reaches them. They scale with batch and sequence.
% -- WARN
Students budget training memory as ``the model size.'' The first OOM usually
happens during the forward pass, before any gradient exists.
% -- FLEX
[CORE]
}

\centering
{\Large $M = M_{\text{weights}} + M_{\text{grads}} + M_{\text{optimizer}} + M_{\text{activations}}$}

\vspace{0.35cm}
\raggedright\small
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\textcolor{bookorange}{\textbf{Static: fixed by the model}}
\begin{itemize}\setlength{\itemsep}{1pt}
  \item weights, and any higher-precision master copy
  \item gradients, one per parameter
  \item optimizer state (SGD: none; momentum: 1 tensor; Adam: 2 tensors)
\end{itemize}
\end{column}
\begin{column}{0.48\textwidth}
\textcolor{bookblue}{\textbf{Dynamic: grows with the batch}}
\begin{itemize}\setlength{\itemsep}{1pt}
  \item saved forward activations that backward rules read
  \item $M_{\text{act}} \propto B$ (and with sequence length)
  \item doubling the batch doubles this term only
\end{itemize}
\end{column}
\end{columns}

\bottomline{A model that fits at a small batch can run out of memory at a larger one, with the weights unchanged.}
\end{frame}

\begin{frame}{Mixed-precision Adam holds 16 bytes per parameter}
\note{
[3 min]
% -- NARRATE
Build the bar left to right: 2 bytes FP16 weights, 2 FP16 gradients, 4 for
the FP32 master copy, 8 for Adam's two FP32 moments. Sixteen bytes, eight
times what an inference server stores.
% -- ENGAGE
Ask: ``Plain FP32 Adam is 4 + 4 + 8. How many bytes?'' [16 again.]
% -- WARN
Students expect mixed precision to halve the static state. It does not: the
master copy and moments stay FP32. Three multipliers appear in the chapter
(3$\times$, 16 B, 8$\times$); they differ only in what is counted.
% -- FLEX
[CORE]
}

\centering
\safeimg[width=0.98\textwidth,height=3.7cm,keepaspectratio]{static-state-16-bytes.pdf}

\vspace{0.1cm}
\raggedright\footnotesize
\textbf{Three multipliers, one budget.} Adam's state is 3$\times$ the FP32 weights (12 B vs 4 B). Add FP32 gradients and FP32 Adam reaches 16 B per parameter. Mixed precision also lands at 16 B, which is \textbf{8$\times$} the 2 B of FP16 inference weights.

\bottomline{Optimizer state, not weights, decides most of the static footprint, and switching to 16-bit math does not shrink it.}
\end{frame}

\begin{frame}{Your turn: does a 7B model train on a 40 GB accelerator?}
\note{
[3 min] Exercise.
% -- NARRATE
Give 90 seconds. Most students will multiply by 2 (FP16) and say it fits.
Reveal the per-term budget.
% -- ENGAGE
Follow-up: ``What fraction of the 112 GB is the Adam moments?'' [Half.]
% -- FLEX
[CORE]
}

\centering
{\large A 7B-parameter model uses \textbf{14 GB} of FP16 weights for inference\\ and fits comfortably on a 40 GB accelerator.}\\[0.3cm]
{\normalsize With mixed-precision Adam, how much memory does training need\\ \textbf{before a single activation is stored}?}\\[0.2cm]
{\small\textcolor{midgray}{90 seconds, then compare with a neighbor.}}

\pause
\vspace{0.1cm}
\small
\begin{tabular}{@{}lr@{}}
  FP16 weights + FP16 gradients & 14 + 14 GB \\
  FP32 master weights & 28 GB \\
  FP32 Adam moments ($m$, $v$) & 56 GB \\
  \midrule
  \textbf{Static state} $= 7\text{B} \times 16$ B & \textbf{112 GB}, almost 3$\times$ the device \\
\end{tabular}
\end{frame}

\begin{frame}{At batch 32, GPT-2 XL's step needs 311 GB, 3.6$\times$ an H100}
\note{
[3 min]
% -- NARRATE
The static state is only 24 GB, under a third of the device. The problem is
the 287 GB of saved activations at batch 32 and 1,024 tokens. Even FP16
activations are 12$\times$ the static state.
% -- ENGAGE
Ask: ``Which single term would you attack first?'' [Activations, and the
next slide shows which part of them.]
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.50\textwidth}
\small
GPT-2 XL, batch 32, sequence 1,024, mixed precision:

\footnotesize\renewcommand{\arraystretch}{0.92}
\begin{tabular}{@{}lr@{}}
  \toprule
  FP16 parameters & 3 GB \\
  FP16 gradients & 3 GB \\
  FP32 master weights & 6 GB \\
  FP32 Adam moments & 12 GB \\
  \midrule
  \textcolor{bookorange}{\textbf{Static state}} & \textbf{24 GB} \\
  \textcolor{bookblue}{\textbf{Saved activations}} & \textbf{286.9 GB} \\
  \midrule
  \textbf{Total} & \textbf{310.9 GB} \\
  \bottomrule
\end{tabular}
\end{column}
\begin{column}{0.46\textwidth}
\begin{mlsyscard}{bookred}
\small The H100 holds 80 GB. The step needs \textbf{3.6$\times$} that before temporary workspace is counted.\\[4pt]
In FP32, activations would be 574 GB and the step 598 GB, about 7$\times$ the device.
\end{mlsyscard}
\end{column}
\end{columns}

\bottomline{For a dense transformer at training batch sizes, activations, not parameters, break the memory budget.}
\end{frame}

\begin{frame}{Attention scores are 83\% of each layer's saved activations}
\note{
[2 min]
% -- NARRATE
Per layer: Q, K, V and output 419 MB, FFN expansion 419 MB, and 4,194 MB for
the attention matrices, because each $S{\times}S$ head matrix is saved three
times (probabilities, dropout mask, post-dropout). That term grows with the
square of the sequence length.
% -- ENGAGE
Ask: ``Double the sequence length. Which bar grows 4$\times$?'' [The red one.]
% -- FLEX
[CORE] This slide sets up FlashAttention later.
}

\centering
\safeimg[width=0.98\textwidth,height=3.5cm,keepaspectratio]{activation-per-layer.pdf}

\vspace{0.15cm}
\raggedright\small
Each of the 25 heads stores an $S{\times}S$ matrix three times for the backward pass: FP16 probabilities (2 B), a dropout mask (1 B), and post-dropout probabilities (2 B). Across 48 layers the line items reach about 242 GB; the library estimate, which also counts layer inputs and masks, is 286.9 GB.

\bottomline{The largest activation term is quadratic in sequence length, so it is the first one to remove.}
\end{frame}

\begin{frame}{Training scope decides which memory terms exist}
\note{
[3 min]
% -- LINK
Fine-tuning is the most common training job students will run.
% -- NARRATE
Full fine-tuning of Llama 3 8B: 128 GB static plus 36.5 GB of activations.
LoRA adds 6.8M trainable parameters (0.08\%) whose gradients, master copy,
and moments take 0.11 GB. The frozen base weights stay resident and the
activations stay too, because gradients must flow back through every frozen
layer to reach the earliest adapter.
% -- WARN
Students think adapters remove activations. They remove optimizer state.
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.55\textwidth}
\safeimg[width=\textwidth,height=5.2cm,keepaspectratio]{llama8b-finetune-scope.pdf}
\end{column}
\begin{column}{0.42\textwidth}
\small
Llama 3 8B, batch 4 $\times$ 2,048 tokens, attention without the quadratic score matrix.

\vspace{0.15cm}
\textbf{Full fine-tune:} gradients and optimizer state for all 8B parameters. Does not fit.

\vspace{0.1cm}
\textbf{LoRA (rank 16):} 6.8M trainable parameters; their update state is 0.11 GB. Fits, with about 33 GB to spare.

\vspace{0.1cm}
\textbf{Unchanged:} frozen base weights and the activations on the backward path.
\end{column}
\end{columns}

\bottomline{Adapters shrink gradients and optimizer state, not the frozen weights or the activations.}
\end{frame}

\section{Feeding}

\begin{frame}{A step is a pipeline; the slowest stage sets the pace}
\note{
[3 min]
% -- NARRATE
Trace the three zones: storage and CPU workers prepare batches, the PCIe
link transfers them, the accelerator computes. Put every rate in batches per
second and take the minimum. With overlap, the step costs the maximum of the
stage times instead of their sum.
% -- WARN
Students treat overlap as a speedup of the slow stage. It only hides the
fast stages behind the slow one.
% -- FLEX
[CORE]
}

\centering
\safeimg[width=0.90\textwidth,height=2.9cm,keepaspectratio]{pipeline-stages.pdf}

\vspace{0.1cm}
{\large $\text{Throughput} = \min\left(R_{\text{prep}},\; \dfrac{BW_{\text{host}}}{\text{bytes/batch}},\; \dfrac{R_{\text{sustained}}}{\text{FLOPs/batch}}\right)$}

\vspace{0.15cm}
\raggedright\footnotesize
Host preparation (storage reads + CPU transforms), host-to-device transfer, and accelerator compute, all in batches per second. With overlap the step time is $\max(t_{\text{fetch}}, t_{\text{process}}, t_{\text{transfer}})$, not the sum.

\bottomline{An accelerator waiting for data does zero useful work, however fast its arithmetic is.}
\end{frame}

\begin{frame}{A faster accelerator turned ResNet-50 input-bound}
\note{
[3 min]
% -- NARRATE
One training image is 24.6 GFLOP, so the H100's peak could eat 40,200 images
per second; at the 25\% sustained fraction the feeding-problem example used,
about 10,100. One host core decodes and augments 375 images/s. That needs 28
cores per accelerator; an 8-GPU H100 server has 112 cores, 14 per GPU.
% -- ENGAGE
Ask: ``Name two fixes that do not touch the accelerator.'' [More host cores,
decode on the accelerator, cache decoded data.]
% -- WARN
Students assume upgrading the GPU always helps. Here it raised the appetite
3$\times$ and changed nothing else.
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.56\textwidth}
\safeimg[width=\textwidth,height=4.4cm,keepaspectratio]{resnet50-feeding.pdf}
\end{column}
\begin{column}{0.41\textwidth}
\small
\textbf{Demand:} 24.6 GFLOP per image at a sustained fraction of peak gives about 10,100 images/s per H100.

\vspace{0.1cm}
\textbf{Supply:} 375 images/s per host core $\times$ 14 cores per accelerator = 5,250 images/s.

\vspace{0.1cm}
\textbf{Result:} busy $\min(1, 5250/10100) \approx$ \textbf{52\%}.

\end{column}
\end{columns}

\bottomline{Upgrading arithmetic moves the bottleneck upstream until the input pipeline is rebalanced.}
\end{frame}

\begin{frame}{Overlap hides preparation; it cannot speed up the slowest stage}
\note{
[3 min]
% -- NARRATE
Top: serial schedule, the GPU row idles during every open and read; 95 min.
Bottom: the next batch is opened and read while the current one trains;
65 min, 31.6\% shorter. Then the knobs: num\_workers sets preparation
parallelism, prefetch\_factor sets queue depth, pin\_memory lets DMA copies
overlap compute at the cost of page-locked host RAM.
% -- ENGAGE
Ask: ``One worker takes 40 ms per batch; the accelerator takes 10 ms. How
many workers at minimum?'' [Four, in the ideal case.]
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.58\textwidth}
\centering
\safeimg[width=\textwidth,height=3.7cm,keepaspectratio]{prefetch-overlap.pdf}\\[2pt]
{\scriptsize Schematic durations. The chapter's illustrative schedule drops from 95 to 65 min (31.6\%).}

\begin{frame}{FP16 needs loss scaling; BF16 usually does not}
\note{
[3 min]
% -- NARRATE
FP16's 5-bit exponent puts its smallest normal number at $6.1\times10^{-5}$;
small gradients underflow to zero. Multiply the loss by $s$, backprop, then
divide the gradients by $s$ (differentiation is linear). A dynamic scaler
skips overflowing steps, halves $s$, and doubles it after a quiet window.
BF16 keeps FP32's 8-bit exponent, so its range matches FP32.
Master weights stay FP32 because an update more than about $2^{11}$ times
smaller than the weight rounds away in FP16.
% -- WARN
Students confuse the two failures: underflow (gradient becomes zero) and
swamping (update is lost when added to a large weight).
% -- FLEX
[CORE]
}

\begin{column}{0.49\textwidth}

  Mantissa bits & 23 & 10 & 7 \\
  Min normal & $10^{-38}$ & $6.1{\times}10^{-5}$ & $10^{-38}$ \\
  Loss scaling & -- & needed & usually not \\
  \bottomrule
\end{tabular}

\begin{frame}{FlashAttention: same result, no $S{\times}S$ matrix in HBM}
\note{
[4 min]
% -- NARRATE

the sum: exact softmax. Backward recomputes tiles instead of reading stored
matrices.

% -- FLEX
[CORE]

becomes 11.5 GB; the whole step 35.5 GB.
% -- ENGAGE

[CORE]

\begin{frame}{Accumulation builds a big batch from micro-batches that fit}
\note{
[3 min]
% -- NARRATE

activations are those of one micro-batch; total FLOPs are unchanged.
% -- WARN
The classic bug: summing micro-batch losses instead of dividing each by $k$
gives a gradient $k$ times too large, which acts like a $k\times$ learning
rate. BatchNorm, dropout, and step-indexed schedules can also break exact
equivalence.
% -- FLEX
[CORE]
}

\begin{columns}[T]
\begin{column}{0.50\textwidth}
\safeimg[width=\textwidth,height=3.0cm,keepaspectratio]{gradient-accumulation.pdf}

\footnotesize
Effective batch $B = k \times b$:
\[
\nabla L_B = \frac{1}{k}\sum_{j=1}^{k}\Big(\frac{1}{b}\sum_{i\in j} \nabla L_i\Big)

\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{Memory:} activations of one micro-batch, $k\times$ smaller
  \item \textbf{FLOPs:} unchanged
  \item \textbf{Time:} $k$ passes per update; small micro-batches can lower utilization
\end{itemize}
\end{column}
\end{columns}

\bottomline{Accumulation reproduces the large-batch gradient only when every micro-batch loss is normalized the same way.}
\end{frame}

\textbf{Three hard limits}
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{Memory:} state exceeds one device. A 70B model needs 140 GB for FP16 weights alone.
  \item \textbf{Wall-clock:} $10^{24}$ FLOPs at $10^{15}$ FLOP/s sustained takes about 32 years.

\begin{frame}{Gradient sync cost depends on parameters, not batch size}
\note{
[4 min]
% -- NARRATE
Ring AllReduce: reduce-scatter then all-gather, each accelerator sends
$2(N-1)/N$ of the gradient bytes. For 8 H100s, 1.75 $\times$ 3 GB = 5.25 GB,
about 12 ms at 450 GB/s per direction over NVLink. Against a 596 ms step that
is 2\%. Split the same batch of 32 eight ways and each replica computes for
75 ms while the 12 ms stays: 14\%.
% -- ENGAGE
Ask: ``What happens to the sync share if we instead use batch 256 total?''
[Back toward 2\%: compute per replica grows, gradient bytes do not.]
% -- WARN
Students expect communication to grow with batch size.
% -- FLEX
[CORE]
}

for GPT-2 XL. ZeRO-1 shards master weights and moments (8.2 GB); ZeRO-2 also
shards gradients (5.6 GB); ZeRO-3, which FSDP implements, also shards the
parameters (3 GB). Stages 1 and 2 move the same bytes as AllReduce; stage 3
gathers each layer's parameters before use, about 1.5$\times$ the volume.
The Llama 3 8B full fine-tune that overflowed one device drops to about
16 GB of static state per accelerator.
% -- FLEX
[CORE]
}

\begin{frame}{Splitting the model pays a pipeline bubble unless micro-batches flow}
\note{
[3 min]
% -- NARRATE
Layerwise partition: device 1 holds blocks 1-6, device 2 blocks 7-12, and so
on. Naively only one device works at a time: utilization $1/N$. Pipeline
parallelism streams micro-batches so the bubble shrinks to fill and drain.
Tensor parallelism splits each layer's matrices; it communicates inside
every layer, so it stays on the fastest links within one node.
% -- WARN
Do not confuse this pipeline bubble with the accelerator bubbles of the
input pipeline: this one occurs even when every device is perfectly fed.
% -- FLEX
[OPTIONAL]
}

\centering
\safeimg[width=0.95\textwidth,height=3.4cm,keepaspectratio]{pipeline-bubble.pdf}

\raggedright\footnotesize
\textbf{Naive layerwise split:} each device waits for the previous one, so utilization is capped at $1/N$.
\textbf{Pipeline parallelism} streams $M$ micro-batches through the stages; the idle fill-and-drain slots are $(N-1)/(M+N-1)$ of the total.
\textbf{Tensor parallelism} instead splits each layer's matrices, paying a collective inside every layer, so it stays on the fastest links within one node.

\bottomline{Data parallelism adds throughput; sharding and model parallelism add memory; each adds communication.}
\end{frame}

\section{Wrap-Up}

\begin{frame}{Fallacies}
\note{
[3 min]
% -- NARRATE
Read each claim, ask for a show of hands on ``true'', then give the number.
% -- FLEX
[CORE]
}

\small
\textbf{Fallacy:} \textit{Larger models always yield better performance.}\\
A 20B model needs about 320 GB of non-activation state in mixed-precision Adam (40 + 40 + 80 + 160 GB). Whether it beats a 7B model depends on data, compute, and optimization, not parameter count alone.

\vspace{0.2cm}
\textbf{Fallacy:} \textit{Hyperparameters transfer directly from small runs to large ones.}\\
Going from batch 512 to 4,096, the linear scaling rule moves the learning rate from 0.1 to 0.8, usually with warmup. It is a recipe to validate, not a guarantee.

\vspace{0.2cm}
\textbf{Fallacy:} \textit{The accelerator is always the training bottleneck.}\\
ResNet-50 on an H100 is busy about 52\% of the time, and GPT-2 XL with one tokenizer core about 48\%. A faster accelerator fixes neither.
\end{frame}

\begin{frame}{Pitfalls}
\note{
[3 min]
% -- NARRATE
Each pitfall is a step skipped in the workflow: measure, then decide.
% -- FLEX
[CORE]
}

\small
\textbf{Pitfall:} \textit{Assuming distributed training automatically accelerates development.}\\
Splitting GPT-2 XL's batch of 32 over eight H100s raises unhidden synchronization to about 14\% of the step; with heavier synchronization, 8 GPUs deliver 4--6$\times$, not 8$\times$.

\vspace{0.2cm}
\textbf{Pitfall:} \textit{Treating mixed precision as a toggle without validation.}\\
Peak ratios bound the gain at 2$\times$ over TF32 and 15$\times$ over FP32; non-tensor work keeps the measured gain lower, and FP16 needs loss scaling.

\vspace{0.2cm}
\textbf{Pitfall:} \textit{Budgeting training memory as if it only contains weights.}\\
Static state alone is 16 B per parameter before activations, workspaces, and allocator overhead.

\vspace{0.2cm}
\textbf{Pitfall:} \textit{Optimizing kernels before profiling the input pipeline.}\\
A starved accelerator looks like an inefficient one; measure dataloader throughput first.
\end{frame}

\begin{frame}{Key takeaways}
\note{
[2 min]
% -- NARRATE
One bullet per section of the lecture. Return to the learning objectives.
% -- FLEX
[CORE]
}

\footnotesize
\begin{itemize}\setlength{\itemsep}{2pt}
  \item \textbf{Run cost:} $\Ttrain = O/(\Rpeak \times \etahw)$ with $O \approx 6PD$. Every optimization reduces work, raises the peak, or raises utilization.
  \item \textbf{Memory:} mixed-precision Adam holds 16 B/param, 8$\times$ the FP16 inference weights, before activations; activations grow with batch and, for attention, with the square of sequence length.
  \item \textbf{Feeding:} throughput is the minimum of preparation, transfer, and compute rates; overlap hides fast stages, it does not speed up the slow one.
  \item \textbf{Diagnosis:} busy time is an upper bound on MFU. Profile, fix the binding stage, re-profile.
  \item \textbf{Optimizations:} mixed precision raises $\Rpeak$; FlashAttention removes quadratic traffic; checkpointing and accumulation trade arithmetic or update frequency for memory.
  \item \textbf{Scaling:} exhaust single-node levers first. Data parallelism adds throughput, sharding adds memory, and both add communication.
\end{itemize}
\end{frame}
