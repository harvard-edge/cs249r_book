\section{Time}

\begin{frame}{A training token costs $6P$ FLOPs; an inference token, $2P$}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=4.9cm,keepaspectratio]{flops_per_token_step}{2}\\[0.35cm]
  \uncover<2->{\normalsize Backward: one product for the activation gradient, one for the weight gradient.}
  \mlsyscredit{Model Training, Lighthouse 8.1.}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Timing a training run starts by counting its arithmetic per token for a model with $P$ parameters. In inference, only the forward pass runs, and each weight enters one multiply and add (2 FLOPs) per token for $2P$ FLOPs in total. Training adds the backward pass, which performs two matrix products per weight as derived in Lecture 5. One product propagates error to the previous layer (the activation gradient, $2P$), and the other computes the parameter update signal (the weight gradient, $2P$). Together they add $4P$, giving $6P$ FLOPs per training token. Over $D$ tokens, total work is $O \approx 6PD$, or $1.5 \times 10^{21}$ FLOPs for GPT-2 XL.

    \notecue{Watch for}{The $6P$ rule omits attention-score products that scale with sequence length squared, which add roughly 9 percent to GPT-2 XL's step arithmetic at 1,024 tokens.}

    \notecue{Next}{Combine $6PD$ with hardware peak rate and utilization into the training-time law.}
  }
\end{frame}

\mlsysnote{%
  \mlsysnotemeta{2 min}{Core}%
  Converting $6PD$ FLOPs into wall-clock seconds adapts Lecture 1's iron law to a full training run as $T_{\text{train}} = 6PD / (R_{\text{peak}} \cdot \eta_{\text{hw}})$. The numerator $6PD$ is total algorithmic work over the data. The denominator is the achieved hardware rate, equal to the peak rate at the chosen number format times utilization $\eta_{\text{hw}}$, which drops under stalls, data waits, synchronization, and slow accelerator kernels. Three levers shorten training, namely less work, higher peak rate, or higher utilization. One critical constraint is missing. Memory never appears in this equation because a step that overflows memory runs at zero speed, making capacity a precondition checked first.

  \notecue{Next}{Apply the training-time law to one GPT-2 XL step before scaling up to the full run.}
}
\mlsysfocus{The Training-Time Law}{%
  $\displaystyle T_{\text{train}} = \frac{\overbrace{6PD}^{\text{work, } O}}{\underbrace{R_{\text{peak}}}_{\text{peak rate}} \times \underbrace{\eta_{\text{hw}}}_{\text{utilization}}}$\\[0.6cm]
  {\small\textcolor{white!75}{Memory is not in the law. It decides whether the step runs at all.}}%
}

  \note{%
    \mlsysnotemeta{2 min}{Core}%
    To ground the law, price one step of GPT-2 XL from its published \texttt{config.json}, which sets 48 layers, hidden width 1,600, 25 attention heads, a 1,024-token context, and 0.1 attention dropout (randomly zeroing attention probabilities, returning in Segment 3). Batching 32 sequences of 1,024 tokens yields 32,768 tokens per step. At $6P$ FLOPs per token, one step does $6 \times 1.5 \times 10^9 \times 32{,}768 \approx 295\text{ TFLOP}$. Dividing by the H100's 989 TFLOP/s dense 16-bit peak at 50 percent utilization gives 0.60 s per step, so $1.5 \times 10^{21}$ FLOPs takes roughly 5.1 million steps (implying $D \approx 1.7 \times 10^{11}$ tokens).

    \notecue{Check}{How long does one step take if utilization drops from 50 percent to 25 percent? Step time doubles to 1.2 s because time scales inversely with utilization. A tempting error halves the time with the percentage, forgetting that less work completes each second.}

    \notecue{Watch for}{Adding quadratic attention-score products raises this step roughly 9 percent, from 295 to 320.8 TFLOP in the chapter's per-layer count.}

    \notecue{Next}{Scale this step across the full run to compute days, kilowatt-hours, and rental dollars.}

\begin{frame}{SGD keeps no extra state; momentum keeps one copy; Adam two}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.6cm,keepaspectratio]{optimizer_bytes_step}{3}
  \mlsyscredit{Model Training, \S8.3.2 and table 3 (FP32 throughout).}
  \note{%
    \mlsysnotemeta{1.5 min}{Optional}%
    Start with the fixed per-parameter state, whose size depends on the optimizer. In pure FP32 (Table 3), every optimizer holds 4 bytes of weights and 4 bytes of gradients, or 8 bytes per parameter (B/param). Plain SGD stores nothing extra. Momentum adds one FP32 velocity buffer $v$, a running directional average of past gradients, reaching 12 B/param (the gold momentum band in Lecture 5's ResNet-50 memory trace). Adam stores both a first moment $m$ (smoothed gradients) and a second moment $v$ (squared-gradient average), totaling 16 B/param, double weights plus gradients. Memory-efficient optimizers such as Adafactor and 8-bit Adam compress these optimizer blocks.

    \notecue{Check}{Why pay 4 extra bytes per parameter for Adam over momentum? Adam often reaches target loss in fewer steps, though net wall-clock savings must be verified empirically. \begin{frame}{Mixed-precision Adam still holds 16 B/param: 24 GB for GPT-2 XL}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.1cm,keepaspectratio]{static_compare_step}{3}\\[0.12cm]
  \uncover<3->{%
    \colorbox{lightgray!25}{\parbox{0.92\textwidth}{\centering\footnotesize\textbf{ZeRO \S3.1 (SC 2020):}\enspace ``$2\Psi + 2\Psi + K\Psi = 16\Psi$ bytes'' $\rightarrow$ \textbf{24 GB} for 1.5B GPT-2}}\\[0.1cm]

  \note{%
    \mlsysnotemeta{3.5 min}{Core}%
    Moving to 16-bit mixed precision leaves Adam's static footprint unchanged. For GPT-2 XL (1.5 billion weights), FP16 inference holds 2 bytes per parameter (B/param), or 3 GB. FP32 Adam uses 4 B weights (6 GB), 4 B gradients (6 GB), and 8 B moments (12 GB), or 16 B/param (24 GB).     \notecue{Check}{Why use mixed precision if static state stays 16 B/param? It unlocks 16-bit matrix-multiply Tensor Cores (Lecture 8b) and halves activations; a tempting guess expects halved static state.}

With overlapped prefetching, while the GPU trains batch 1 (20 to 35), the host reads batch 2 (20 to 30) and opens file 2 (30 to 37.5), then reads batch 3 (37.5 to 50) while batch 2 trains (35 to 50). The GPU runs continuously from 20 to 65 minutes, finishing 40 minutes sooner, or 1.6 times faster. Overlap hides I/O latency only when host throughput matches or beats GPU demand; otherwise gaps shrink without vanishing.

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Run time is $6PD$ over peak times utilization; utilization moves time and energy together.
    \item Mixed-precision Adam holds 16 bytes per parameter before any activation.
    \item A step holds weights, gradients, optimizer state, and activations; only activations grow with batch and sequence.
    \item Busy time bounds MFU; profile before fixing, and fit before profiling.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1 min}{Core}%
    Together, these four takeaways answer the driving question of why training costs so much and what decides what fits. Run time equals $6PD / (R_{\text{peak}} \cdot \eta_{\text{hw}})$, moving time and energy together. Mixed-precision Adam holds 16 B/param statically, while only saved activations scale with batch and sequence length. Engineers fit the step first so it runs, and then profile before fixing because busy time only bounds MFU. Star the single line you would have missed before today.
