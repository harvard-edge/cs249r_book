    \notecue{Check}{The axes are Data, Algorithm, and Machine. A tempting mistake is assigning total FLOPs to M, when M measures only how fast hardware finishes each operation. Extending Lecture 0's GPT-3 energy example, this chapter's Napkin Math 1.2 applies this law to GPT-3's $3.14 \times 10^{23}$ FLOPs on a hypothetical cluster of 1,024 NVIDIA A100 datacenter GPUs at 312 trillion FLOPs per second (TFLOP/s) each and an assumed 45\% utilization, estimating roughly 25.3 days, revisited in Segment 5.}

  \note{%
    \mlsysnotemeta{1.5 min}{Optional}%
    Tesla's missed stop signs illustrate why offline tests never catch every real-world case. A $224 \times 224$ color image with red, green, and blue (RGB) channels holds 150,528 bytes, and with 256 values per byte there are $256^{150{,}528}$ possible inputs, a number with 362,508 digits. By contrast, the validation set (the held-out photos used to measure accuracy on unseen inputs) of ImageNet, the landmark visual-recognition benchmark, contains 50,000 images. That disparity is the verification gap. Offline testing supplies statistical evidence only over the distribution it sampled, so evidence must continue after launch.

    \notecue{Watch for}{Conventional software also cannot be exhaustively tested. Unit tests verify explicit control-flow branches, whereas machine learning evaluations make statistical claims about an input population that shifts over time.}

  \mlsyscredit{Photo: TheStriker, CC BY-SA 4.0, commons.wikimedia.org/wiki/File:EVGAGeforceGTX580.jpg.}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    Built in 2012 by Alex Krizhevsky, Ilya Sutskever, and Geoffrey Hinton for the ImageNet challenge, AlexNet achieved 15.3 percent top-5 error (the true label missing its top five guesses) versus 26.2 percent for second place, helping launch the deep learning era. This multi-layer neural network paired convolutions (sliding learned filters across an image, Lecture 6), known since 1989, with 1.3 million labeled images on two 3 GB GTX 580 GPUs. Its layers split into two GPU streams exchanging data only at select layers to minimize slow PCIe traffic. Why split 60 million parameters (learned weights) of 4 bytes each? Estimate their size first.

\begin{frame}{The machine factor splits into memory, compute, and overhead}
  \vspace{-0.15cm}
  \centering
  {\large $T = \underbrace{\dfrac{\text{Samples}}{\text{Task}} \times \dfrac{\text{FLOPs}}{\text{Sample}}}_{\uncover<2->{\term{OrangeLine}{total operations $O$}}} \times \dfrac{\text{Seconds}}{\text{FLOP}}$}\\[0.22cm]
  \uncover<3->{{\large $T = \underbrace{\dfrac{\Dvol}{\BW}}_{\substack{\term{BlueLine}{memory}\\ \gloss{bytes moved / bytes per second}}} + \underbrace{\dfrac{O}{\Rpeak \cdot \etahw}}_{\substack{\term{OrangeLine}{compute}\\ \gloss{operations / (peak rate $\times$ utilization)}}} + \underbrace{\Llat}_{\substack{\term{midgray}{overhead}\\ \gloss{kernel launch, sync, network}}}$}\\[0.14cm]
  \begin{tikzpicture}[font=\footnotesize,
      st/.style={rounded corners=2pt, minimum height=0.46cm, inner xsep=8pt, text=darktext, line width=0.9pt},
      ar/.style={-{Latex[length=1.8mm]}, midgray, line width=0.8pt}]
    \node[st, draw=BlueLine, fill=BlueL] (m) at (0,0) {\textbf{1. Load bytes} ($\Dvol/\BW$)};
    \node[st, draw=OrangeLine, fill=OrangeL, right=0.55cm of m] (c) {\textbf{2. Execute FLOPs} ($O/(\Rpeak\etahw)$)};
    \node[st, draw=midgray, fill=vlightgray!35, right=0.55cm of c] (o) {\textbf{3. Fixed overhead} ($\Llat$)};
    \draw[ar] (m) -- (c); \draw[ar] (c) -- (o);
  \end{tikzpicture}\\[0.10cm]}
  \uncover<4->{\small $\Dvol$ counts bytes moved; one decoded token moves every weight.}
  \mlsyscredit{Introduction, \S1.7, equations 2 and 3.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Once diagnosis points to the Machine axis, the iron law unpacks where execution time physically goes. Grouping Samples per Task times FLOPs per Sample gives total operations $O$, about $3.14 \times 10^{23}$ FLOPs for GPT-3. Assuming the three physical costs occur sequentially, execution time splits into three terms. Memory movement is bytes moved over bandwidth ($\Dvol / \BW$), compute execution is $O / (\Rpeak \cdot \etahw)$ for peak rate $\Rpeak$ and achieved utilization $\etahw$, and fixed overhead $\Llat$ covers kernel launches (starting accelerator operations), synchronization (coordinating parallel work), and networking. Unlike logical sample count, $\Dvol$ counts physical bytes moved; for example, generating one output token at a time (a decode step, developed in Lecture 6b) reads every model weight.

    \notecue{Watch for}{Do not conflate the Data axis (sample count, D) with physical data volume ($\Dvol$). Shrinking weights from 16-bit to 8-bit halves $\Dvol$, while sample count stays fixed.}

    \notecue{Next}{Verify the $\Dvol / \BW$ memory term directly inside a real PyTorch profiler trace of GPT-2 decoding.}
  }
\end{frame}

  {\small\textcolor{white!75}{With ideal overlap:\quad $\displaystyle T \ge \max\!\left(\frac{\Dvol}{\BW},\ \frac{O}{\Rpeak \cdot \etahw}\right) + \Llat$}}%

  \mlsyscredit{Introduction, \S1.7 (The iron law analogy) and \S1.8; H100 FP16 decode vs.\ 50\% MFU training (MLSysIM, derived: 147.6$\times$).}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Each factor of the iron law maps to one efficiency lever. Data selection shrinks Samples per Task with fewer, higher-value examples (Lecture 9). Algorithmic efficiency shrinks FLOPs per Sample through better architectures, pruning unneeded weights, and quantization to fewer bits (Lectures 6 and 10). Compute efficiency shrinks Seconds per FLOP via batching, operator fusion (combining adjacent operations), and overlap (Lectures 7, 8, and 11); raising GPT-3 utilization from 45\% to 60\% cuts training from 25 to 19 days. These factors remain coupled. On an H100 (989 TFLOP/s dense FP16, 3.35 TB/s), batch-1 FP16 decode runs at 3.35 TFLOP/s (1 FLOP/byte) versus 494.5 TFLOP/s for 50\% model FLOPs utilization (MFU, the share of peak compute doing model math) training, taking $147.6\times$ (roughly $150\times$) the Seconds per FLOP.

    \notecue{Watch for}{Pulling one lever naively can backfire. Removing scattered individual weights (unstructured pruning, Lecture 10) cuts FLOPs per sample yet can slow execution if irregular memory reads inflate Seconds per FLOP.}
