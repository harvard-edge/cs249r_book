\begin{frame}{Moving a byte costs far more energy than computing with it}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.9cm,keepaspectratio]{energy_per_op_step}{3}\\[0.1cm]
  \uncover<3->{\normalsize Reading a byte from DRAM costs over 100 times an FP16 multiply.}
  \mlsyscredit{Introduction, \S1.7, after Horowitz 2014 (45 nm process, DDR3 DRAM; per byte read and per operation).}
  \note{[3 min] Step 1: reading one byte from off-chip DRAM, about 160 pJ. Step 2: one FP16 multiply, about 1.1 pJ. Step 3: one INT8 multiply, about 0.2 pJ. The book's ratio is about 145 to 1 per byte against one multiply. WARN: these are Horowitz's 45 nm figures; modern HBM costs less per byte, and an FP16 multiply reads more than one byte of operands, so say "over a hundred times" rather than defending the exact ratio. Whether movement dominates a whole workload depends on how often each byte is reused. LINK: Lecture 11.}
\end{frame}

\begin{frame}{Generating text is limited by memory, not arithmetic}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.0cm,keepaspectratio]{roofline_train_decode_step}{2}
  \mlsyscredit{Schematic roofline. Model Serving, \S13.9; Hardware Acceleration, \S11.6.}
  \note{[3 min] This plot is the roofline; Lecture 11 builds it properly. Right of the bend, performance is limited by arithmetic; left of it, by how fast memory delivers bytes. Step 1: generating text for one user. Each new token reads every weight of the model once and does about two operations per weight, so with 16-bit weights it performs about one operation per byte moved. It sits low on the memory slope; most of the arithmetic units wait. Step 2: training with a large batch reuses each weight across many examples, so it sits on the compute ceiling. Same chip, opposite bottlenecks. This is why serving systems batch users together (Lecture 13) and why accelerator designers care about memory bandwidth.}
\end{frame}

\begin{frame}{A poorly used accelerator spends six times the energy per token}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=3.8cm,keepaspectratio]{energy_utilization_step}{2}\\[0.3cm]
  \uncover<2->{\normalsize At 10\% of the token rate, the GPU still draws about 300 W and the host 300 W.}
  \mlsyscredit{Model Serving, Napkin Math 13.5.}
  \note{[2 min] Step 1: the chat service from the opening, well batched: about 1,000 W for about 912 tokens per second, about 1.1 J per token. Step 2: the same hardware running at 10 percent of that token rate, because requests are not batched. The GPU still draws about 300 W and the host about 300 W, so about 600 W for about 91 tokens per second, about 6.6 J per token. Idle hardware still burns power. The same idea as the 45 percent utilization on the GPT-3 slide: work divided by what the hardware could do.}
\end{frame}

  \end{columns}
  \note{[2.5 min] D·A·M. Step 1: three axes joined by edges, because relieving one bottleneck often exposes another. Steps 2 and 3: data and algorithm. Step 4: machine, and the three together. Every lecture says which axis it works on.}
\end{frame}

\mlsysnote{[2.5 min] The iron law in three factors, one per D·A·M axis. Samples are the units of work: images, tokens, or examples. FLOPs per sample is set by the model. Effective seconds per FLOP is set by the machine and by how well it is used, so it already includes memory stalls and idle time; that is why the decode example earlier still fits. For students who know computer architecture: it has the same form as the CPU iron law, instructions times cycles per instruction times seconds per cycle. Lecture 1 develops it properly.}
\mlsysfocus{The Iron Law of ML Systems}{%
  {\normalsize$\text{Time} = \underbrace{\text{samples}}_{\text{data}} \times
   \underbrace{\text{FLOPs per sample}}_{\text{algorithm}} \times
   \underbrace{\text{effective seconds per FLOP}}_{\text{machine}}$}\\[0.5cm]
  {\small\textcolor{white!75}{Same form as the CPU iron law:\\instructions $\times$ cycles per instruction $\times$ seconds per cycle.}}%
}
