\begin{frame}{Skewed inputs make the right operands meet}
  \mlsysactivity{Predict}{1 min}
  \centering
  \mlsyssteps[width=\textwidth,height=5.15cm,keepaspectratio]{trace2_step}{5}\\[0.05cm]
  \small
  \only<1|handout:0>{$C = AB$ on a 2$\times$2 array: PE$_{rc}$ holds weight $b_{rc}$.}%
  \only<2|handout:0>{In cycle 1, $a_{00}b_{00}$ reaches PE$_{10}$ (holding $b_{10}$); which activation must meet it?}%
  \only<3|handout:0>{$a_{01}$: it enters row 1 one cycle after $a_{00}$ entered row 0.}%
  \only<4|handout:0>{$C_{01}$ leaves one cycle after $C_{00}$; the second input row follows one cycle behind.}%
  \only<5-|handout:1>{Each row starts one cycle later, so operands with the same reduction index meet.}
  \mlsyscredit{Hardware Acceleration, \S11.7.5 (the 2$\times$2 trace) and figure 5 (interactive Explore figure: Systolic Array Dataflow); Kung 1982. $C_{10}$ and $C_{11}$ follow the same stagger.}
  \note{%
    \mlsysnotemeta{3.5 min}{Core}%
    Why must inputs enter staggered? H. T. Kung and Charles Leiserson introduced systolic arrays, formalized by Kung in 1982, to pass operands between neighboring processing elements (PEs). In this 2 by 2 trace of $C = AB$ ($C_{00} = a_{00}b_{00} + a_{01}b_{10}$) at one hop per cycle, each PE holds one weight, activations move right, and partial sums move down. At cycle 0, $a_{00}b_{00}$ forms in $\text{PE}_{00}$ and shifts to $\text{PE}_{10}$ ($b_{10}$) at cycle 1. Predict which activation must meet it.

    \notecue{Check}{The answer is $a_{01}$, entering row 1 one cycle late so operands sharing the reduction index (the dot product's summation index) form $a_{01}b_{10}$ for $C_{00}$. Starting all rows together mismatches indices. As $C_{00}$ exits, $a_{00}$ moves right and $a_{10}$ enters $\text{PE}_{00}$; $C_{01}$ and $C_{10}$ exit in cycle 2 and $C_{11}$ in cycle 3, taking four cycles for two rows.}

    \notecue{Teach}{Pause at cycle 1 and ask which activation must reach $\text{PE}_{10}$ before showing $a_{01}$.}

    \notecue{Next}{Next, scale this skew to a 4 by 4 array to see fill, steady state, and drain.}
  }
\end{frame}

\begin{frame}{A 4$\times$4 array fills, runs full, then drains}
  \centering
  \mlsyssteps[width=\textwidth,height=5.7cm,keepaspectratio]{wave4_step}{3}
  \mlsyscredit{Derived from Hardware Acceleration, \S11.7.5 (one hop per cycle). Weight loading not shown.}
  \note{%
    \mlsysnotemeta{2 min}{Optional}%
    Because skewed rows enter one cycle apart, a larger array spends cycles filling and draining. Here a 4 by 4 array streams 8 input rows past one held weight tile, with cell numbers showing the active input row. At cycle 2, the array is still filling, with only 6 of 16 cells active. By cycle 6, all 16 cells run full, yet steady state (every cell busy) lasts only cycles 6 and 7. By cycle 11, the array drains back to 6 active cells. For $B$ rows on an $N$ by $N$ array, eight rows take $B + 2N - 2 = 8 + 8 - 2 = 14$ cycles, averaging 57 percent utilization. Sending more input rows per weight load raises that share.

  \note{%
    \mlsysnotemeta{3 min}{Core}%
    Holding weights in place is only one way to schedule a matrix multiply. Reordering the three nested loops of the chapter's dense layer $Z = WX$ ($W$ is $512\times 256$ and $X$ is $256\times 32$, totaling 4,194,304 MACs, Listing 15) selects which operand does not change in the innermost loop and therefore stays pinned in the cell while the other two stream past. Weight stationary pins each weight for 32 batch uses, which is the TPU's dataflow and works best when one weight matrix serves a large batch. Output stationary pins each running sum (accumulator) and writes each output once while streaming weights and inputs. Input stationary pins each input for 512 output-row uses.

    \notecue{Watch for}{A single cell holding one value cannot capture all three reuses at once, and the next slide tallies what each order still moves.}

\section{The Tile}

\begin{frame}{Four weight tiles cut the layer's traffic 47 times}
  \begin{columns}[T]

\begin{frame}{Coalesced loads fill one sector; strided loads waste 75\%}
  \centering
  \mlsyssteps[width=0.96\textwidth,height=4.65cm,keepaspectratio]{coalesce_step}{3}\\[0.08cm]
  {\footnotesize\textcolor{midgray}{Boehm Kernel 2 jumped 6.4$\times$ (309 $\rightarrow$ 1,987 GFLOP/s): coalesced warp loads fill single sectors.}}
  \mlsyscredit{Hardware Acceleration, \S11.5.3 (interactive Explore figure: Irregular Address Transactions). Boehm 2022 (A6000, FP32).}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Staging tiles works well only if threads fetch them cleanly from off-chip HBM, which returns aligned fixed-size chunks called sectors (16 bytes here, 32 bytes on an H100). When four neighboring threads in a warp (a lockstep group of GPU threads) read adjacent 4-byte words $[0, 4, 8, 12]$, the memory controller (the hardware managing HBM transfers) coalesces (merges) them into one 16-byte sector at 100 percent efficiency. By contrast, strided column reads at $[0, 16, 32, 48]$ pull four 16-byte sectors (64 bytes) for only 16 useful bytes, wasting 75 percent of bandwidth. Assigning consecutive threads to consecutive columns of $B$ produced Boehm Kernel 2's 6.4 times jump (309 to 1,987 GFLOP/s) before touching shared memory. Finally, dependent pointer chases in sparse kernels or embedding tables, where one load must return before the next address is known, serialize about 378 nanoseconds (ns) of HBM latency and block overlap.

Each of the five intermediate tensors stays live from its producer layer to its last consumer layer, so naive allocation reserves five separate buffers. Peak memory, however, depends on simultaneously live tensors rather than the total tensor count. Mapping non-overlapping intervals onto shared buffers reduces five buffers to two, while overlapping pairs such as T1 and T2 cannot share. Across dozens of layers, buffer reuse keeps activation memory inside HBM.

    \notecue{Teach}{For a 50-minute class, skip this liveness diagram and go straight to diagnosing idle Tensor Cores.}

    \notecue{Next}{Next, diagnose why a transformer ported to A100 GPUs leaves its Tensor Cores idle.}
  }
\end{frame}

    The opening hook now resolves rung by rung on Boehm's 75x ladder (FP32, A6000). First, coalesced HBM loads jump 6.4x by eliminating sector waste. Next, shared-memory tiles (1.5x), 1D and 2D per-thread register tiles (2.8x and 1.9x), and vector loads (fetching adjacent values together in one instruction) pull operands progressively closer to arithmetic. Autotuning (automated schedule search) and warp-level tiling (an extra tiling tier per warp) then close the gap to cuBLAS at 23,250 GFLOP/s (75x) with zero FLOPs removed, purely through data locality. The same mapping rules answer the driving question for our opening H100 stage-3 convolution recall. Its FP16 rate (563 FLOP/byte) reaches 989 TFLOP/s only when tiles fit shared memory and shapes fill tiles and waves. At INT8, activations must stay INT8 too, reaching 1,126 FLOP/byte against the 591 ridge instead of 569.

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.35cm}
    \item Hand-written kernels still lead on new hardware for months. Should the next accelerator be designed so a compiler can map it well, even at some cost in peak rate?
    \item Model designers already choose widths of 512 over 500. Who should fit shapes to tiles and waves: the model team or the compiler?
    \item A fixed dataflow is efficient yet inflexible, whereas a GPU relies on software to find reuse; which wins as models change faster than chips?
  \end{itemize}
  \note{%
    \mlsysnotemeta{1 min}{Core}%
    These three open engineering questions sit at the boundary of hardware and compiler design. Consider whether future chips should trade peak hardware rate for compiler-friendly regularity (connecting to Ansor and Definition 11.4), how shape-alignment responsibility should split between model teams and compilers, and whether fixed TPU-style dataflows or flexible GPU software mapping will age better as models evolve.
