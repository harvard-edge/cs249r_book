Step 3: ENGAGE: fingers up for fits or does not fit, FP16 then INT8. Step 4: INT8 fits one SM's 228 KB (201); FP16 does not (401). Format and tile size decide which tier can hold it. The registers feed the Tensor Cores at about 0.1 pJ per access, and the dataflow decides how long a value stays there. WARN: a kernel stages tiles, not whole maps; whole-map fit is the chapter's simple test. FLEX: [CORE].}
\end{frame}

\begin{frame}{True or false: four claims about mapping}
  \mlsysactivity{Vote}{2 min}
  \begin{columns}[T]
    \begin{column}{0.48\textwidth}
      \tfcard{A production compiler finds the best mapping for every layer.}{Ansor still found up to 3.8$\times$ over the prior best.}
      \tfcard{A larger tile is always faster.}{Every live buffer must fit, and big tiles fill fewer SMs.}
    \end{column}
    \begin{column}{0.48\textwidth}
      \tfcard{The right stationary operand fixes batch-one decode.}{Each weight is used once per token.}
      \tfcard{Vendor-tuned kernels cost nothing later.}{Vendor intrinsics and layouts take months to port.}
    \end{column}
  \end{columns}
  \mlsyscredit{Hardware Acceleration, Definition 11.4, equation 6, Systems Perspective 11.1, \S11.12; Zheng et al. 2020; NVIDIA guide \S2.3.}
  \note{[2.5 min] Peer instruction: vote on all four, one minute with a neighbor, vote again. Step 2: all false. One: for systolic arrays and custom chips, compiler mappings can still lag hand-tuned schedules (Definition 11.4), and Ansor's gains show how much earlier compilers missed. Two: equation 6 caps the tile, and NVIDIA's guide notes that larger tiles leave fewer tiles to run in parallel. Three: at batch one there is no weight reuse to recover (Systems Perspective 11.1). Four: the chapter's fallacy: code full of vendor intrinsics, assembly, and nonstandard layouts takes months to port when a cheaper accelerator arrives (\S11.12). FLEX: [OPTIONAL]; for a 60-minute version keep statements two and three.}
\end{frame}

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.35cm}
    \item Hand-written kernels still lead on new hardware for months. Should the next accelerator be designed so a compiler can map it well, even at some cost in peak rate?
    \item Model designers already choose widths of 512 rather than 500. Who should fit shapes to tiles and waves: the model team or the compiler?
    \item A fixed dataflow is efficient and inflexible; a GPU depends on software to find reuse. Which wins as models change faster than chips?
  \end{itemize}
