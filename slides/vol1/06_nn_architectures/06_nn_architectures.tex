\begin{frame}{At batch one, a dense layer does 0.5 FLOP per byte it reads}
  \begin{columns}[T]
    \begin{column}{0.40\textwidth}
      \begin{mlsyscard}{mlsysaccent}
        \textbf{Given}\\[0.1cm]
        $d_{\text{in}} \times d_{\text{out}}$ weights in FP32\\
        (4 bytes each)\\
        One example (batch one)\\
        Each weight: one multiply-add,\\
        2 FLOPs
      \end{mlsyscard}
    \end{column}
    \begin{column}{0.56\textwidth}
      \normalsize
      \uncover<2->{FLOPs $= 2\,d_{\text{in}}\,d_{\text{out}}$\\[0.3cm]}
      \uncover<3->{Bytes read $= 4\,d_{\text{in}}\,d_{\text{out}}$\\[0.3cm]}
      \uncover<4->{$I = \dfrac{2\,d_{\text{in}}\,d_{\text{out}}}{4\,d_{\text{in}}\,d_{\text{out}}} = $ {\Large\textbf{\textcolor{mlsysaccent}{0.5 FLOP/byte}}}\\[0.35cm]}
      \uncover<5->{Accelerators need tens to hundreds of FLOPs per byte to stay busy.}
    \end{column}
  \end{columns}
  \mlsyscredit{Network Architectures, equation 2 (weight-only model; ignores inputs, outputs, and caches).}
  \note{[2.5 min] Worked example 1. Step 1: the given. Step 2: each weight takes part in one multiply-add, two FLOPs. Step 3: each weight is read once, four bytes in FP32. Step 4: the ratio, arithmetic intensity, is half a FLOP per byte, whatever the widths, because both counts grow with the same product. Step 5: an accelerator's arithmetic can consume tens to hundreds of FLOPs for every byte its memory delivers, so this layer leaves most of the arithmetic idle, waiting for weights. ENGAGE: "What single change raises this ratio?" Expected: a larger batch, because each weight read then serves B examples, so intensity grows to about 0.5 times B until activation traffic takes over (Lecture 5). WARN: this is a weight-only model; a small layer such as 784 by 128 can stay in on-chip cache, and then it is dispatch overhead, not memory bandwidth, that dominates. FLEX: [CORE].}
\end{frame}

\mlsysnote{[1 min] The one ratio to remember today. Arithmetic intensity is the work done per byte moved. Compare it with the machine's balance, its peak FLOP/s divided by its memory bandwidth: above the balance the arithmetic limits (the compute term of the iron law), below it the memory limits (the data term). Each family today lands at a different intensity, and two families escape this axis entirely, which is the surprise of the lecture. LINK: Lecture 11 draws the full roofline.}
\mlsysfocus{Arithmetic intensity decides which term binds}{%
  $\displaystyle I = \frac{\text{operations}}{\text{bytes moved}}\quad\text{(FLOP/byte)}$\\[0.7cm]
  {\normalsize\textcolor{white!80}{Above the machine's balance: compute bound.\quad Below it: memory bound.}}%
}

  \mlsyssteps[width=0.95\textwidth,height=4.4cm,keepaspectratio]{energy_weight_step}{2}\\[0.3cm]

  \centering
  {\normalsize Input 224$\times$224$\times$64, 64 features out.\quad
   Dense: $224^2 \times 64 \times 64$.\quad
   \uncover<2->{Conv: $3 \times 3 \times 64 \times 64$.}}\\[0.25cm]

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Each architecture bets on the data's structure; a matching bet saves weights and data.
    \item Dense layers at batch one do 0.5 FLOP per byte; convolution reuses each weight at every position.
    \item Recurrence holds state fixed and pays in serial steps.
    \item Attention pays $S^2$: double the context, four times the score work.
    \item Recommenders are capacity bound: where the tables live comes first.
  \end{itemize}
  \note{[1.5 min] One line per segment. Ask students to circle the one they could not have explained an hour ago. FLEX: [CORE].}
\end{frame}
