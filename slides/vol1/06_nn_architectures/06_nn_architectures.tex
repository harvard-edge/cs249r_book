    }
  \end{tikzpicture}
  \mlsyscredit{Ordering: Network Architectures, \S6.1 and \S6.9.4.}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Every architecture sits somewhere along a spectrum of inductive bias, meaning the structural assumptions wired into it before training begins. When a strong prior matches the data, it saves both training data and compute. CNNs assume spatial locality in images, and RNNs assume sequential order. Transformers relax those priors so any token can interact with any other token (priced in Part 2, Lecture 6b), while MLPs assume no fixed neighbor structure for tabular data, and recommenders sit off this axis using lookup tables. Under Lecture 1's Bitter Lesson, weak priors tend to win once data and compute scale.

    \notecue{Watch for}{Do not equate a stronger prior with a better architecture. A mismatched prior excludes good solutions, which is why CNNs struggle with links between distant words in language.}

    \notecue{Next}{Measure how much sharing a local filter cuts per-detector weights on MNIST and where a CNN's total weights still hide.}
  }
\end{frame}

\begin{frame}{A shared filter learns 87 times fewer weights per detector}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=3.9cm,keepaspectratio]{mnist_detectors_step}{2}\\[0.3cm]
  \uncover<3->{\normalsize Whole networks: a small CNN, 421,408 weights; the 784-128-64-10 MLP, 109,184.\\[0.1cm]
  The CNN's dense head holds 96 percent of its weights.}
  \mlsyscredit{Network Architectures, Example 6.1 (MNIST).}
  \note{%
    \mlsysnotemeta{1.5 min}{Optional}%
    How large is the payoff when a prior matches the data? On $28 \times 28$ MNIST images, learning 32 dense feature detectors takes $32 \times 784 = 25{,}088$ weights. Replacing them with 32 shared $3 \times 3$ convolutional filters reused across all 784 pixels drops the count to 288 weights, or $87\times$ fewer per detector. Whole-network totals, however, carry a surprise. The small CNN holds 421,408 weights against 109,184 for the MLP, because the CNN's closing fully connected classifier layers, called its dense head, hold 96\% of its parameters.

    \notecue{Check}{Did convolution actually save weights here? Yes per feature detector, because each $3 \times 3$ filter is shared across every pixel. A tempting conclusion is that a CNN always has fewer total weights than an MLP, yet whole-network totals depend on layer widths and dense heads.}

    \notecue{Teach}{For a 50-minute class, skip this slide and mention the $87\times$ per-detector saving aloud on the previous slide.}

    \notecue{Next}{Price the dense layer itself, from a miniature graph to production widths.}
  }
\end{frame}

    To price the weak-prior baseline directly, recall from Lecture 5 that a dense layer connects every input to every output as one matrix multiply.     \notecue{Check}{What happens to the dense weight count if both image height and width double? The input count quadruples, so the weights quadruple as well. A tempting answer is that the weights merely double, which forgets that image area grows with height times width.}

          \node[font=\footnotesize\bfseries, text=mlsysaccent, anchor=north west, align=left] at (-0.75,-0.55) {one read,\\[-2pt]$B$ uses};}
      \end{tikzpicture}
    \end{column}
    \begin{column}{0.56\textwidth}
      \normalsize
      \uncover<2->{FLOPs $= 2\,d_{\text{in}}\,d_{\text{out}}$\quad / \quad Bytes read $= 4\,d_{\text{in}}\,d_{\text{out}}$\\[0.35cm]}
      \uncover<3->{$I = \dfrac{2\,d_{\text{in}}\,d_{\text{out}}}{4\,d_{\text{in}}\,d_{\text{out}}} = $ {\Large\textbf{\textcolor{mlsysaccent}{0.5 FLOP/byte}}}\\[0.35cm]}
      \uncover<4->{Accelerators need tens to hundreds of FLOPs per byte to stay busy.\\[0.25cm]}
      \uncover<5->{Batch $B$: each weight read serves $B$ examples.}
    \end{column}
  \end{columns}
  \mlsyscredit{Network Architectures, equation 2 (weight-only model; ignores inputs, outputs, and caches).}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    Single-use weights immediately expose memory traffic. At batch 1, a dense layer performs $2 d_{\text{in}} d_{\text{out}}$ FLOPs and reads $4 d_{\text{in}} d_{\text{out}}$ bytes of FP32 weights. Dividing FLOPs by bytes cancels both widths, leaving 0.5 FLOP/byte regardless of layer size. Accelerators need tens to hundreds of FLOP/byte, so batch-1 execution stalls arithmetic and burns energy. In Horowitz's 2014 energy model for a 45 nm (45-nanometer) chip process, developed in Lecture 11, one FP32 read from off-chip DRAM costs roughly 139 MACs of energy. Batching $B$ examples reuses each weight read $B$ times, lifting intensity toward $0.5 B$ until activations enter the byte count (Lecture 5).

    \notecue{Check}{What batch size lifts this weight-only model to 100 FLOP/byte? Roughly $B = 200$, because $0.5 B$ must reach 100. A tempting answer is 100, overlooking that batch 1 starts at 0.5 rather than 1.}

    \notecue{Watch for}{Small layers like 784-by-128 can fit in on-chip cache, shifting the limit from HBM bandwidth to kernel launch overhead.}

    \notecue{Next}{Set arithmetic intensity against the machine's balance to close Segment 1.}
  }
\end{frame}

\mlsysnote{%
  \mlsysnotemeta{1.5 min}{Core}%
  Segment 1 established that an assumption-free dense layer sits at 0.5 FLOP/byte at batch 1. Recall from Lectures 1 and 2 that arithmetic intensity $I$, operations per byte moved, decides which iron-law term dominates when set against the machine's balance, or ridge point (peak FLOP/s divided by memory bandwidth, expanded into full hardware roofline analysis in Lecture 11). Above that balance a layer is compute-bound; below it, memory-bound. Every family today occupies its own band on this axis except recurrence, which stalls on serial steps instead.

  \notecue{Check}{Does the batch-1 dense layer sit above or below an accelerator's balance? It sits below by over a hundredfold, making it memory-bound. A tempting answer is compute-bound because dense layers hold large weight matrices, yet moving every weight for a single multiply-add starves the arithmetic units.}

  \notecue{Next}{Begin Segment 2 to test whether assuming spatial locality in convolution lifts intensity above the machine's balance.}
}

    \notecue{Check}{Can one 10 TFLOP/s GPU handle 30 FPS ResNet-50? Yes, with $20.3\times$ headroom at 5 TFLOP/s achieved. A tempting mistake is dividing peak 10 TFLOP/s by 8.2 GFLOP to claim over 1,000 FPS, ignoring achieved utilization.}

    \notecue{Watch for}{A single 30 FPS stream runs at batch 1, where launch overhead and small matrices can push utilization well below 50\%, so always benchmark on hardware.}

\begin{frame}{Factoring a convolution cuts its work about eight times}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.0cm,keepaspectratio]{depthwise_step}{3}\\[0.2cm]
  \uncover<2->{\normalsize Depthwise: one 3$\times$3 filter per channel, $9 \times 64 = 576$ (reused by all outputs).\\[0.1cm]}
  \uncover<3->{\normalsize Pointwise 1$\times$1 mixes channels ($64 \times 64 = 4{,}096$): $36{,}864 / 4{,}672 \approx$ {\large\textbf{\textcolor{mlsysaccent}{7.9$\times$}}} fewer.}
  \mlsyscredit{Network Architectures, \S6.3.5 (Howard et al. 2017; interactive Explore figure: Spatial Filtering and Channel Mixing).}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Standard convolutions strain mobile budgets because one $3 \times 3$ layer across 64 input and 64 output channels costs $9 \times 64 \times 64 = 36{,}864$ MACs per position. Popularized by MobileNet (Howard et al., 2017) for smartphones, depthwise separable convolution splits that work in two. A depthwise pass applies one $3 \times 3$ filter per input channel ($9 \times 64 = 576$ MACs for 64 spatial maps), and a $1 \times 1$ pointwise pass mixes channels ($64 \times 64 = 4{,}096$ MACs). Together they cost 4,672 MACs, or $7.9\times$ fewer, following $1/C_{\text{out}} + 1/K^2 \to 9\times$.

    \notecue{Check}{Where did the $7.9\times$ reduction come from? Separating spatial filtering from channel mixing makes their costs add rather than multiply. A tempting assumption is that the block shrinks the filter or drops channels, yet all 64 channels and $3 \times 3$ windows remain.}

    \notecue{Watch for}{Do not equate $7.9\times$ fewer FLOPs with a $7.9\times$ wall-clock speedup. The next slide tests that claim on real hardware.}

    \notecue{Next}{Test whether MobileNetV2's $13.7\times$ FLOP reduction delivers a $13.7\times$ speedup on CPUs and GPUs.}
  }
\end{frame}

  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Plain RNNs also lose gradients over long sequences, so Hochreiter and Schmidhuber (1997) invented the Long Short-Term Memory (LSTM) layer. It carries a separate memory vector, the cell state $c_t$, beside the hidden state $h_t$, replacing one affine map (matrix multiply plus bias) with four gated updates (input, forget, candidate, and output). The forget gate preserves cell-state gradients across long spans at $4\times$ the weights and MACs. PyTorch packs all four maps into single matrices of shape \texttt{[512, 100]} and \texttt{[512, 128]}, lowering them onto GEMM without removing serial steps. Inference overwrites one fixed state (2 KB for 512 FP32 values at any length), whereas training via backpropagation through time (BPTT) keeps all $T$ states, the trade-off Lecture 6b reverses.

    \notecue{Check}{Why does a fixed 2 KB inference state appeal on a microcontroller? Working memory stays constant regardless of stream duration, whereas a state growing with length would quickly overflow on-chip memory.}

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Each architecture bets on the data's structure; a matching bet saves weights and data.
    \item Dense layers at batch one do 0.5 FLOP per byte with FP32 weights; convolution reuses each weight at every position.
    \item A convolution becomes a matrix multiply by unfolding its patches, at up to $K^2$ times the input memory.
    \item Skip connections and normalization make depth trainable; each adds memory traffic.
    \item Recurrence holds state fixed and pays in serial steps.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Taken together, these five takeaways summarize what each fixed-weight architecture commits the machine to. Matching inductive biases saves data and weights. Batch-1 dense layers sit at 0.5 FLOP/byte, whereas convolution reuses each weight across the image. Unfolding via im2col lowers convolution onto GEMM at up to $K^2$ memory expansion. Skip connections and normalization make depth trainable while adding memory traffic, and recurrence holds state fixed while paying in serial steps.

    \notecue{Check}{Which of these five points could you not have explained an hour ago? Pick one and explain both the data assumption and the hardware cost in your own words without looking back.}
