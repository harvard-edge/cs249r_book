  \note{[3 min] Worked example 1. Step 1: the given. Step 2: each weight takes part in one multiply-add, two FLOPs. Step 3: each weight is read once, four bytes in FP32. Step 4: the ratio, arithmetic intensity, is half a FLOP per byte, whatever the widths, because both counts grow with the same product. Step 5: an accelerator's arithmetic can consume tens to hundreds of FLOPs for every byte its memory delivers, so this layer leaves most of the arithmetic idle, waiting for weights. Step 6: the one change that raises the ratio. The diagram under the given card shows it: with a batch of B examples each weight read serves B multiply-adds, so intensity grows to about 0.5 times B until activation traffic takes over (Lecture 5). Low intensity also costs energy. In Horowitz's 45 nm figures, reading one FP32 weight from DRAM costs about 139 multiply-adds' worth, so batching that divides the reads also cuts energy per inference; Lecture 11 shows the full energy table. ENGAGE: ``At what batch does this layer reach 100 FLOP per byte?'' Expected: about 200. WARN: this is a weight-only model; a small layer such as 784 by 128 can stay in on-chip cache, and then dispatch overhead dominates over memory bandwidth. FLEX: [CORE].}
\end{frame}

\mlsysnote{[1.5 min] The one ratio to remember today. Arithmetic intensity is the work done per byte moved. Compare it with the machine's balance, its peak FLOP/s divided by its memory bandwidth: above the balance the arithmetic limits (the compute term of the iron law), below it the memory limits (the data term). Step 1: BatchNorm computes its mean and variance across the examples in the mini-batch (and, for CNNs, across positions), so its output depends on which other examples share the batch; small batches give noisy statistics, and a batch split across accelerators needs an all-reduce to agree on them. LayerNorm computes them across the features of one token, so it works at batch one and for text generated one token at a time. RMSNorm drops the mean and keeps only the root mean square, a simpler kernel. Typical use: BatchNorm in CNNs, LayerNorm in transformers and RNNs, RMSNorm in Llama-family models. Step 2: the operational cost. BatchNorm keeps running averages and switches to them at serving, so a mismatch between those averages and live data is a frequent source of training-serving skew. All three are elementwise and memory bound. ENGAGE: ``Which one could you use to generate text one token at a time?'' Expected: LayerNorm or RMSNorm. LINK: Part 2's transformer block. FLEX: if cut, Part 2 names LayerNorm in the transformer block.}
\end{frame}

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Each architecture bets on the data's structure; a matching bet saves weights and data.
    \item Dense layers at batch one do 0.5 FLOP per byte with FP32 weights; convolution reuses each weight at every position.
    \item A convolution becomes a matrix multiply by unfolding its patches, at up to $K^2$ times the input memory.
    \item Skip connections and normalization make depth trainable; each adds memory traffic.
    \item Recurrence holds state fixed and pays in serial steps.
  \end{itemize}
