\mlsysdivider{Why does the ML lifecycle loop back?}{ML Lifecycle, \S3.1}
\section{The Loop}

\begin{frame}{Six stages, each handing an artifact to the next}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=5.4cm,keepaspectratio]{loop_step}{3}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    Every ML project moves through six stages in order, from Define, Collect and prepare data, and Develop and train, through Evaluate and validate, Deploy and integrate, and Monitor and maintain. Each stage hands forward a concrete artifact, namely numeric targets, a versioned dataset (a tracked data snapshot, Lecture 4), trained weights, a release manifest recording verification evidence, and a live service. The dashed green return arrow closes the loop, sending monitoring evidence and drift (shifts in incoming data, Lecture 1) back to any earlier stage, automated in Lectures 14 and 14b.

    \notecue{Check}{Which arrow does a traditional rule-based project draw thinly or omit? The answer is the return arrow. Forward hand-offs are a tempting guess, yet ordinary software also specifies, builds, tests, and deploys. The return arrow separates an ML lifecycle from a one-way build pipeline because deployment starts continuous monitoring and retraining.}

    \notecue{Watch for}{Do not read stages 1 to 6 as a one-pass schedule, because deployment starts the live loop.}

    \notecue{Next}{See measured benchmark evidence explaining why unchanged ML code degrades when only input data shifts.}
  }
\end{frame}

\begin{frame}{ML behavior can change when only the data changes}
  \centering
  \safeimg[width=0.86\textwidth,height=4.7cm,keepaspectratio]{wilds_camelyon17_fig4.png}\\[0.2cm]
  {\normalsize Same code. Accuracy \textbf{93.2\%} on the training hospitals, \textcolor{RedLine}{\textbf{70.3\%}} on hospital 5.}
  \mlsyscredit{Koh et al., ``WILDS: A Benchmark of in-the-Wild Distribution Shifts,'' ICML 2021, figure 4 and table 1 (Camelyon17-WILDS, standard training). Argument: ML Lifecycle, table 1.}
  \note{%
    \mlsysnotemeta{1.5 min}{Optional}%
    Why does an ML system require that return arrow when rule-based software stays fixed until code or configuration edits land? A learned model changes behavior whenever the world shifts beneath frozen weights, recalling Lecture 1's silent failure. In the Camelyon17-WILDS medical imaging benchmark (Koh et al., ICML 2021), tissue stains and scanners differ across hospitals. A model trained on hospitals 1 through 3 reaches 93.2\% accuracy on held-out patches (images withheld from training) from those same hospitals. With zero code changes, accuracy drops 22.9 points to 70.3\% on hospital 5, mirroring what happens when a clinic swaps fundus cameras.

    \notecue{Watch for}{The 93.2\% score is in-distribution accuracy, measured on held-out examples from the training hospitals using the identical model. Only fresh labeled outcomes from the new site expose the gap.}

    \notecue{Teach}{For a 50-minute class, skip this slide and state orally on the loop slide that ML behavior changes when only the input distribution changes.}

    \notecue{Next}{Follow the chapter's Day-153 scenario to see what happens when teams treat the six stages as a one-way line.}

\end{frame}

\mlsysdivider{How does one decision reach every other stage?}{ML Lifecycle, \S3.2 and \S3.4}
\section{Propagation}

\mlsysnote{%
  \mlsysnotemeta{2 min}{Core}%
  A constraint discovered late forces rework in every artifact that relied on its absence. Datasets, trained weights, validation reports, and deployment packages all encode earlier assumptions, so late discovery requires tracing dependencies and rebuilding every affected artifact. No universal cost multiplier predicts the bill. Stating limits early lets constraints shape design choices instead of rejecting finished work.

  \notecue{Watch for}{This principle does not require freezing every decision on Day 1. Teams freeze the operating envelope (memory, latency, power, and safety floors) early while iterating freely on data and models inside those bounds.}

  \notecue{Teach}{Read the principle aloud before unpacking why late constraints force dependency tracing.}

  \notecue{Next}{Trace the Day-153 memory limit backward around the six-stage loop.}
}
\mlsysfocus{The Constraint Propagation Principle}{%
  A constraint discovered late forces rework in every artifact\\that relied on its absence.\\[0.5cm]
  {\normalsize\textcolor{white!75}{State a limit early, while it can still shape the work.}}%
}

  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Applying that principle to Day 153 begins where the 500 MB memory ceiling surfaced, at Stage 5 (Deployment). Along the dashed rework arrow, four stages turn red because Stage 2 preprocessing (resizing and preparing input images), Stage 3 weights, Stage 4 validation evidence, and Stage 5 packaging all assumed an unconstrained memory footprint. Placing that 500 MB requirement in Stage 1 on Day 1 lets it select an appropriate architecture family before training begins.

    \notecue{Check}{Must all of Stage 2 be discarded when this limit arrives late? Not necessarily. It is tempting to assume that every artifact in a red stage is lost, yet some Stage 2 artifacts can survive even when preprocessing changes, setting up the artifact-level dependency audit shortly in this section.}

\begin{frame}{Constraints travel backward and forward through the stages}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=5.3cm,keepaspectratio]{directions_step}{2}
  \mlsyscredit{ML Lifecycle, \S3.2.}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    The Day-153 limit traveled backward, yet dependencies run in both directions across the six stages, forming a coupled network. Tracing backward, a 2 Mb/s (megabits per second) clinic uplink forces lossy image compression (discarding fine detail to shrink files) at Stage 5, so matching compression artifacts must appear in Stage 2 training data to prevent training-serving skew (Lecture 1's mismatch between training and live inputs). Tracing forward, the Stage 2 capture resolution needed to resolve tiny retinal hemorrhages fixes input dimensions and inference FLOPs (floating-point operations) on the Stage 5 clinic device. Lecture 4 develops data cascades, chains of downstream failures triggered by bad data.

    \notecue{Check}{Name one more backward constraint path in the loop. One example is a serving latency ceiling at Stage 5 limiting how many layers the model can have during Stage 3 training. Treating Stage 3 in isolation is tempting, yet an accurate model fails if it answers too slowly in the clinic.}

  }
\end{frame}

\begin{frame}{A contract at each hand-off names the stage that owns a defect}
  \begin{columns}[c]
    \begin{column}{0.74\textwidth}
      \centering\mlsyssteps[width=\textwidth,height=5.8cm,keepaspectratio]{contracts_step}{4}
    \end{column}
    \begin{column}{0.24\textwidth}
      \small\raggedright
      Each hand-off checks an \textbf{invariant}.\\[0.3cm]
      \uncover<2->{Target ``TBD'': data collection is \textcolor{RedLine}{\textbf{blocked}}.\\[0.3cm]}
      \uncover<4->{No result for patients over 70: \textcolor{RedLine}{\textbf{stage 4}} owns the gap.}
    \end{column}
  \end{columns}

  \note{%
    \mlsysnotemeta{2 min}{Core}%

At later hand-offs, Stage 2 requires provenance (camera, settings, and operator) and Stage 4 requires subgroup floors. When monitoring later flags a clinic referral shift for patients over 70, auditing the release manifest shows no over-70 sensitivity entry, so Stage 4 owns the gap. Across D\textperiodcentered{}A\textperiodcentered{}M (Lecture 1), Stages 2, 3, and 5 own Data, Algorithm, and Machine, while Stages 4 and 6 verify.

\begin{frame}{Takeaways}
  \small
  \begin{itemize}\setlength{\itemsep}{0.12cm}
    \item The lifecycle is a loop of six stages; monitoring sends evidence back, so deployment starts a phase.
    \item A late constraint forces rework in every artifact that relied on its absence, so trace the dependencies.
    \item Cycle time sets how many ideas a team can test; speed buys breadth of search.
    \item Requirements are numbers in three layers: statistical, physical, operational.
    \item Validation decides readiness by testing the floors on field data, per subgroup, on the device.
    \item Screen deployment for feasibility first; cost only confirms.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Those clinic lessons condense into six core lifecycle principles, covering the six-stage loop with monitoring return paths, late-constraint rework tracing, iteration breadth, three-layer numeric requirements, subgroup and on-device release manifests, and feasibility-first deployment screening.
