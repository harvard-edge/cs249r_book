\mlsysdivider{Why does the ML lifecycle loop back?}{ML Lifecycle, \S3.1}
\section{The Loop}

\begin{frame}{Six stages, each handing an artifact to the next}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=5.4cm,keepaspectratio]{loop_step}{3}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    This six-stage loop anchors the entire lecture. Step 1 names the stages in initial project order: Define, Collect and prepare data, Develop and train, Evaluate and validate, Deploy and integrate, and Monitor and maintain. Step 2 labels each hand-off artifact: numeric targets, a versioned dataset, trained weights, a release manifest recording verification evidence, and a live service. Step 3 adds the dashed green return arrow: post-launch monitoring feeds drift and failure evidence back to any earlier stage (operationalized in Lectures 14 and 14b).

    \notecue{Check}{Ask which arrow a traditional rule-based project draws thinly or omits. The return arrow separates an ML lifecycle from a one-way build pipeline because deployment starts continuous monitoring and retraining.}

    \notecue{Watch for}{Students often read stages 1 to 6 as a one-pass schedule; stress that deployment marks the start of the live loop.}

    \notecue{Next}{Examine empirical benchmark evidence showing why unchanged ML code degrades when only input data shifts.}
  }
\end{frame}

\begin{frame}{ML behavior can change when only the data changes}

\mlsysdivider{How does one decision reach every other stage?}{ML Lifecycle, \S3.2 and \S3.4}
\section{Propagation}

\mlsysnote{%
  \mlsysnotemeta{2 min}{Core}%
  Read the principle aloud: a constraint discovered late forces rework in every artifact that relied on its absence. Datasets, trained weights, validation reports, and deployment packages all encode earlier assumptions, so late discovery requires tracing dependencies and rebuilding every affected artifact; no universal cost multiplier predicts the bill. Stating limits early lets constraints shape design choices instead of rejecting finished work.

  \notecue{Watch for}{Students sometimes infer that every decision must be frozen on Day 1; clarify that teams freeze the operating envelope (memory, latency, power, safety floors) early while iterating freely on data and models inside it.}

  \notecue{Next}{Trace the Day-153 memory limit backward around the six-stage loop.}
}
\mlsysfocus{The Constraint Propagation Principle}{%
  A constraint discovered late forces rework in every artifact\\that relied on its absence.\\[0.5cm]
  {\normalsize\textcolor{white!75}{State a limit early, while it can still shape the work.}}%
}

\begin{frame}{Constraints travel backward and forward through the stages}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=5.3cm,keepaspectratio]{directions_step}{2}
  \mlsyscredit{ML Lifecycle, \S3.2.}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Because dependencies run in both directions, the six stages form a coupled constraint network. \begin{frame}{Takeaways}
  \small
  \begin{itemize}\setlength{\itemsep}{0.12cm}
    \item The lifecycle is a loop of six stages; monitoring sends evidence back, so deployment starts a phase.
    \item A late constraint forces rework in every artifact that relied on its absence, so trace the dependencies.
    \item Cycle time sets how many ideas a team can test; speed buys breadth of search.
    \item Requirements are numbers in three layers: statistical, physical, operational.
    \item Validation decides readiness by testing the floors on field data, per subgroup, on the device.
    \item Screen deployment for feasibility first; cost only confirms.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Review one summary line per major lecture idea: the six-stage loop with monitoring return paths, late-constraint rework tracing, iteration breadth (omit if Segment 3 was skipped), three-layer numeric requirements, subgroup and on-device release manifests, and feasibility-first deployment screening.
