\begin{frame}{Proving one false wake a month takes 2,160 hours of audio}
  \begin{columns}[c]
    \begin{column}{0.72\textwidth}
      \centering\safeimg[width=\textwidth,height=3.2cm,keepaspectratio]{listen_hours.pdf}
    \end{column}
    \begin{column}{0.25\textwidth}
      \centering\mlsysphoto[width=\textwidth,height=2.8cm,keepaspectratio]{amazon-echo-dot-board.jpg}\\[0.04cm]
      {\scriptsize\textcolor{midgray}{Smart speaker board}}
    \end{column}

  \vspace{0.25cm}\centering
  {\normalsize Zero false wakes in $T$ hours: the 95\% upper bound on the rate is about $3/T$.}\\[0.15cm]
  \uncover<2->{\normalsize\textcolor{mlsysaccent}{The target sets a data requirement that no training set replaces.}}
  \mlsyscredit{Data Engineering, \S4.11; the rule of three (Hanley and Lippman-Hand 1983). Photo: Raimond Spekking, CC BY-SA 4.0, Wikimedia Commons.}
  \note{%
    \mlsysnotemeta{2.5 min}{Optional}%
    Even observing zero false wakes across one 720-hour month does not prove a rate below one per month. By the rule of three (Hanley and Lippman-Hand, 1983), zero events in $T$ hours yield a 95\% upper confidence bound near $3/T$, ruling out higher true rates at that confidence level. Bounding the rate at $1/720\text{ h}$ therefore requires $3 \times 720 = 2{,}160$ hours of continuous audio. At a 16 kHz sampling rate, how frequently audio is measured per second, and 16 bits per sample, that corpus spans roughly 248 GB, a line the initial \$150K plan never budgeted. Statistical targets create data requirements no training set can replace.

    \notecue{Check}{Why must these 2,160 hours never enter training or threshold tuning? Once a model or threshold adapts to those recordings, they no longer give an unbiased estimate of live false-wake rates.}

    \notecue{Teach}{For a 50-minute class, skip this slide and state orally that proving 1 false wake per month requires 2,160 held-out listening hours.}

    \notecue{Next}{If those streams must stay untouched, how do they differ from hard negatives collected to improve rejection?}

\begin{frame}{Training-serving consistency needs shared statistics}
  \centering
  \mlsyssteps[width=0.94\textwidth,height=4.7cm,keepaspectratio]{skew_step}{3}\\[0.1cm]
  \uncover<3->{\small\textcolor{mlsysaccent}{KWS: normalizing each stored clip against its own peak uses audio a streaming device never has.}}
  \mlsyscredit{Data Engineering, \S4.7.1 (interactive Explore figure: Shared Preprocessing State).}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Recall from Lecture 1 that training-serving skew degrades predictions silently when training and serving compute features differently. Identical code still skews when fitted state diverges. Training fits normalization parameters ($\mu=20.0, \sigma=8.17$) strictly on the training split and standardizes inputs by subtracting the mean and dividing by the standard deviation, mapping $x=50$ to $z=+3.67$. If serving runs the same code on a shifted batch $[50, 70, 90]$, refitting yields $\mu=70.0, \sigma=16.33$ and maps $x=50$ to $z=-1.22$, a silent $4.90\sigma$ skew. Sealing those frozen statistics with the learned weights cuts skew to $0.00\sigma$. Likewise, normalizing KWS clips by each clip's peak fails because streaming microphones never see future peaks.

    \notecue{Watch for}{Sharing transformation code alone never guarantees consistency. Training-serving consistency also requires synchronizing frozen fitted state, explored interactively in \S4.7.1.}

\begin{frame}{Tay had no boundary; the wake-word pipeline has four so far}
  \centering
  \mlsyssteps[width=0.96\textwidth,height=5.6cm,keepaspectratio]{pipeline_step}{2}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Returning to the opening hook answers our driving question directly. In Tay's unguarded loop, live public replies flowed straight into learned weights without filtering or rate limits. By contrast, the wake-word pipeline places four boundaries between raw input and the model. Those boundaries combine contracted ingestion with a dead-letter queue (alongside the batch-versus-streaming choice at $\approx 3\times$ cost and ETL versus ELT from Napkin Math 4.3), rubric-driven labeling tracked by $\kappa$, frozen training-split feature state, and hashed speaker-key releases recording how the dataset was built. The two remaining downstream stages, accelerator delivery and drift monitoring, open Part 2.

    \notecue{Check}{Which single boundary would have prevented Tay's collapse? Contracted ingestion would have stopped it by enforcing adversarial filtering and rate limits before user text reached learning.}

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Data is the program, so version it, test it, and review it.
    \item A product target sets a data budget; 1 false wake a month means 2,160 h of audio.
    \item Labels are the specification and usually the largest data cost.
    \item Leakage and skew come from inside the pipeline; contracts fitted on the training split stop them.
    \item A release records how the dataset was built.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1 min}{Core}%
    Together, these principles answer how to engineer training data with the discipline given to code. Treat data as code, derive data and 2,160-hour listening budgets from product targets, price and audit labels, stop leakage and skew with training-fitted boundary contracts, and publish immutable traceable releases.
