\section{Rebuild and Trace}

\begin{frame}{A model is a function of four versioned inputs and the rounding}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=5.3cm,keepaspectratio]{repro_step}{2}
  \mlsyscredit{ML Operations, equation 1 and footnote 4 (DVC), \S14.1.1.}
  \note{[2.5 min] Equation 1 as a picture. Step 1: the deployed model's behavior is a function of four inputs, each identified by a version: the code (a Git commit), the data (a content hash, for example from DVC, a tool that versions datasets the way Git versions code), the configuration and hyperparameters (a config file), and the environment (a container image with pinned libraries). Lose any one and no combination of the others rebuilds the model. Step 2: even with all four frozen, a run on an accelerator is not bit-for-bit repeatable. Floating-point addition is not associative, so sums reduced in a different order round differently, and the differences compound over thousands of steps; identical seeds can still diverge. Deterministic kernels fix the order at a cost in speed. ENGAGE: which input do teams most often fail to version? The data; the chapter's footnote: without it, the data term is unrecoverable. LINK: Lecture 12 owns the reproducibility envelope across runs. FLEX: [CORE].}
\end{frame}

\begin{frame}{The registry promotes and reverts the exact artifact evaluated}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=6.0cm,keepaspectratio]{registry_step}{3}
  \mlsyscredit{ML Operations, \S14.3.1 (versioning and lineage, footnote 7) and \S14.7.2 (promotion gate).}
  \note{[3 min] A model registry is the store that holds every deployable model as an immutable, versioned artifact with a lifecycle state. Step 1: candidate, staging, production, retired. Promotion moves the exact artifact that was evaluated; rollback returns traffic to a previous artifact, not to a rebuilt approximation. Step 2: lineage links each artifact to its inputs by hash: raw logs, the dataset snapshot, the features, the training run, the weights, the endpoint. Any live prediction can be traced back to the data that produced it. Step 3: the chapter's promotion gate makes governance a release rule: a signed feature contract, a lineage hash, subgroup metrics above policy, a canary service-level objective with rollback criteria, and a named owner. ENGAGE: what goes wrong without a registry? Registry bypass, the chapter's footnote: a hotfix applied directly to the serving endpoint, so the model in production is not the one anyone evaluated, and rollback means hunting for the right weights during an incident. LINK: Lecture 3 handed the registry to this lecture; Lecture 8's checkpoints are what it stores. FLEX: [CORE].}
\end{frame}

\begin{frame}{A continuous-training pipeline runs seven gated stages}
  \centering
  \mlsyssteps[width=0.9\textwidth,height=4.9cm,keepaspectratio]{cicd_step}{2}
  \mlsyscredit{Slide variant of ML Operations, figure 6 (\S14.3.2). Baylor et al., ``TFX,'' KDD 2017 (Example 14.1).}
  \note{[2.5 min] Step 1: when a trigger starts a retraining run, the data stages run first: ingest new data, validate it against the schema, and transform it into features with the versioned transform. Step 2: then train, evaluate, and validate the model, and register it. \begin{frame}{Only a request-keyed replay proves two pipelines agree}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.1cm,keepaspectratio]{parity_step}{3}\\[0.05cm]
  \uncover<3->{\small At 1 percent skew, 1 million queries a day, and \$0.10 an error: \$365,000 a year.}
  \mlsyscredit{ML Operations, \S14.3.1 (illustrative ranking-service case) and equation 2.}
  \note{[3 min] Training-serving skew, from Lecture 4: training and serving compute a feature differently. Step 1: the test is a replay. Take recorded requests and run each one through both versioned transforms, offline and online. Step 2: in the chapter's illustrative case, a serving release cost the ranking service 8 percent of its accuracy with no change to model code or weights. The feature user\_session\_length averaged 45 minutes in training and 12 in serving: the offline pipeline measured wall-clock time from first to last event, the serving path counted only foreground-active time. Step 3: why a distribution test is not enough. Swap the values for requests A and B: the histograms match, so a Kolmogorov-Smirnov (K-S) test, which compares two distributions, passes. Only comparing the same request on both paths finds the bug. ENGAGE: what makes the replay possible? Versioned code, data, and transforms: equation 1 and the registry from the last frames. WARN: a mean difference alone could be a new user population. LINK: a feature store, one shared definition for both paths, is the usual fix (Lecture 4). FLEX: [CORE].}
\end{frame}

  \mlsyssteps[width=0.92\textwidth,height=4.9cm,keepaspectratio]{artifact_step}{2}

  \note{[2 min] Step 1: the checkpoint that passed evaluation is usually compiled into a static graph for one runtime and often lowered in precision, for example to 8-bit integers (INT8), before it serves. Each conversion can change what the model computes. Step 2: so the checks run on the engine users will get: outputs compared with the original slice by slice, peak memory measured at load, warm-up and startup time, and a pinned runtime version, because even a minor runtime upgrade can change kernel selection and results for weights that never changed. The chapter's case: a team checked only throughput after quantizing to INT8; accuracy fell on rare, high-value cases and went unnoticed for weeks because the aggregate stayed within bounds. ENGAGE: an unpinned runtime is an untracked input to which equation? Equation 1, the environment term. LINK: Lecture 10 owns quantization; this slide owns only the check. Land the segment: version code, data, config, and environment; promote and revert only registered artifacts; prove parity by replay. FLEX: [OPTIONAL].}

\begin{frame}{One of eight servers missed the update}
  \centering
  {\fontsize{36}{40}\selectfont\bfseries\textcolor{mlsysaccent}{about 70\%}}\\[0.1cm]
  {\normalsize of outages come from changes to a live system.}\\[0.35cm]
  \uncover<2->{\safeimg[width=0.9\textwidth,height=2.9cm,keepaspectratio]{knight_servers.pdf}\\[0.1cm]
  {\small Knight Capital had no second technician review and no written procedure requiring one.}}
  \mlsyscredit{Beyer et al., \emph{Site Reliability Engineering} (Google, 2016), ch.~1. SEC, Knight Capital Americas LLC, Release No.~34-70694 (2013), \P15 and \P16.}
  \note{[2 min] Step 1: Google's site reliability engineers report that roughly 70 percent of outages are due to changes in a live system. Releasing is the risky moment. Step 2: Knight Capital, a large U.S. market maker, July and August 2012. Engineers deployed new code to SMARS, its order router, a few servers a day; one technician did not copy the code to the eighth server. Knight had no second review and no written procedure that required one. The new code reused an old flag. On seven servers the flag meant the new retail program; on the eighth it switched on Power Peg, a retired routine still in the code. ENGAGE: what one check would have caught this? Verifying that every node runs the intended version before traffic arrives. WARN: the book's war story adds two figures (17 percent of NYSE volume, about 1,400 orders a second) that are not in the SEC order; use the order's numbers. FLEX: [CORE].}
\end{frame}

\begin{frame}{Knight lost \$460 million in about 45 minutes}

  \only<3-|handout:1>{\mlsysactivity{Predict}{2 min}}%

  \note{[3.5 min] Step 1: 1 August 2012. From about 8:01 a.m., an internal system sent automated e-mails reading ``Power Peg disabled''; 97 reached staff before the 9:30 open. \begin{frame}{Exposure grows in stages: shadow, canary, then ramp}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=5.4cm,keepaspectratio]{release_step}{3}
  \mlsyscredit{ML Operations, \S14.4.3 and table 11; ranking service illustrative.}
  \note{[2.5 min] Three ways to put v2 in front of traffic, in order of exposure. Step 1: shadow deployment. The router sends every user to v1 and a copy of every request to v2; v2's answers are logged and compared, never shown. No user is exposed, but nothing is learned about how users respond, because they never see v2. Step 2: canary. Now 5 percent of users get v2's answers, and the team compares click-through and p99 latency against v1 on that slice. Step 3: the ramp. Exposure rises in steps, 5, 25, 50, 100 percent, and each step passes only if its metrics hold; a failed gate routes traffic back to v1. ENGAGE: why not jump from 5 to 100? Some failures appear only at load: the chapter's example is p99 inflation at 30 percent of traffic that was invisible at 5. WARN: a canary needs enough traffic to tell a real drop from noise; Lecture 12's statistics apply. Note the boxes: v2 is a full second copy in every mode, which the next slide prices. FLEX: [CORE].}
\end{frame}

  \note{[2.5 min] Step 1: the chapter's three rollback tiers. Immediate rollback answers crashes and errors seen right after release, by switching traffic to the hot standby. Rapid rollback answers canary metrics that degrade, by redeploying the previous version from the model registry, the store of every trained version with the code, data, and settings that produced it. \begin{frame}{A device that cannot be reached keeps a second flash bank}
  \centering
  \mlsyssteps[width=0.92\textwidth,height=5.3cm,keepaspectratio]{dualbank_step}{2}
  \mlsyscredit{ML Operations, \S14.4.4 and table 11 (keyword spotter: 200 KB model, 4 MB of flash).}
  \note{[2 min] The keyword spotter: a 200 KB model listening on a microcontroller with 4 MB of flash, in someone's home, on intermittent Wi-Fi. No engineer can log in and roll it back.
