    \mlsysnotemeta{2 min}{Core}%

  \end{tikzpicture}\\[0.3cm]
  \uncover<2->{\normalsize A chain of $k$ elementwise operations: $2kNb$ bytes unfused, $2Nb$ fused.}
  \mlsyscredit{ML Frameworks, \S7.3.2. FlashAttention applies the same idea to attention: up to 9$\times$ fewer HBM accesses (Dao et al. 2022; Lecture 8b).}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Blue arrows mark HBM reads and red arrows mark HBM writes. First, running LayerNorm, Dropout, and ReLU as three separate kernels requires 6 trips to HBM and 3 launches; because elementwise work does little math per byte, memory traffic dominates runtime. Second, a compiler seeing all three fuses them into one kernel that reads input once, holds intermediates in registers and on-chip SRAM, and writes once, cutting traffic roughly threefold to 2 trips and 1 launch. In general, $k$ elementwise ops over $N$ elements of $b$ bytes move $2kNb$ bytes unfused versus $2Nb$ fused; FlashAttention applies this principle to attention in Lecture 8b for up to 9 times fewer HBM accesses.

    \notecue{Check}{Ask why an eager runtime cannot fuse these three calls. It launches LayerNorm before Python ever reaches Dropout.}

    \notecue{Watch for}{Fusion cannot discard an intermediate required by the backward pass, and LayerNorm's row reduction is harder to fuse than pure elementwise ops. Lecture 11b examines where fusion stops paying.}

\mlsysnote{%
  \mlsysnotemeta{1 min}{Core}%
  The dispatch overhead law divides total host issue time ($N_{\text{ops}} \cdot t_{\text{dispatch}}$) by total device time ($T_{\text{compute}} + T_{\text{memory}}$, assuming no overlap). Per-operation work size, more than total parameter count, sets the regime.

\begin{frame}{Strides map tensor indices to 1D memory without copying}

  \uncover<4->{\small Views and transposes cost zero bytes; calling \texttt{.contiguous()} pays a full copy.}
  \mlsyscredit{ML Frameworks, \S7.5.1 (interactive Explore figure: Tensor Memory Layout).}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Physical memory is a flat 1D array, and a tensor is a metadata view over that storage. First, compare a $2 \times 3$ tensor in row-major order (C and PyTorch default, strides \texttt{[3, 1]}) against column-major order (Fortran, strides \texttt{[1, 2]}). Second, the stride formula $i \cdot s_0 + j \cdot s_1$ maps element \texttt{(1, 0)} (value 4) to address \texttt{[3]} in row-major memory and \texttt{[1]} in column-major memory. Third, reading row 0 touches adjacent addresses \texttt{[0, 1, 2]} in row-major order so cache lines coalesce, whereas column-major hops \texttt{[0, 2, 4]}. Fourth, \texttt{.T} copies zero bytes, issuing only a new header with shape \texttt{(3, 2)} and strides \texttt{[1, 3]}.

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Eager code shows the framework one operation at a time, easy to debug at about 15\,\textmu s of host time each.
    \item A captured graph lets the compiler fuse and plan; compiling pays only after enough runs.
    \item Reverse mode gets every gradient in one pass by keeping forward values, and those set training memory.
    \item The host link is 52$\times$ slower than HBM, so place data once, pin it, and overlap the copies.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    These four bullets distill one takeaway per section: eager dispatch costs roughly 15 \textmu s per operation; graph capture enables fusion and pays back only after enough runs; reverse-mode autodiff saves forward activations that dominate training memory; and the 52-fold PCIe gap demands explicit placement, pinned memory, and overlap. Ask students to star the takeaway they could least explain tomorrow and reread that section first.

    \notecue{Next}{Consider three open framework design questions, or proceed to readings in the core path.}
  }
\end{frame}

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.4cm}
    \item Should frameworks compile by default? Who should pay for the compile step?
    \item Checkpointing trades arithmetic for memory. When would you never use it?
    \item Operator coverage often decides whether a model runs on new hardware. Should the field standardize on a small operator core?
  \end{itemize}
  \note{%
    \mlsysnotemeta{1 min}{Optional}%
    None of these three engineering questions has a fixed answer. First, compiling by default trades researcher iteration speed against steady throughput, which is why PyTorch kept compilation opt-in. Second, activation checkpointing adds overhead whenever arithmetic is already the limiting factor. Third, standardizing a small operator core like ONNX's 203 ops eases hardware bring-up yet lags newly invented research ops. Ask students to pick one prompt and write two sentences defending a stance.

    \notecue{Optional}{Skip in a 50-minute class.}
