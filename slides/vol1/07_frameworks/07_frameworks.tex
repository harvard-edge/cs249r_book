  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Start with the simplest execution model, running every line the moment Python reaches it. Creating \texttt{x} immediately materializes \texttt{[1., 2.]} in tensor memory. Evaluating \texttt{y = x * 2} dispatches a multiply kernel right away and produces \texttt{[2., 4.]}. Because \texttt{y} already holds real numbers, \texttt{print(y)} succeeds at once, as would a debugger or a Python \texttt{if} branch on \texttt{y}. Evaluating \texttt{y.sum()} then runs immediately as well, giving \texttt{6.}. Executing each operation immediately as Python runs, building any needed gradient graph on the fly, is define-by-run execution, PyTorch's default and the model you build in TinyTorch module 01.

    \notecue{Check}{When \texttt{y = x * 2} runs, does the runtime know that \texttt{y.sum()} follows next? No. A tempting assumption is that the interpreter inspects the whole block first, yet eager Python hands the runtime one line at a time. That narrow view keeps debugging simple while blocking cross-operation optimization.}

  \mlsyscredit{ML Frameworks, \S7.3.2. FlashAttention applies the same idea to attention: up to 9$\times$ fewer HBM accesses (Dao et al. 2022; Lecture 8b).}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Whole-graph visibility pays off on the chain of LayerNorm, Dropout (randomly zeroing activations during training), and ReLU. Three separate kernels read from HBM (blue) and write back (red), costing 3 launches and 6 HBM trips. One fused kernel reads once, keeps intermediates in on-chip registers (fast slots beside the arithmetic units) and SRAM (detailed in Lecture 11), and writes once, cutting traffic roughly threefold to 2 trips and 1 launch. Generally, $k$ elementwise operations (acting on each entry independently) over $N$ elements of $b$ bytes move $2kNb$ bytes unfused versus $2Nb$ fused. Recall FlashAttention from Lecture 6b (Dao et al., 2022), which applies tiled fusion for up to 9 times fewer HBM accesses (revisited in Lecture 8b).

    \notecue{Check}{Why can an eager runtime not fuse these calls? It launches LayerNorm before Python reaches Dropout, never seeing the chain together.}

    \notecue{Watch for}{Fusion still must save intermediates needed for backward, and LayerNorm's row reduction (mean and variance per row) is harder to fuse than pure elementwise operations. Lecture 11b examines where fusion stops paying.}

\mlsysnote{%
  \mlsysnotemeta{1 min}{Core}%
  To predict which trace a workload will resemble before profiling, the dispatch overhead law divides total host issue time ($N_{\text{ops}} \cdot t_{\text{dispatch}}$) by total device time ($T_{\text{compute}} + T_{\text{memory}}$, assuming no overlap). When this ratio exceeds 1, host dispatch consumes more than half the step and the workload is overhead bound. In Napkin Math 7.2, a small 6-operation multilayer perceptron spends 90 \textmu s in dispatch against 2.6 \textmu s on the device, giving a ratio of 35 and 97 percent host overhead. By contrast, a large-batch GPT-3 block spends 0.18 ms across 12 kernels against 100 ms on the device, for a ratio of 0.002. Per-operation work size, more than total parameter count, sets the regime.

  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    To compute gradients automatically without manual calculus, PyTorch records a reverse-mode autograd tape as the forward pass runs, starting when \texttt{requires\_grad=True} marks \texttt{x}. Evaluating \texttt{y = x * 2} computes 2 and attaches \texttt{MulBackward0}, which links backward through \texttt{next\_functions} to \texttt{AccumulateGrad}, the leaf sink writing into \texttt{x.grad}. Next, \texttt{z = y + 1} attaches \texttt{AddBackward0} and finishes the forward tape. Calling \texttt{z.backward()} seeds $\partial z/\partial z = 1$, walks backward by the chain rule (propagating local derivative 1 across addition and multiplying by 2 across multiplication), populates \texttt{x.grad}, and releases the tape. Reading \texttt{x.grad} then returns \texttt{[2.]}. With millions of parameters and one scalar loss, forward mode (sweeping one parameter direction at a time) requires millions of passes. Reverse mode obtains every gradient in one pass without storing a Jacobian, the full matrix of partial derivatives, which would take 40 GB in FP32 for one 100,000-wide layer. You build this tape in TinyTorch module 06.

\begin{frame}{Caching avoids OS calls, but fragmentation still triggers OOM}

\begin{frame}{Strides map tensor indices to 1D memory without copying}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.9cm,keepaspectratio]{tensor_layout_step}{4}\\[0.1cm]
  \uncover<4->{\small Views and transposes cost zero bytes; calling \texttt{.contiguous()} pays a full copy.}
  \mlsyscredit{ML Frameworks, \S7.5.1 (interactive Explore figure: Tensor Memory Layout).}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    Because physical memory is a flat 1D array, frameworks view each multidimensional tensor through shape and strides, the elements skipped along each axis. On a $2 \times 3$ tensor, row-major order (C and PyTorch default, strides \texttt{[3, 1]}) contrasts with column-major order (strides \texttt{[1, 2]}), used by the scientific computing language Fortran and some Basic Linear Algebra Subprograms (BLAS) libraries. By $i \cdot s_0 + j \cdot s_1$, element \texttt{(1, 0)} (value 4) sits at \texttt{[3]} in row-major memory and \texttt{[1]} in column-major. Reading row 0 touches adjacent addresses \texttt{[0, 1, 2]} in row-major order so accesses coalesce into one cache line, a fixed contiguous block (memory coalescing, Lecture 11b), whereas column-major hops across \texttt{[0, 2, 4]}. Calling \texttt{.T} copies zero bytes, issuing only a new header with shape \texttt{(3, 2)} and strides \texttt{[1, 3]}.

    \notecue{Check}{When does a transpose actually copy bytes? Only when a downstream kernel requires contiguous memory and your code calls \texttt{.contiguous()}. A tempting belief is that \texttt{.T} rearranges elements in memory right away.}

\begin{frame}{Overlap pays for the longer stage instead of the sum}
  \centering

  \mlsyscredit{ML Frameworks, \S7.5.2 and listing 13.}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    Because every training batch must still cross PCIe, the way to hide transfer time (violet) behind GPU compute (orange) is to run them concurrently. Serial execution copies each batch before computing it, paying the sum on every step. Overlapped execution uses a separate CUDA stream, an independent GPU command queue, to drive the GPU's dedicated transfer hardware (the copy engine) for batch $i+1$ while compute units process batch $i$, so step time approaches $\max(T_{\text{copy}}, T_{\text{compute}})$. Overlap requires two conditions. Host buffers must be pinned (page-locked) so direct memory access (DMA), hardware transfers that bypass the CPU, avoids synchronous OS staging, and the loop must avoid accidental CPU-GPU synchronizations such as \texttt{.item()}, tensor prints, or \texttt{torch.cuda.synchronize()}.

    \notecue{Check}{What happens when a training loop logs \texttt{loss.item()} on every iteration? A single scalar log looks harmless, yet each call forces the host to wait for the GPU, collapsing the overlapped timeline back to serial execution.}

    \notecue{Next}{Next, inspect how PyTorch's \texttt{DataLoader} wires workers, prefetching, pinning, and asynchronous copies.}

\end{frame}

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Eager code shows the framework one operation at a time, easy to debug at about 15\,\textmu s of host time each.
    \item A captured graph lets the compiler fuse and plan; compiling pays only after enough runs.
    \item Reverse mode gets every gradient in one pass by keeping forward values, and those set training memory.
    \item The host link is 52$\times$ slower than HBM, so place data once, pin it, and overlap the copies.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1.5 min}{Core}%
    These four takeaways capture the quantitative rules behind those three decisions. Eager dispatch costs roughly 15 \textmu s per operation. Graph capture enables kernel fusion and pays back its compile cost only after enough runs. Reverse-mode automatic differentiation saves forward activations that dominate training memory. Finally, the 52-fold PCIe bandwidth gap demands explicit placement, pinned memory, and copy-compute overlap. Mark the takeaway you could least explain tomorrow and reread that section first.

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.4cm}
    \item Should frameworks compile by default? Who should pay for the compile step?
    \item Checkpointing trades arithmetic for memory. When would you never use it?
    \item Operator coverage often decides whether a model runs on new hardware. Should the field standardize on a small operator core?
  \end{itemize}
  \note{%
    \mlsysnotemeta{1 min}{Optional}%
    None of these three engineering questions has a fixed answer. Compiling by default trades researcher iteration speed against steady throughput, which is why PyTorch kept compilation opt-in. Activation checkpointing adds recomputation overhead whenever arithmetic is already the limiting factor. Standardizing on a small operator core such as ONNX's 203 operators eases hardware bring-up yet lags newly invented research operations. Pick one prompt and write two sentences defending a stance.
