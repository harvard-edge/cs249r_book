\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.25cm}
    \item Eager code shows the framework one operation at a time: easy to debug, about 15\,\textmu s of host time each.
    \item A captured graph lets the compiler fuse and plan; compiling pays only after enough runs.
    \item Reverse mode gets every gradient in one pass by keeping forward values, and those set training memory.
    \item The host link is 52$\times$ slower than HBM: place data once, pin it, overlap the copies.
  \end{itemize}
  \note{[1.5 min] One line per section. Ask students to star the line they could least explain tomorrow and reread that section of the chapter first. FLEX: [CORE].}
\end{frame}

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.4cm}
    \item Should frameworks compile by default? Who should pay for the compile step?
    \item Checkpointing trades arithmetic for memory. When would you never use it?
    \item Operator coverage often decides whether a model runs on new hardware. Should the field standardize on a small operator core?
  \end{itemize}
  \note{[1 min] [OPTIONAL] No single answer. The first weighs researcher time against production throughput; PyTorch stayed eager by default and made compilation opt-in. The second: when compute, not memory, is the binding constraint, recomputation only adds time. The third: a small core like ONNX's 203 operators makes new hardware easier to support but can lag the operators researchers invent. Ask students to pick one and write two sentences. FLEX: [OPTIONAL].}
\end{frame}
