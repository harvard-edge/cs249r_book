\begin{frame}{A systolic array reuses each operand across a whole row}
  \begin{columns}[c]
    \begin{column}{0.55\textwidth}

    \end{column}

      \normalsize
      \only<1|handout:0>{\textbf{Weights} stay in the cells.}%
      \only<2|handout:0>{\textbf{Activations} enter at the edge and move right, one cell per cycle.}%
      \only<3-|handout:1>{\textbf{Weights} stay in the cells.\\[0.2cm]
        \textbf{\textcolor{BlueLine}{Activations}} move right.\\[0.2cm]
        \textbf{\textcolor{GreenLine}{Partial sums}} move down.\\[0.4cm]
        {\small $\val{tpu4_dim}{\times}\val{tpu4_dim}$ cells: \val{tpu4_macs} MACs per cycle (TPU v4)}}
    \end{column}
  \end{columns}
  \mlsyscredit{After Hardware Acceleration, figure 6 and \S11.4.4; Kung 1982; Jouppi et al. 2023.}
  \note{[2.5 min] A systolic array is a grid of multiply-add cells that pass data to their neighbors on every clock tick; this one is weight stationary, the design inside the TPU. Step 1: each cell holds one weight and does one multiply-add per cycle. Step 2: activations enter at the left edge and pass from cell to neighbor; each one loaded once is used by every cell in its row. Step 3: partial sums flow down each column, adding one product per cell, and leave at the bottom as outputs. No value returns to a register file or memory between cells; a neighbor wire replaces a memory read. A \val{tpu4_dim} by \val{tpu4_dim} array does \val{tpu4_macs} multiply-accumulates (MACs) per cycle; the first TPU's array was \val{tpu_dim} by \val{tpu_dim}. ENGAGE: in an N by N array, how many times is each activation used after one load? Expected: N times. WARN: the diagram omits timing: each row's inputs enter one cycle later than the row above, so the array takes a few cycles to fill and drain; the next lecture runs this array cycle by cycle, with its fill and drain. FLEX: [CORE].}
\end{frame}

\mlsysdivider{Which ceiling binds: arithmetic or bytes?}{Hardware Acceleration, \S11.6}
\section{Roofline}

\mlsysnote{[2 min] The roofline (Williams et al. 2009). Arithmetic intensity I is operations per byte moved from memory. Attainable rate is the smaller of two ceilings: the chip's peak, or bandwidth times intensity. The ridge point is where they meet, peak divided by bandwidth. Below the ridge a kernel waits for bytes, and only fewer bytes or more reuse help; above it, only a faster datapath helps. LINK: Lecture 2 drew this for the A100: \val{a100_fp16} TFLOP/s over \val{a100_bw} TB/s, a ridge of \val{a100_ridge} FLOP/byte. Today puts numbers on both axes for the H100. WARN: the roofline gives an upper bound; a kernel below both lines may be limited by something else, such as launch overhead, which profiling finds (Lecture 12). FLEX: [CORE].}
\mlsysfocus{The Roofline}{%
  $\displaystyle \text{Attainable} = \min\left(\Rpeak,\ \text{BW} \times I\right)$\\[0.6cm]
  $\displaystyle I_{\text{ridge}} = \frac{\Rpeak}{\text{BW}}$\\[0.5cm]
  {\small\textcolor{white!75}{One ridge per number format: each path has its own $\Rpeak$.}}%
}
