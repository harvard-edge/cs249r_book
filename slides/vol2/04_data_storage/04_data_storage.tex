\begin{frame}{Required bandwidth is consumers $\times$ batch bytes $\div$ compute time}
  \centering
  \vspace{0.3cm}
  {\Large $\text{BW}_{\text{required}} =
    \underbrace{N_{\text{GPU}}}_{\text{\normalsize\uncover<2->{consumers}}} \times
    \underbrace{\eta_{\text{target}}}_{\text{\normalsize\uncover<3->{busy fraction}}} \times
    \dfrac{\overbrace{D_{\text{vol,batch}}}^{\text{\normalsize\uncover<4->{bytes per batch}}}}
          {\underbrace{T_{\text{iteration}}}_{\text{\normalsize\uncover<4->{compute time}}}}$}\\[0.6cm]
  {\normalsize\uncover<5->{Delivered rate $=$ the slowest stage: read, network, decode, host copy, PCIe.}}
  \mlsyscredit{Data Storage, \S4.4, equations 2 and 3.}
  \note{[2.5 min] [CORE] The input delivery budget. Step 1: the equation. Step 2: $N_{\text{GPU}}$ counts accelerators that consume distinct batches; GPUs that split one batch share one read. Step 3: $\eta_{\text{target}}$ is the fraction of wall-clock time spent computing, typically 0.8 to 0.95; it is an active-time fraction and differs from model FLOPs utilization. Step 4: bytes in one local batch over its uninterrupted compute time. A faster accelerator shrinks the denominator, which is exactly why it raises demand. Step 5: every stage between storage and HBM must sustain this rate, measured in the same output-equivalent bytes, because the delivered rate is the minimum over stages. Compression may speed the read and slow the decode. ENGAGE: double the GPUs at the same batch and step time; what happens to the requirement? (Expected: it doubles.) WARN: if the measured iteration time already includes stalls, multiplying by $\eta$ again counts the slowdown twice.}
\end{frame}

\begin{frame}{Overlap turns read plus compute into the longer of the two}
  \centering
  \mlsyssteps[width=\textwidth,height=5.0cm,keepaspectratio]{stall_step}{2}\\[0.05cm]
  {\small Data stall $= (T_{\text{step}} - T_{\text{compute}}) / T_{\text{step}}$: the share of each step spent waiting for input.}
  \mlsyscredit{Data Storage, Napkin Math 4.5 and equation 4.}
  \note{[2 min] [CORE] The data stall ratio. Compute takes 200 ms per batch; storage takes 250 ms to deliver one. Step 1: without overlap, the GPU waits for each read, then computes, 450 ms per step, 250 of them stalled, 55.6 percent. Step 2: overlapped, the loader reads batch $i+1$ while the GPU computes batch $i$, so a step costs the longer of the two, 250 ms, and the stall falls to 50 of 250 ms, 20 percent. Overlap cannot go further, because delivery is slower than compute on every step, so the only fixes are a faster stage or more parallel input streams. ENGAGE: a profiler shows the GPU idle 20 percent of the time; is storage to blame? (Expected: only if that idle time is spent waiting on the input queue; the same gap can be collectives or barriers, so measure them separately.) LINK: the Fleet Law has no input term; a stall like this is idle compute added on top of the communication and synchronization terms.}
\end{frame}

\begin{frame}{An open goes to one metadata server; bytes come from many}
  \centering
  \safeimg[width=0.97\textwidth,height=5.1cm,keepaspectratio]{pfs.pdf}\\[0.1cm]

  \note{[2 min] [CORE] A parallel file system such as Lustre splits two jobs. Step 1 of a read: the client asks the metadata server (MDS) where the file lives, and opens, stats, and locks go there too. Step 2: the client reads the file's stripes directly from many object storage servers (OSS) in parallel. A hundred OSS at 10 GB/s each give 1 TB/s, and adding servers adds bandwidth. The metadata server does not grow with them. It serves a few hundred thousand operations per second. The command at the bottom is real Lustre. It stripes every new file in a directory over 100 storage targets in 4 MB pieces, so one large shard can draw on many servers. ENGAGE: which resource does a dataset of one file per image stress?   \note{[2 min] [CORE] The checkpoint write path starts with its size. Mixed-precision Adam keeps 16-bit (FP16) weights, a 32-bit (FP32) master copy, and two FP32 Adam moments: 2 + 4 + 8 = 14 bytes per parameter, 2,450 GB for 175 billion parameters. Gradients, 2 more bytes, are left out because the restored job recomputes them; the scheduler, random-number, and data-loader state add little but are required to continue exactly. The rule that keeps the save short is to write each unique byte once. The running layout shards optimizer state across nodes, a technique called sharded data parallelism that Lecture 6 develops, so each of the 256 nodes saves about 9.6 GB. The code is real PyTorch Distributed Checkpoint: with sharded state, each rank writes only the shards it owns, and one rank writes a metadata file that lists them all. \end{frame}

  \note{[2 min] [OPTIONAL] The checkpoint storm: a burst of synchronized writes when every node saves at once. If every replica writes its own copy, the shared tier absorbs about 1,004 TB at 100 GB/s in 10,035 seconds, 167 minutes of stalled training, every save. \begin{frame}{The pause ends at $t_1$; the checkpoint is restorable at $t_3$}
  \centering
  \mlsyssteps[width=\textwidth,height=5.7cm,keepaspectratio]{staging_step}{3}
  \mlsyscredit{Data Storage, \S4.6 and figure 8 (redrawn at slide size). GitLab 2017: War Story 4.1.}
  \note{[3 min] [CORE] The checkpoint write path as four lanes in time. Step 1: at $t_0$ training pauses and each node writes its shard to local NVMe; at $t_1$ it resumes on live state. Step 2: between $t_1$ and $t_2$ the shards copy to the file system in the background. Until each copy lands, a node failure destroys that node's new shard, so the previous checkpoint must be kept. Step 3: the coordinator waits for every rank's shard, verifies checksums, and publishes a manifest, the list of the complete shard set, last, with an atomic create or rename. Only at $t_3$ is the new generation restorable. Lecture 7 owns those commit rules and the save interval; this lecture owns the path and the pause. ENGAGE: what can a crash between $t_2$ and $t_3$ leave behind? (Expected: garbage to clean up; a half checkpoint never looks valid.) WARN: GitLab in 2017 lost six hours of production writes because none of five backup paths could be restored; a checkpoint counts only if restores are tested. Land the segment: write each byte once, pause only for the local write, and declare a save done only when its manifest is published.}
\end{frame}

\begin{frame}{At a commit boundary, a replay is safe only with keyed writes}

Saving: each node writes 9.6 GB of unique bytes to local flash in 0.34 seconds, the copy drains in the background, and the generation counts only when its manifest is published. In Fleet Law terms, storage succeeds when it adds no exposed time: prefetch keeps the input wait hidden, and staging shrinks the synchronization pause to the local write. ENGAGE: which number would you watch first on a dashboard for this job? (Expected: the save pause and its drain time, then the input stall ratio.)}
\end{frame}

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.18cm}
    \item Tiers quote bandwidth at different scopes; 5\% misses at 100$\times$ cost 83\% of the rate.
    \item Required bandwidth is consumers $\times$ batch bytes $\div$ compute time, at the slowest stage.
    \item Shards amortize file opens; the metadata server binds before the bytes do.
    \item A checkpoint writes each byte once, pauses for the local write, and counts at its manifest.
    \item Versioned, keyed writes make replay safe; price placement by the whole delivery bill.
  \end{itemize}
  \note{[1 min] [CORE] One line per segment. Ask students to star the one they would have gotten wrong before today; most star the second or the third.}
\end{frame}

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.35cm}
    \item Generated data keeps growing as human text runs short. How much provenance should a fleet store per sample, and who pays for it?
    \item Memory pooled over CXL could add a tier between DRAM and NVMe. Which of today's buffers would move there first?
    \item A file system shared by ten jobs gives each a tenth. Should checkpoints get priority over input reads, or the reverse?
  \end{itemize}
