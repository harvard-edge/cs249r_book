\section{Contract}

\begin{frame}{A request spends a first-token budget and a cadence budget}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=3.9cm,keepaspectratio]{lifecycle_step}{3}\\[0.05cm]
  {\small TTFT: time to first token.\quad TPOT: time per output token.\quad TBT: one gap between tokens.}\\[0.1cm]
  {\footnotesize\textcolor{midgray}{Real log, Azure:}\enspace\texttt{TIMESTAMP,ContextTokens,GeneratedTokens}\\
  \texttt{2023-11-16 18:15:46.6805900,374,44}}
  \mlsyscredit{Serving at Scale, \S10.1 (figure 1) and \S10.2. Log: Azure LLM inference trace 2023 (Patel et al., ISCA 2024), CC BY. Explore: Inference Lifecycle (mlsysbook.ai).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Trace one streamed request across three steps. Step 1: routing, queueing, and prefill (one forward pass over the prompt that populates the KV cache) produce the first token; that total delay is time to first token (TTFT), so queue wait directly spends TTFT. Step 2: decode emits one token per iteration; time per output token (TPOT) is the mean interval between tokens, spent by other concurrent requests sharing the step. Step 3: time between tokens (TBT) measures each individual gap, catching a single visible stall that a healthy mean TPOT hides. The real Azure log row at the bottom shows arrival time, 374 prompt tokens (setting prefill work and TTFT), and 44 generated tokens (setting decode slot residency).

  \notecue{Watch for}{A faster decode kernel shrinks neither queueing delay before prefill nor TBT stalls caused when another request's long prefill enters the batch.}

  \notecue{Next}{A peer-instruction Vote tests why raw completed throughput misranks serving configurations when deadlines matter.}
}
\end{frame}

\begin{frame}{A 100 ms target leaves 30 ms outside the model}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.2cm,keepaspectratio]{tax_step}{2}\\[0.2cm]
  {\normalsize $T_{\text{request}} = T_{\text{model}} + T_{\text{network}} + T_{\text{serialize}} + T_{\text{coordinate}} + T_{\text{queue}}$}
  \mlsyscredit{Serving at Scale, \S10.3.2 and equation 1 (illustrative budget).}
  \note{%
  \mlsysnotemeta{1.5 min}{Core}%
  Step 1 presents the chapter's illustrative interactive budget: a 100 ms end-to-end target with a 70 ms model forward pass leaves only 30 ms for everything else, called the serving tax. Step 2 unpacks the equation: four sequential network hops at 50 to 500 $\mu$s each cost 0.2 to 2 ms (Lecture 3's $\alpha + \text{bytes}/\beta$), serialization, routing, and multi-backend fan-in add further overhead, and queueing grows rapidly as utilization approaches capacity. Adding replicas shrinks queueing, whereas co-locating adjacent services shrinks network hops.

  \notecue{Watch for}{Microbenchmarks of model kernels measure only $T_{\text{model}}$; users experience the full sum along the request path.}

  \notecue{Next}{Real InferenceX benchmark data now shows how sharply tightening the per-user speed contract reduces per-GPU output.}
}

\section{Batching}

\begin{frame}{Throughput saturates past a knee near $t_0 / t_{\text{req}}$}
  \begin{columns}[c]
    \begin{column}{0.36\textwidth}
      \small Batch service time\\[0.05cm]
      $\;S(B) = t_0 + B\,t_{\text{req}}$\\[0.2cm]
      Throughput\\[0.05cm]
      $\;X(B) = \dfrac{B}{t_0 + B\,t_{\text{req}}}$\\[0.25cm]
      {\footnotesize $t_0$: paid once per batch (weight read, launch).\\ $t_{\text{req}}$: added per request.}
    \end{column}
    \begin{column}{0.62\textwidth}
      \centering\safeimg[width=\textwidth,height=4.6cm,keepaspectratio]{knee.pdf}
    \end{column}
  \end{columns}
  \mlsyscredit{Serving at Scale, \S10.6.2 and Napkin Math 10.2 (assumed service times).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Walk through the linear batch service model: each batch pays a fixed cost $t_0$ once (weight reads and kernel launches) plus $t_{\text{req}}$ per request, giving throughput $X(B) = B / (t_0 + B t_{\text{req}})$. Throughput climbs steeply while $t_0$ dominates and saturates toward $1 / t_{\text{req}}$. The knee at $B = t_0 / t_{\text{req}}$ marks half peak throughput where fixed and variable costs match: vision (2 ms fixed, 1 ms per image) hits its knee at $B = 2$, whereas LLM decode (about 40 ms fixed, 41.8 ms computed to stream 140 GB across one H100's 3.35 TB/s, plus 0.5 ms per sequence for KV reads) hits its knee near 80. Spreading weights across 8 GPUs divides both terms by 8, leaving the knee unchanged.

  \notecue{Watch for}{The knee is only a candidate operating point; real batches also wait to form and must fit inside the latency budget remaining after queueing.}

  \notecue{Next}{An optional measured chart verifies this batch-size versus per-user speed curve on B200 hardware.}
}
\end{frame}

\begin{frame}{Iteration-level batching refills a slot when a request ends}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.8cm,keepaspectratio]{cb_step}{3}\\[0.08cm]
  {\small Measured: vLLM, 2 to 4$\times$ the throughput of FasterTransformer and Orca at similar latency.}

  \mlsysnotemeta{2 min}{Core}%

Step 1: fixed batching holds every slot until R2 ends at iteration 200, idling 300 of 800 slot-iterations (37.5\%). Step 2: iteration-level (continuous) batching rebuilds the batch every iteration, so when R1 finishes at iteration 50, R5 immediately takes slot 1 while R2, R3, and R4 continue decoding. \begin{frame}{Speculative decoding trades idle compute for shorter mean TPOT}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.7cm,keepaspectratio]{spec_step}{3}\\[0.08cm]
  {\footnotesize $E = 3.52$ tokens/round ($K = 5$, $p = 0.78$): $53.6 / 3.52 = 15.2$ ms mean TPOT, $53.6$ ms burst TBT.}
  \mlsyscredit{Serving at Scale, \S10.15.1 and equation 6 (constructed budget). Explore: Speculative Decoding (mlsysbook.ai).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Trace how speculative decoding bypasses the low-batch weight-bandwidth ceiling in three steps. Step 1: a lightweight draft model generates $K = 5$ candidate tokens serially in 4.0 ms total. Step 2: the 70B target model verifies all 5 positions in one parallel forward pass (49.6 ms), reading weights once instead of five times (248 ms serially) and spending decode's unused arithmetic. Step 3: rejection sampling accepts the matching prefix (here 3 tokens), draws one exact bonus token at the first mismatch from the target distribution, and discards the remaining drafts, guaranteeing mathematically unchanged output quality. At acceptance probability $p = 0.78$, each 53.6 ms round yields $E = 3.52$ tokens, giving 15.2 ms mean TPOT (3.26$\times$ faster) alongside a 53.6 ms burst TBT.

  \notecue{Watch for}{Speculative gains shrink as batch size grows because larger batches already consume the spare arithmetic that parallel verification relies on.}

}

\begin{frame}{Two random probes halve the busiest replica's load}
  \centering
  \begin{columns}[c]
  \begin{column}{0.63\textwidth}

  \end{column}
  \begin{column}{0.35\textwidth}
    \centering\mlsysphoto[width=\textwidth,height=1.9cm,keepaspectratio]{datacenters-ashburn-aerial.jpg}\\[0.02cm]
    {\scriptsize Data centers in Ashburn, Virginia (US-East)}\\[0.2cm]
    \raggedright\footnotesize Random: $\Theta(\log n / \log\log n)$\\ Two probes: $\Theta(\log\log n)$\\[0.15cm]
    LLM signal: active tokens, remaining decode, KV pressure
  \end{column}
  \end{columns}
  \mlsyscredit{Simulated here (balls into bins). Serving at Scale, \S10.11.2 and \S10.11.3; Mitzenmacher 2001. Photo: Theodore Christopher, CC0, Wikimedia Commons.}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  In a large serving region like Ashburn (US-East), a router distributes traffic across thousands of replicas without polling every one. In the static balls-into-bins model (Mitzenmacher 2001), pure random placement leaves the busiest of 100,000 replicas with 7.6 jobs in simulation ($\Theta(\log n / \log\log n)$), whereas probing two random replicas and choosing the lighter cuts max load in half to 3.6 ($\Theta(\log\log n)$). For LLMs, request count is too coarse because remaining decode length varies fiftyfold; routers instead compare active tokens, estimated remaining decode, and KV pressure, while respecting KV prefix affinity on multi-turn chats and verifying admission atomically against stale probes. Heterogeneous fleets weight probes by capacity (10 H100s at 1,000 and 20 A100s at 600 req/s balance at 68.2\% under 15,000 req/s).

  \notecue{Watch for}{The two-choices bound models static placement and does not by itself bound p99 tail latency.}

  \notecue{Next}{A Diagnose activity shows how fan-out turns modest per-shard tail latency into frequent request-level slowdowns.}
}
\end{frame}

\begin{frame}{Diagnose: how often is a 100-leaf request slow?}
  \mlsysactivity{Diagnose}{2.5 min}
  \begin{columns}[c]

        A ranking request fans out to 100 shards and waits for all. Each shard meets its own p99.
      \end{mlsyscard}

      Leaves at p99.99: 1\%\\[0.1cm]
      {\footnotesize Archetype B: $10^{7}$ QPS $\times 10^{-4}$ = 1,000 slow/s}}
    \end{column}
    \begin{column}{0.64\textwidth}
      \centering
      \only<1|handout:0>{}%
      \only<2-|handout:1>{\safeimg[width=\textwidth,height=4.6cm,keepaspectratio]{fanout.pdf}}
    \end{column}
  \end{columns}
  \mlsyscredit{Serving at Scale, \S10.11.1 and Lighthouse 10.2 (independence assumed).}
  \note{%
  \mlsysnotemeta{2.5 min}{Core}%
  Give students one minute to calculate how often a 100-shard ranking request exceeds shard p99 latency before revealing step 2. Because the parent waits for its slowest leaf, the request is slow if any of 100 independent leaves hits its 1\% tail: $1 - 0.99^{100} = 63\%$. Holding the parent request at p99 requires each leaf to stay near p99.99 (0.01\% slow). At Archetype B's scale of $10^7$ queries per second, a one-in-10,000 event still fires 1,000 times per second. Engineering levers attack different terms: fewer shards lower $N$, queue-aware routing and isolation lower leaf tail rate $q$, deadlines with partial results cap damage, and hedged requests (Lecture 4) trade duplicate work for lower $q$.

  \notecue{Check}{Ask students for the slow-request probability. Answering 1\% wrongly averages the leaves instead of taking their maximum; waiting for all 100 compounds tail probability to 63\%.}

  \notecue{Watch for}{Independence is optimistic; shared switches or hot keys slow many leaves simultaneously.}

\begin{frame}{A slow replica spreads overload through retries}
  \centering
  \mlsyssteps[width=0.88\textwidth,height=4.1cm,keepaspectratio]{breaker_step}{2}\\[0.15cm]
  {\small Backpressure (503) turns routing into admission control when every replica is degraded.\\
  Deadlines travel with each request; canceled work leaves the batch.}
  \mlsyscredit{Serving at Scale, \S10.11.10 (illustrative 50 ms to 500 ms slowdown); Nygard 2007.}
  \note{%
  \mlsysnotemeta{1.5 min}{Optional}%
  In the chapter's illustration, one replica slowing from 50 to 500 ms builds a queue, triggers client timeouts and retries, and pushes overload onto healthy neighbors. Step 1: a circuit breaker starts closed, then trips open once errors or latencies breach a threshold so requests fail fast or reroute within a retry budget. Step 2: after a cooldown interval, a half-open state sends probes and closes again upon recovery. Opening a breaker only shifts load without adding capacity; when every replica is saturated, HTTP 503 backpressure converts routing into edge admission control alongside Lecture 7's graceful degradation fallbacks. Deadlines must travel with each request so canceled work leaves continuous batches immediately instead of holding zombie KV pages.

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.18cm}
    \item Capacity is SLO goodput: completed requests that meet TTFT and TPOT for a fixed mix.
    \item Batching trades waiting for reuse up to a knee; iteration-level admission keeps slots full.
    \item Free HBM over per-request KV state admits 12 long requests or 1,397 chats.
    \item Chunk or split the phases, and shard only as far as the collectives allow.
    \item A fleet routes on work, budgets the fan-out tail, and keeps ready headroom.
  \end{itemize}
  \note{%
  \mlsysnotemeta{1 min}{Core}%
  Review the five takeaways, one per segment: define capacity as SLO goodput, batch to the knee with iteration-level refill, budget KV memory explicitly (12 long vs 1,397 chat), manage prefill-decode interference and NVLink sharding, and route on work with tail headroom. If time is tight, emphasize the first and third items.

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.3cm}
    \item Reasoning models choose how many tokens to spend. Who should set the per-request budget, the user, the provider, or the model?
    \item Split pools win at some per-user targets and lose at others. Should a fleet switch between layouts as load changes?
    \item Serving cost recurs for every request. When does a cheaper, smaller model that misses some answers serve users better?
