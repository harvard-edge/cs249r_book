\section{Contract}

\begin{frame}{A request spends a first-token budget and a cadence budget}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=3.9cm,keepaspectratio]{lifecycle_step}{3}\\[0.05cm]
  {\small TTFT: time to first token.\quad TPOT: time per output token.\quad TBT: one gap between tokens.}\\[0.1cm]
  {\footnotesize\textcolor{midgray}{Real log, Azure:}\enspace\texttt{TIMESTAMP,ContextTokens,GeneratedTokens}\\
  \texttt{2023-11-16 18:15:46.6805900,374,44}}
  \mlsyscredit{Serving at Scale, \S10.1 (figure 1) and \S10.2. Log: Azure LLM inference trace 2023 (Patel et al., ISCA 2024), CC BY. Explore: Inference Lifecycle (mlsysbook.ai).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Because a user judges both when an answer starts and how smoothly it streams, one request spends separate first-token and cadence budgets. First, routing, queueing, and prefill produce the first token, where prefill runs one forward pass over the prompt to populate the KV cache of stored key and value vectors. That total wait is time to first token (TTFT), so queueing spends TTFT directly. Next, decode emits one token per iteration. Time per output token (TPOT) is the mean gap between tokens, lengthened by concurrent requests sharing each step, whereas time between tokens (TBT) measures each individual gap and catches a visible stall that a healthy mean TPOT hides. The Azure log row records an arrival timestamp, 374 prompt tokens setting prefill work and TTFT, and 44 generated tokens setting how long the request holds a decode slot.

  \notecue{Watch for}{A faster decode kernel shrinks neither queueing delay before prefill nor TBT stalls caused when another request's long prefill enters the batch.}

  \notecue{Next}{Next, compare two serving configurations to see why raw completed throughput misranks systems when deadlines matter.}
}
\end{frame}

\begin{frame}{A 100 ms target leaves 30 ms outside the model}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.2cm,keepaspectratio]{tax_step}{2}\\[0.2cm]
  {\normalsize $T_{\text{request}} = T_{\text{model}} + T_{\text{network}} + T_{\text{serialize}} + T_{\text{coordinate}} + T_{\text{queue}}$}
  \mlsyscredit{Serving at Scale, \S10.3.2 and equation 1 (illustrative budget).}
  \note{%
  \mlsysnotemeta{1.5 min}{Core}%
  Meeting an SLO requires budgeting the full request path rather than model execution alone. Inside an illustrative 100 ms end-to-end target, a 70 ms model forward pass leaves only 30 ms for everything else, called the serving tax, split into four non-model terms. Four sequential network hops at 50 to 500 $\mu$s each cost 0.2 to 2 ms under Lecture 3's $\alpha$-$\beta$ model ($\alpha + \text{bytes}/\beta$). Serialization (converting structured payloads into wire format and back), routing, and collecting replies across multiple backends add further overhead, and queueing delay grows steeply as utilization approaches capacity. Adding replicas shrinks queueing, whereas colocating adjacent services on one host removes network hops.

  \notecue{Watch for}{Microbenchmarks of model kernels measure only $T_{\text{model}}$, whereas users experience the full sum along the request path.}

  \notecue{Next}{Next, measured InferenceX benchmark data shows how sharply tightening the per-user speed contract reduces per-GPU output.}
}
\end{frame}

\begin{frame}{Throughput saturates past a knee near $t_0 / t_{\text{req}}$}
  \begin{columns}[c]
    \begin{column}{0.36\textwidth}
      \small Batch service time\\[0.05cm]
      $\;S(B) = t_0 + B\,t_{\text{req}}$\\[0.2cm]
      Throughput\\[0.05cm]
      $\;X(B) = \dfrac{B}{t_0 + B\,t_{\text{req}}}$\\[0.25cm]
      {\footnotesize $t_0$: paid once per batch (weight read, launch).\\ $t_{\text{req}}$: added per request.}
    \end{column}
    \begin{column}{0.62\textwidth}
      \centering\safeimg[width=\textwidth,height=4.6cm,keepaspectratio]{knee.pdf}
    \end{column}
  \end{columns}
  \mlsyscredit{Serving at Scale, \S10.6.2 and Napkin Math 10.2 (assumed service times).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  Grouping requests amortizes one-time step costs across more outputs, yet larger batches eventually stop paying off. In this linear batch service model, each batch pays a fixed cost $t_0$ once for weight reads and kernel launches, plus $t_{\text{req}}$ per request. Throughput is $X(B) = B / (t_0 + B t_{\text{req}})$, climbing steeply while $t_0$ dominates and saturating toward $1 / t_{\text{req}}$. The knee at $B = t_0 / t_{\text{req}}$ marks half peak throughput, where fixed and variable costs match. A vision model with 2 ms fixed cost and 1 ms per image hits its knee at $B = 2$. For LLM decode, streaming 140 GB across one H100's 3.35 TB/s memory takes 41.8 ms, or about 40 ms fixed. Adding 0.5 ms per sequence for KV reads puts its knee near 80. Spreading weights across 8 GPUs divides both terms by 8, leaving the knee unchanged.

  \notecue{Watch for}{The knee is only a candidate operating point. Production batches also wait to form and must fit inside the latency budget remaining after queueing.}

  \notecue{Next}{Next, measured B200 data tests how rising concurrency trades per-GPU output against per-user speed.}
}

\begin{frame}{Iteration-level batching refills a slot when a request ends}

  \mlsysnotemeta{2 min}{Core}%

Meta's Llama 3.1 70B \texttt{config.json} specifies 80 layers, 64 query attention heads sharing 8 KV heads, head width $8192/64 = 128$, and a maximum context length (\texttt{max\_position\_embeddings}) of 131,072 tokens. \begin{frame}{A whole prefill lands in every active stream's token gap}

  Whether phases share a pool or split, Lecture 1's Fleet Law sets how many GPUs one replica spans, dividing compute by $N$ while adding collectives and synchronization. In the chapter's long-prompt prefill reference, one serial layer takes 30 ms (12 ms attention, 18 ms feed-forward). Applying 8-way tensor parallelism (Lecture 6) cuts compute to 3.75 ms and adds two 0.3 ms AllReduce collectives summing partial outputs, giving 4.35 ms per layer. Across 80 layers, latency drops from 2,400 ms to 348 ms, a 6.9$\times$ speedup. Weights set the minimum shard floor (140 GB requires at least two 80 GiB, or 85.9 decimal GB, GPUs), whereas the SLO sets the serving degree. During decode, small layer compute lets collective latency dominate.

  \notecue{Watch for}{Tensor parallelism runs 160 collectives per token on an 80-layer model and must stay inside one NVLink domain, because slower cross-node links multiply latency 160 times. MoE expert parallelism adds AllToAll collectives (Lecture 5; \S10.10.4).}

  \notecue{Next}{Next, inspect a vLLM launch command to see these memory and scheduling levers as engine flags.}
}

\begin{frame}{Speculative decoding trades idle compute for shorter mean TPOT}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.7cm,keepaspectratio]{spec_step}{3}\\[0.08cm]
  {\footnotesize $E = 3.52$ tokens/round ($K = 5$, $p = 0.78$): $53.6 / 3.52 = 15.2$ ms mean TPOT, $53.6$ ms burst TBT.}
  \mlsyscredit{Serving at Scale, \S10.15.1 and equation 6 (constructed budget). Explore: Speculative Decoding (mlsysbook.ai).}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  How does speculative decoding cut mean TPOT without altering output quality? It bypasses the low-batch weight-bandwidth ceiling in three stages. First, a lightweight draft model generates $K = 5$ candidate tokens serially in 4.0 ms. Second, the 70B target model verifies all 5 positions in one 49.6 ms parallel pass, reading weights once instead of five times (248 ms serially) using decode's spare arithmetic. Third, rejection sampling accepts the matching prefix (here, 3 tokens), draws one exact bonus token at the first mismatch from the target distribution, and discards remaining drafts, leaving output quality unchanged. At acceptance probability $p = 0.78$, each 53.6 ms round yields $E = 3.52$ tokens, giving 15.2 ms mean TPOT (3.26$\times$ faster) alongside a 53.6 ms burst TBT. Together, phase handling, sharding, fused kernels, and speculation bound one replica's token cadence.

  \notecue{Watch for}{Speculative gains shrink as batch size grows because larger batches already consume the spare arithmetic that parallel verification relies on.}

  \notecue{Next}{Section 5 leaves the single replica to examine fleet-wide tail control.}
}
\end{frame}

  \end{column}

  \mlsyscredit{Simulated here (balls into bins). Serving at Scale, \S10.11.2 and \S10.11.3; Mitzenmacher 2001. Photo: Theodore Christopher, CC0, Wikimedia Commons.}
  \note{%
  \mlsysnotemeta{2 min}{Core}%
  In a large region such as Ashburn (US-East), a router spreads traffic across thousands of replicas without polling every one. Mitzenmacher's load-balancing theorem (``The Power of Two Choices,'' IEEE TPDS 2001) analyzes a static balls-into-bins model placing $n$ equal-size jobs sequentially into $n$ empty bins without departures. Random placement leaves the busiest of 100,000 simulated replicas with 7.6 jobs ($\Theta(\log n / \log\log n)$), whereas probing two random replicas and picking the lighter halves that peak to 3.6 jobs ($\Theta(\log\log n)$). Because remaining LLM decode varies fiftyfold, routers compare active tokens, estimated remaining decode, and KV pressure, preserve KV prefix affinity for multi-turn chats, and admit atomically against stale probes. Mixed fleets weight probes by capacity; at 15,000 req/s, 10 H100s at 1,000 req/s and 20 A100s at 600 req/s balance at 68.2\% utilization.

  \notecue{Watch for}{The two-choices bound models static placement and does not by itself bound p99 tail latency.}

  Balancing replicas is not enough when one request fans out across many shards, echoing Lecture 4's storage fan-out tail. A ranking request queries $N = 100$ independent shards and waits for all, with each meeting p99 ($q = 1\%$ slow). Calculate how often the parent request is slow.

  \notecue{Check}{The answer is 63\%. Across $N$ leaves with tail rate $q$, parent tail probability is $1 - (1 - q)^N$, so 100 leaves compound 1\% to $1 - 0.99^{100} = 63\%$. At Archetype B's $10^7$ queries per second, that one-in-10,000 event fires 1,000 times per second. \begin{frame}{A slow replica spreads overload through retries}
  \centering
  \mlsyssteps[width=0.88\textwidth,height=4.1cm,keepaspectratio]{breaker_step}{2}\\[0.15cm]
  {\small Backpressure (503) turns routing into admission control when every replica is degraded.\\
  Deadlines travel with each request; canceled work leaves the batch.}
  \mlsyscredit{Serving at Scale, \S10.11.10 (illustrative 50 ms to 500 ms slowdown); Nygard 2007.}
  \note{%
  \mlsysnotemeta{1.5 min}{Optional}%
  When a burst or fault outpaces ready headroom, retries can turn one slow replica into a fleet-wide cascade. In the chapter's illustration, one replica slowing from 50 to 500 ms builds a queue, triggers client timeouts and retries, and pushes overload onto healthy neighbors. A circuit breaker begins closed and trips open once errors or latencies cross a threshold, letting requests fail fast or reroute within a retry budget. After a cooldown interval, a half-open state sends probes and closes again once the replica recovers. Opening a breaker shifts load without adding capacity. When every replica is saturated, HTTP 503 (Service Unavailable) overload backpressure turns routing into edge admission control alongside Lecture 7's graceful degradation fallbacks. Deadlines must travel with each request so canceled work leaves continuous batches immediately instead of holding abandoned KV pages.

\begin{frame}{Takeaways}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.18cm}
    \item Capacity is SLO goodput: completed requests that meet TTFT and TPOT for a fixed mix.
    \item Batching trades waiting for reuse up to a knee; iteration-level admission keeps slots full.
    \item Free HBM over per-request KV state admits 12 long requests or 1,397 chats.
    \item Chunk or split the phases, and shard only as far as the collectives allow.
    \item A fleet routes on work, budgets the fan-out tail, and keeps ready headroom.
  \end{itemize}
  \note{%
  \mlsysnotemeta{1 min}{Core}%
  These five takeaways summarize one rule per segment. Define capacity as SLO goodput, batch to the knee with iteration-level refill, and budget KV memory explicitly (12 long requests versus 1,397 chats). Manage prefill-decode interference alongside NVLink sharding, and route on remaining work while keeping tail headroom.
