    Before pricing any schedule, we must see which traffic each way of splitting a model creates, previewing the parallelism strategies of Lecture 6. Tensor parallelism splits weight matrices inside layers, pipeline parallelism hands small activations across layer stages on the critical path where latency dominates, and expert or embedding parallelism routes Mixture-of-Experts (MoE) tokens or recommender lookups with AllToAll, bounded by routing skew and fabric bisection bandwidth, the capacity across the network's narrowest cut (Lecture 3).

\begin{frame}{A collective names what each rank holds afterward}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=5.6cm,keepaspectratio]{contracts_step}{4}
  \mlsyscredit{Collective Communication, \S5.4 and figure 2. Ranks R0 to R3; color marks the source rank; numbers in AllToAll cells are chunk indices.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    Once a split selects a primitive, that collective specifies a mathematical outcome across participating ranks R0 to R3, independent of the wire schedule used to achieve it. In AllReduce, every rank contributes a full tensor and receives the identical global sum. In AllGather, each rank starts with one shard and finishes holding all shards. In ReduceScatter, every rank contributes a full tensor and rank $i$ retains only the $i$-th summed shard; notice that running ReduceScatter followed by AllGather equals AllReduce. Finally, AllToAll performs a distributed transpose in which rank $i$ sends chunk $j$ to rank $j$. Broadcast, where one rank sends to all, and Reduce, where all ranks sum to one root, round out the core six primitives.

    \notecue{Watch for}{A collective defines a data-dependency contract rather than a strict barrier. Ranks can enter asynchronously, and a late rank stalls only the ranks waiting on its chunks.}

    \notecue{Next}{Next, an optional slide shows why sharded data parallelism decomposes AllReduce into separate AllGather and ReduceScatter calls.}
  }
\end{frame}

  \note{%
    \mlsysnotemeta{2 min}{Optional}%
    That ReduceScatter-plus-AllGather decomposition is how sharded data parallelism, such as FSDP and ZeRO-3 (PyTorch's \texttt{ShardingStrategy} enumeration), stores only $1/N$ of each layer's weights per rank. It splits AllReduce across the training step, running AllGather to assemble full weights right before computation and ReduceScatter to return each rank's gradient shard after the backward pass. For an $L$-layer model of size $M$, one unbucketed Distributed Data Parallel (DDP) AllReduce moves $\approx 2M$ bytes in 1 call. Standard FSDP moves $\approx 2M$ bytes across $2L$ calls, while resharding after forward, which discards gathered weights and gathers them again for backward, moves $\approx 3M$ bytes across $3L$ calls (96 calls for 32 layers, derived). Sharding trades memory (Lecture 6) mainly by multiplying per-call startup latencies rather than greatly increasing wire volume.

    \notecue{Watch for}{Calling a full AllReduce when each rank updates only its own shard wastes half the bytes assembling data that every rank discards.}

\section{Pricing}

\mlsysnote{%
  \mlsysnotemeta{1 min}{Core}%
  Examine the ring AllReduce cost equation term by term. It represents Lecture 1's $T_{\text{comm}}$ for one gradient synchronization. Across $N$ ranks reducing an $M$-byte tensor, the ring executes $2(N-1)$ rounds, paying startup latency $\alpha$ per round and sending one $M/N$-byte chunk at link rate $\beta$. The latency term $2(N-1)\alpha$ grows linearly with $N$, whereas the bandwidth term $2\frac{N-1}{N}\frac{M}{\beta}$ saturates near $2M/\beta$ regardless of cluster size. Every optimization in this lecture targets round count, chunk size, or the link rate $\beta$ used per round.

  \notecue{Next}{The next slide identifies the critical chunk size $n^* = \alpha\beta$ across five physical interconnects.}
}
\mlsysfocus{Ring AllReduce time}{%
$T_{\text{ring}} \;=\; \underbrace{2(N-1)\,\alpha}_{\text{one startup per round}} \;+\; \underbrace{2\,\frac{N-1}{N}\,\frac{M}{\beta}}_{\text{one chunk per round}}$\\[0.4cm]
{\normalsize $N$ ranks\quad $M$ bytes per rank\quad $\alpha$ startup\quad $\beta$ bandwidth}}

\begin{frame}{Each link has a size where startup and transfer cost the same}
  \centering
  \only<1|handout:0>{\safeimg[width=0.95\textwidth,height=5.6cm,keepaspectratio]{chunk_step1.pdf}}%
  \only<2-|handout:1>{\safeimg[width=0.95\textwidth,height=5.6cm,keepaspectratio]{chunk_step2.pdf}}
  \mlsyscredit{Collective Communication, table 4 (vendor latency and bandwidth ranges, midpoints) and Napkin Math 5.1.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    To see which term of the ring equation dominates, compare each round's chunk against the link's critical chunk size $n^* = \alpha\beta$, where startup and transfer cost the same (Table 4 midpoints across five interconnects). Below $n^*$, startup latency dominates; above $n^*$, bandwidth dominates. InfiniBand NDR crosses at $1.5\text{ \textmu s} \times 50\text{ GB/s} = 75\text{ KB}$, whereas high-bandwidth NVLink stays latency-bound up to about 0.7 MB. Applying Napkin Math 5.1 to a 25 MB gradient bucket shows how group size shifts the regime. In a 64-GPU ring, each chunk is $25\text{ MB} / 64 = 390.6\text{ KB}$, which sits above 75 KB and is bandwidth-bound. In a 1,024-GPU ring, each chunk shrinks to 24.4 KB, falling below 75 KB into the latency-bound regime where faster links barely help.

    \notecue{Watch for}{Classify a collective by its per-round chunk size $M/N$ rather than the whole-tensor size $M$. A 25 MB bucket is $333\times$ larger than 75 KB yet becomes latency-bound at 1,024 ranks.}

  \mlsyscredit{Collective Communication, \S5.6.1 and \S5.6.2. 1 GB buffer, 64 workers, 50 GB/s. Server time $N M/\beta$ derived; ring byte term 39.4 ms; tree 240 ms (\S5.6.4).}
  \note{%
    \mlsysnotemeta{2 min}{Core}%
    On large, bandwidth-bound payloads, topology sets the byte ceiling, explaining why Uber's parameter server stalled. On the 64-worker, 1 GB scoreboard over 50 GB/s ports, a single parameter server receives 64 GB and returns 64 GB through one port, taking $64\text{ GB} / 50\text{ GB/s} = 1{,}280\text{ ms}$ each way (derived). The ring byte term takes 39.4 ms, which is $32.5\times$ faster and close to $N/2 = 32$, alongside a simple tree at 240 ms (derived in Section 3). Combining $N$ tensors and distributing the result requires moving at least $2(N-1)M$ bytes across all ranks, so at least one rank must send $2\frac{N-1}{N}M$ bytes. The ring meets this bandwidth lower bound, whereas the star topology funnels all traffic through one port.

    \notecue{Watch for}{Sharding parameter servers reduces port concentration only by adding extra server ports, whereas a peer-to-peer ring uses every worker's port automatically.}

    Passing the per-step codec test is not enough when lossy compression slows convergence. The run-level scenario in \S5.9.5 takes 100,000 baseline steps with 300 ms of compute per step. Compression cuts communication $4\times$, yet requires 10\% more steps (110,000) to reach the same validation quality. Before reading on, predict whether compression shortens total training time on a slow network (200 ms communication) and on a fast network (30 ms communication).

    \notecue{Check}{Compression wins on the slow network and loses on the fast one. On the slow network, uncompressed training takes $100\text{k} \times 500\text{ ms} = 50{,}000\text{ s}$, whereas compressed training takes $110\text{k} \times 350\text{ ms} = 38{,}500\text{ s}$, or 23\% faster. On the fast network, uncompressed takes 33,000 s, whereas compressed takes $110\text{k} \times 307.5\text{ ms} = 33{,}825\text{ s}$, or 2.5\% slower, because the step-time saving ($22.5 / 330 = 6.8\%$) cannot offset 10\% extra steps. A tempting error is judging by the $4\times$ communication speedup rather than wall-clock time to matched target quality.}

      \centering\mlsyssteps[width=\textwidth,height=4.7cm,keepaspectratio]{errfb_step}{3}

  \mlsyscredit{Collective Communication, Example 5.2 and tables 10 and 11.}
  \note{%
    \mlsysnotemeta{2.5 min}{Core}%
    To keep aggressive compression from adding extra steps or stalling learning, error feedback carries dropped values forward instead of discarding them. Example 5.2 tests an integer-rounding compressor in which any gradient below 0.5 rounds to zero. Across five steps whose values ($0.4, 0.3, 0.2, 0.4, 0.3$) sum to 1.6, naive rounding sends 0 every step and prevents learning. Error feedback retains the dropped residual $e = +0.4$ locally at step 1, so adding $e$ pushes $g + e$ past 0.5 at steps 2 and 5, firing transmitted green pulses of 1. For a constant 0.3 gradient, roughly three 1s fire every ten steps. At every step, the transmitted total plus the stored residual conserves the true sum, giving $2 + (-0.4) = 1.6$.

    \notecue{Watch for}{Error feedback is not automatic inside generic quantization hooks. The runtime must allocate memory to store and accumulate residuals per parameter.}

\begin{frame}{Overlap hides each reduction under the next layer's backward}
  \centering
  \mlsyssteps[width=0.95\textwidth,height=4.35cm,keepaspectratio]{overlap_step}{3}\\[0.05cm]
  {\small Faster buckets: 9 buckets/layer $\times$ 0.85 ms $=$ 7.6 ms hides under 15 ms backward; exposed time is what remains.}
  \mlsyscredit{Collective Communication, Napkin Math 5.9 and \S5.10.4 (interactive Explore figure: Communication-Compute Overlap). 487.6 ms derived from 9 buckets/layer $\times$ 0.85 ms.}
  \note{%
    \mlsysnotemeta{3 min}{Core}%
    Once payload size is set, the second lever hides transfers behind ongoing computation. Because backpropagation flows from the output layer to the input layer, each layer's gradients become ready while earlier layers still compute. Napkin Math 5.9 models 32 layers with 15 ms of backward compute each. Sequential execution adds 480 ms of compute to $32 \times 27\text{ ms}$ of communication for 1,344 ms total. Launching each 27 ms reduction immediately leaves a 12 ms backlog per layer because $27 > 15$ ms, plus the unhidden final reduction, totaling $480 + 27 + 31 \times 12 = 879$ ms, or 34.6\% faster. Switching to the hierarchical schedule cuts each layer to 9 buckets of 100 MB at 0.85 ms, or 7.6 ms, fitting under 15 ms of backward compute. Only the final layer's 7.6 ms stays exposed, giving 487.6 ms total (derived) and maximizing the Fleet Law's $T_{\text{overlap}}$.

    \notecue{Watch for}{Even with ideal overlap, at least the final bucket's communication remains exposed after the backward pass finishes.}

\begin{frame}{Takeaways}
  \small
  \begin{itemize}\setlength{\itemsep}{0.15cm}
    \item Choose the narrowest contract the next computation consumes.
    \item Each round pays $\alpha$ on a chunk of $M/N$; the ring sends the minimum bytes in $2(N-1)$ rounds.
    \item Trees cut rounds; hierarchy shrinks the slow tier's payload to $M/G$ when each GPU has its own port.
    \item An AllToAll finishes when its hottest receiver or its narrowest cut finishes.
    \item Compression and overlap act on what remains; judge them by step time and time to quality.
  \end{itemize}
  \note{%
    \mlsysnotemeta{1 min}{Core}%
    Together, these five rules answer the driving question of how long $N$ accelerators take to agree on a gradient and which algorithm to choose. Pick the narrowest collective contract, price $2(N-1)$ ring rounds on $M/N$ chunks, cut rounds with trees and slow-tier bytes to $M/G$ with hierarchy (where $G$ is the number of GPUs per node, assuming one port per GPU), bound AllToAll by its hottest receiver or narrowest cut, and judge compression and overlap by wall-clock time to matched quality.

\begin{frame}{Open questions}
  \normalsize
  \begin{itemize}\setlength{\itemsep}{0.35cm}
    \item In-switch reduction moves arithmetic into the network. Which other parts of a training step belong there?
    \item Routing skew is set by the data. Should the router balance load, or should the fabric absorb skew?
    \item Overlap needs memory for in-flight buffers. When does hiding communication cost more memory than it saves time?
  \end{itemize}
  \note{%
    \mlsysnotemeta{0.5 min}{Optional}%
    Three open engineering trade-offs extend the mechanisms of this lecture. The first weighs in-switch SHARP reduction, which sums packets inside network switches, against operator and precision limits and limited switch memory for active reduction trees (\S5.7.3). The second asks whether auxiliary load-balancing losses, extra training penalties that spread tokens evenly, should reshape MoE models to protect the network (Lecture 6). The third balances the memory cost of in-flight overlap buffers against saved step time.
