# Volume IV: buildable lab sequence

**Status:** One-axis fallback assignment blueprint, not a released student kit. The proposed primary course is the [SO-101 sequence](../curriculum/so101-uno-q-course.md) under the [course operating plan](../curriculum/course-architecture.md). This reference sequence remains available if the SO-101 STM32-to-servo command path does not work. The [staff build brief](../staff/staff-build-brief.md) states what must work before release; the [candidate kit](../staff/kit-bom.md) lists station parts and modular attachments. Numeric motion and timing limits must come from a pilot on the exact station.

## One station, one reference task

Staff supply an assembled, guarded, low-force pointer driven only by the UNO Q microcontroller; a home and position sensor, with a staff-qualified SPI angle sensor for comparison; a separate motor supply and physical cutoff; a fixed USB camera with repeatable lighting; and a target placed at several positions within a marked arc. The Linux processor captures an image and runs a pinned Hugging Face vision model locally. Its output proposes **one bounded step or abstention**. The microcontroller checks the request, moves the pointer, and reports measured motion. The next image tests whether target–pointer error fell. Staff set the target speed below the measured loop rate and verify that the learned model has a meaningful advantage over a simple image rule under some tested visual conditions.

The teaching package starts with a known-good board image, a pinned model and preprocessing artifact, a small labeled starter dataset and LeRobot-compatible episode, a simple nonlearned image rule, a Bridge proposal stub, an MCU motion sketch, a trace recorder, a fitted one-axis Python simulator, a MuJoCo model of the same axis, an SPI sensor wiring guide, a custom LeRobot `Robot` adapter or converter, ACT and SmolVLA exercises from staff-provided SO-101 or simulated episodes, and recorded traces for hardware outages. Students modify and test these pieces. The first six labs use the pointer station even when a team intends a different capstone. Optional inspection-stage, retained-carrier, and SO-101 arm paths enter only after staff qualify their geometry, power, and authority boundaries. Teams choose a project by week 2 and use its data and measurement plan during the common labs when its attachment is ready.

The common trace links a task epoch, MCU-issued observation cycle ID, frame ID, model revision, model output, proposal sequence, MCU receipt and decision, measured position, and the next frame. The MCU starts a local deadline when it issues a cycle ID and accepts a proposal only for the current cycle. Linux capture time is recorded for performance analysis, not treated as an independently trusted MCU safety timestamp. This contract still cannot prove that Linux used a fresh camera frame. Staff freeze the trace schema and supply a passing example before the first lab.

## Six common labs: get to a physical AI loop

| Week | Starting state and student experiment | Deliberate failure | Exit check |
|---:|:---|:---|:---|
| **1. Boundary and safe state** | With motor power disconnected, trace camera → Qualcomm inference → Bridge → STM32 permission → motor driver → sensor. Boot, reset, and use the cutoff while observing the driver enable and sensor state. Apply the book's three-part scope test to the reference task and the team's proposed task. | Stop the Linux process during a synthetic proposal. | An annotated authority and power diagram, observed power-off state, and a project direction. No unexplained actuator enable. |
| **2. Characterize the plant and its sensors** | On the guarded station, home the axis, command small turns within the staff-set envelope, and compare servo position, an MCU-read SPI angle sensor, and the camera. Record sample rates, units, disagreement, settling, repeatability, and duty. Fit a one-axis Python simulator to part of this data, then predict held-out motion. Choose a project and its observable outcome. | Disconnect the SPI sensor under staff-defined conditions; interrupt a move with the cutoff and compare the simulated prediction with the actual stop. | A project charter, pin/voltage and sensor contract, measured motion envelope, simple simulator, prediction error, and recovery procedure. |
| **3. Give the MCU authority** | The MCU issues an observation cycle ID and starts a local deadline. Send synthetic proposals from Linux with that ID, task epoch, sequence, and requested step. The MCU checks its own state, deadline, and measured travel before energizing the driver; Linux never writes motor pins. Trace permission and refusal. | Repeat a sequence, use an expired cycle ID, exceed the limit, and stop Linux during a request. | A proposal schema, MCU state diagram, and traces showing one accepted move and each refused case. |
| **4. Build physical data** | Capture target and pointer frames at recorded angles, including varied backgrounds, illumination, and occlusions. Map observations and actions to a LeRobot-compatible episode; preserve proposed, permitted, and measured actions in explicit fields or a linked trace. Keep entire capture sessions out of the training split. Run a simple image rule on the same held-out set. | Change lighting or partly hide the target and measure the rule's failure. | A dataset manifest and card, linked image/action/position records, one replayable episode, a held-out split, and a rule baseline. |
| **5. Run the Hugging Face model on the Q** | Export the staff-pinned model with its preprocessing, compare host and ONNX outputs on the same held-out frames, then run inference on the QRB2210 CPU and log memory and latency. Students can fine-tune off board if the project needs new classes. | Use an intentionally wrong color order or normalization, then locate the discrepancy. | A reproducible model revision and processor configuration, output comparison, on-board trace, and model card. Inference must occur on the Q. |
| **6. Close the first loop** | Randomize target and pointer starts. Capture, infer, request at most one bounded move, accept or refuse it on the MCU, and capture again. Continue until the pointer reaches the target or the system abstains. Repeat from comparable starts with the image rule and no-action baseline. | Move the target after apparent convergence or withhold the second frame; the system must respond to new evidence and never claim an unobserved result. | A live observation → model → permission → motion → observation trace, physical outcome comparison, and a week-6 feasibility verdict. |

Week 6 is the first complete physical AI demonstration. A team advances only if a learned output can change an admissible physical action, the action changes or tests the next observation, and the MCU can refuse it. If its custom project misses this demonstration, the team continues on the reference follower while narrowing the project.

## Eight project studios: turn the loop into evidence

All teams run the same experiment type on their chosen fixture. The reference follower gives a working fallback and makes results comparable.

| Week | Student experiment | Deliberate failure | Exit check |
|---:|:---|:---|:---|
| **7. Freshness and learned dynamics** | Add frame identity, task epoch, and expiring intent. Fit a small learned next-state model from physical episodes; build or modify the staff MuJoCo model to share the simple simulator's observation/action adapter. Compare one-step and rollout predictions from all three on held-out hardware traces. | Replay a proposal after reset in both simulators and on the real MCU; introduce a measured perturbation that the learned model has not seen. | Old work cannot cause motion; matched rollouts expose the prediction errors and domain limits of each model. |
| **8. Feedback and simulator transfer** | Run the same bounded policy in the simple simulator, MuJoCo, and on the real station from matched starts. Compare open-loop moves with observing measured position or image error after each move. | Omit one planned step in simulation and on the guarded rig while keeping motion within the safe envelope. | The feedback run detects and handles the discrepancy; the report quantifies simulation-to-hardware error and explains which modeled assumption failed. |
| **9. Policy families and placement** | With staff-provided SO-101 or simulated episodes, evaluate a LeRobot ACT policy and a task-matched SmolVLA policy or recorded policy trace. Compare short action chunks with stepwise correction and test whether changing the instruction changes the VLA action. Separately compare two compact model settings on the Q and examine the staff's local SmolVLA memory and timing report; measure capture, inference, Bridge, decision, motion, and next observation under load. | Let an old action chunk continue in replay after the scene changes; add controlled Q CPU load until proposals expire. | A policy-family comparison, accuracy/latency tails, refusal rate, and evidence-based verdict on what can execute on the Q. A physical SO-101 or on-board SmolVLA rollout requires a separate staff pilot. |
| **10. Permission under faults** | Probe malformed, duplicate, stale, and out-of-envelope proposals and camera or Linux loss. Check driver and position traces, not just return codes. | Deliver a previously valid request while the operator state is disarmed. | The MCU refuses every prohibited move and the team repairs any counterexample. |
| **11. Human interruption** | Stop a running task with the physical cutoff, reset, rehome, and deliberately rearm for a new epoch. | Queue a proposal before the interruption and deliver it after rearm. | No queued movement executes; the new task requires fresh evidence. |
| **12. Failure, correction, and fault exchange** | Another team runs a documented fault script on the rig or trace replay: occlusion, camera disconnect, staff-simulated position feedback loss, delayed frame, or incomplete travel. Record a human correction or new demonstration, revise the dataset or policy, and repeat a matched physical trial. | Repeat the fault after the repair or policy revision. | Before-and-after physical outcomes show what changed and which failure remains unresolved; a new model metric alone is insufficient. |
| **13. Evidence for a bounded claim** | Freeze code, model, preprocessing, target set, simulator parameters, and trial protocol. Repeat randomized trials against the rule and no-action baselines; report success, abstention, moves, time, simulation gap, and fault response. | Include an unfamiliar visual input outside the claimed perception envelope while all motion remains inside the mechanical envelope. | A claim–argument–evidence case supports release, restricted release, or no release within the tested envelope. |
| **14. Unfamiliar trial and defense** | Staff choose an unseen starting condition and one safe seeded fault. The team runs the physical loop and explains each proposal, MCU decision, observation, and outcome. | The seeded fault is disclosed only after the trial. | A trace-backed defense states where the model helped, what the MCU prevented, and what cannot yet be claimed. |

## How the three capstones use the same sequence

| Project | Learned output used by the controller | Observation after action | Principal outcome |
|:---|:---|:---|:---|
| **Active inspection** | Class or condition evidence and uncertainty select decide, turn, or abstain. | Another view and measured stage angle. | Correct decisions with abstention, views, and time. |
| **Slow visual follower** (reference) | Target location proposes a bounded pointer step. | New target–pointer error. | Tracking error, lag, overshoot, and recovery. |
| **Verified routing** | Object class proposes a retained-carrier destination. | Measured carrier endpoint and object position before human removal. | Corrected completion and response to incomplete travel. |

Every team uses the LeRobot episode and policy workflow, but a physical SmolVLA rollout becomes a requirement only after staff prove that it fits the exact UNO Q and task deadline. The stock SO-101 motor bus connects to the Linux host over USB/UART; an SO-101 capstone cannot claim STM32 command veto until staff implement and test an STM32-to-servo command path. A faster Qualcomm execution provider can be explored after staff reproduce the CPU path on the exact board. The teaching team should write executable handouts and set pass thresholds only after completing weeks 1–6 on its reference station.
