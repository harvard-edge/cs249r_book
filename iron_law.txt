
## Iron Law of ML Systems {#sec-introduction-iron-law-ml-systems-c32a}

The physical cost of computational scale becomes concrete in two familiar failures. A training job stalls when storage cannot feed an accelerator; an inference path misses its deadline when model state moves too slowly through memory or across the network. Their symptoms differ, but both consume the same finite time budget through data movement, computation, and fixed overhead. The **iron law of ML systems**\index{Iron law of ML systems!definition}\index{Iron law of ML systems!equation} makes this shared structure explicit by decomposing total execution time $\Time$ (seconds) into those three physical costs (@eq-intro-iron-law):
$$\Time = \underbrace{\frac{\DataVolume}{\Bandwidth}}_{\text{Memory Time}} + \underbrace{\frac{\Operations}{\PeakRate \cdot \EfficiencyHw}}_{\text{Compute Time}} + \underbrace{\Latency}_{\text{Latency Overhead}}$$ {#eq-intro-iron-law}

*This equation is the mathematical spine of this book.* It decomposes the total time required for any ML task, whether training a model for weeks or serving an inference in milliseconds, into three terms that correspond directly to the physical constraints of the dual mandate introduced in @sec-introduction-ai-moment-37f1:

1.  **The memory term** $(\DataVolume/\Bandwidth)$ represents the physical cost of moving bits. $\DataVolume$ is the volume of data moved (bytes), and $\Bandwidth$ is the memory or network bandwidth (bytes/s). Whether loading terabytes from cloud storage or fetching weights from high-bandwidth memory, performance is often limited by I/O physics. Part I develops this foundation.
2.  **The compute term** $(\Operations/(\PeakRate \cdot \EfficiencyHw))$ represents the cost of arithmetic. $\Operations$ is the number of floating-point operations (FLOPs), $\PeakRate$ is the hardware's theoretical peak throughput (FLOP/s), and $\EfficiencyHw$ is dimensionless realized hardware utilization $(0 \le \EfficiencyHw \le 1)$. Parts II and III develop this term.
3.  **The latency term** $(\Latency)$ represents fixed overhead, the irreducible "tax" of system orchestration, networking, and serialization (seconds). This overhead can dominate small, latency-critical requests, where little data moves and little arithmetic runs. Part IV develops this term.

::: {#psp-introduction-iron-law-analogy .callout-perspective title="The iron law analogy"}

The name "iron law" follows Patterson & Hennessy's Iron Law of Processor Performance [@patterson2017hardware]. P&H's law is a *multiplicative decomposition* (a tautology factoring CPU time), whereas this equation is an *additive first-order model* that approximates performance under simplifying assumptions.

The additive form assumes sequential execution. When movement and computation overlap, we replace the sum with their critical-path lower bound in @eq-intro-iron-law-pipelined:
$$T_{\text{pipelined}} \ge \max\left(\frac{\DataVolume}{\Bandwidth}, \frac{\Operations}{\PeakRate \cdot \EfficiencyHw}\right) + \Latency$$ {#eq-intro-iron-law-pipelined}
This max-based formulation reflects hardware that transfers the next block of data while computing on the current one, so the slower of the two stages hides the faster. Equality requires ideal overlap and assumes that $\Latency$ remains outside the overlapped phases.

Even in additive form, the iron law remains useful because, like Amdahl's Law\index{Amdahl's law!diagnostic analogy} [@amdahl1967], its value lies in identifying which physical constraint dominates before optimizing. @Sec-appdx-dam-taxonomy-dam-coordination-sum-max-92bb presents the refined treatment, including pipelining and overlap techniques that transform the additive model into the max-based formulation used in practice.

:::

Decomposing execution time matters only if the engineer can diagnose which term dominates the critical path. The answer depends on how many operations a workload performs per byte it moves, a ratio called arithmetic intensity, relative to the machine's ability to compute and move data. The Roofline Model (@sec-appdx-machine-foundations-roofline-model-2529) names the boundary between its memory and compute limits the **ridge point**\index{Ridge point!definition}. At this stage, the essential comparison is between the time needed to move the data and the time needed to perform the arithmetic; overhead can dominate both. Every optimization technique developed in this book manipulates one of these variables by moving less data ($\DataVolume$), executing fewer operations ($\Operations$), utilizing hardware more effectively ($\EfficiencyHw$), or hiding orchestration delay ($\Latency$). A GPT-3-class training estimate isolates the compute term to show how an efficiency change affects execution time under stated assumptions.

::: {.column-margin .margin-pointer}
↪ The Roofline Model, which bounds attainable throughput by arithmetic intensity and locates the ridge point, is developed in @sec-appdx-machine-foundations-roofline-model-2529.
:::

```{python}
#| echo: false
#| label: gpt3-training
# ┌─────────────────────────────────────────────────────────────────────────────
# │ GPT-3 TRAINING (IRON LAW EXAMPLE)
# ├─────────────────────────────────────────────────────────────────────────────
# │ Context: Callout "Training GPT-3"—worked notebook example
# │
# │ Goal: Apply the Iron Law to estimate large-scale training time.
# │ Show: That improving efficiency from 45% to 60% saves significant accelerator days.
# │ How: Calculate training duration using the dTime formula for GPT-3.
# │
# └─────────────────────────────────────────────────────────────────────────────
from mlsysim import Models, Hardware
from mlsysim.physics import dTime
from mlsysim.fmt import fmt_int, fmt, fmt_flop_rate, fmt_math, check, fmt_count, fmt_percent, fmt_time, MarkdownStr
from mlsysim.core.units import flop, TFLOPs, day, second

# ┌── LEGO ───────────────────────────────────────────────
class GPT3Training:
    """
    Namespace for the 'Training GPT-3' napkin math callout.
    Isolates variables (accelerators, eta) so they do not leak into other scenarios.
    """

    # ┌── 1. LOAD (Constants) ───────────────────────────────────────────────
    m_gpt3 = Models.Language.GPT3
    h_accelerator = Hardware.Cloud.A100

    ops_quantity = m_gpt3.training_ops
    num_accelerators = Systems.Clusters.Training_1K.total_accelerators
    peak_flops_per_device = h_accelerator.compute.peak_flops
    peak_flops_rate = peak_flops_per_device.to(TFLOPs / second)
    eta_base = 0.45
    eta_opt = 0.60

    # ┌── 2. EXECUTE (The Compute) ─────────────────────────────────────────
    days_base = dTime(
        total_ops=ops_quantity,
        num_devices=num_accelerators,
        peak_flops_per_device=peak_flops_per_device,
        efficiency_eta=eta_base,
    ).to(day)
    days_opt = dTime(
        total_ops=ops_quantity,
        num_devices=num_accelerators,
        peak_flops_per_device=peak_flops_per_device,
        efficiency_eta=eta_opt,
    ).to(day)
    days_saved = days_base - days_opt
    _ops_mag = f"{ops_quantity.to(flop).magnitude:.2e}"
    ops_exp_value = int(_ops_mag.split("e+")[1])
    peak_rate_value = peak_flops_rate.to(TFLOPs / second).magnitude

    # ┌── 3. GUARD (Invariants) ───────────────────────────────────────────
    check(days_base > 20 * day, f"Text implies >20 days, got {days_base.to(day).magnitude:.1f}")
    check(days_saved > 5 * day, f"Text claims significant savings, got {days_saved.to(day).magnitude:.1f}")
    check(days_opt < days_base, "Optimization failed to reduce time")

    # ┌── 4. OUTPUT (Formatting) ──────────────────────────────────────────────
    # Text strings
    num_accelerators_str = fmt_count(num_accelerators, commas=True, label="accelerator")
    eta_base_pct_str = fmt_percent(eta_base, precision=0, commas=False, style='prose')
    eta_opt_pct_str = fmt_percent(eta_opt, precision=0, commas=False, style='prose')
    days_initial_str = fmt_time(round(days_base.to(day).magnitude), day, precision=0, commas=False, style="word")
    days_optimized_str = fmt_time(round(days_opt.to(day).magnitude), day, precision=0, commas=False, style="word")
    days_saved_str = fmt_time(round(days_saved.to(day).magnitude), day, precision=0, commas=False, style="word")

    # LaTeX math components
    _ops_coeff = _ops_mag.split("e+")[0]
    peak_tflop_per_s_per_accelerator_str = fmt_flop_rate(peak_flops_rate, unit=TFLOPs / second, precision=0, commas=False)

    # Equation assembly (inline refs use GPT3Training.* form)
    time_formula_math = fmt_math(r"T_{\text{train}} \approx \frac{I/O}{\AcceleratorCount \cdot \PeakRate \cdot \EfficiencyHw}")
    time_value_math = fmt_math(
        rf"\approx \frac{{{_ops_coeff} \times 10^{{{ops_exp_value}}}}}{{{num_accelerators} \times {peak_rate_value:.0f} \times 10^{{12}} \times {eta_base}}}"
    )
    time_days_math = fmt_math(rf"\approx {fmt_int(days_base.to(day).magnitude, commas=False)}\ \text{{days}}")
    ops_math = fmt_math(rf"\approx {_ops_coeff} \times 10^{{{ops_exp_value}}}\ \text{{FLOPs}}")
```

The iron law governs execution time, but time is not the only physical constraint. For battery-powered edge devices and warehouse-scale accelerator clusters alike, energy dissipation and thermal limits often bind the system before throughput limits are reached. Moving bits across the memory hierarchy exacts an **energy tax**\index{Energy tax!definition} that parallels the delay of the memory term.

::: {.column-margin}
![](images/svg/introduction_energy_hierarchy.svg){width="100%" fig-alt="Vertical ladder of three orange bars on a log scale, longest at top: DRAM (Dynamic Random-Access Memory) 160 pJ towers far above FP16 1.1 pJ and INT8 (8-bit integer) 0.2 pJ, showing data movement costs orders of magnitude more energy than arithmetic."}

*Moving a byte costs about 145 times an FP16 op, the data-movement tax.*
:::

Let $\DataVolume$ be the total data volume moved (bytes), $\EnergyPerByteMoved$ the energy per byte moved, $\Operations$ the total operation count, and $\EnergyPerOperationCompute$ the energy per operation. @Eq-energy-cost formalizes this relationship, following the hardware-energy observation that data movement can dominate arithmetic energy [@horowitz2014]:
$$ \TotalEnergy \approx \underbrace{ \DataVolume \times \EnergyPerByteMoved }_{\text{Movement Term}} + \underbrace{ \Operations \times \EnergyPerOperationCompute }_{\text{Compute Term}} $$ {#eq-energy-cost}

```{python}
#| echo: false
#| label: energy-movement-ratios
# ┌─────────────────────────────────────────────────────────────────────────────
# │ DATA MOVEMENT ENERGY RATIOS
# ├─────────────────────────────────────────────────────────────────────────────
# │ Context: Energy Tax paragraph in the Iron Law section
# │
# │ Goal: Keep the data-movement-vs-arithmetic comparison executable.
# │ Show: DRAM byte movement is about 145× FP16 arithmetic and 800× INT8 arithmetic.
# │ How: Compare one off-chip DRAM byte energy with one operation energy.
# │
# └─────────────────────────────────────────────────────────────────────────────
from mlsysim.fmt import fmt_int, fmt, check

# ┌── LEGO ───────────────────────────────────────────────
class EnergyMovementRatios:
    """Compare off-chip data movement energy with local arithmetic energy."""

    # ┌── 1. LOAD (Constants) ───────────────────────────────────────────────
    ENERGY_DRAM_PJ_PER_BYTE = Hardware.Tech.Memory.DRAM.energy_per_byte
    ENERGY_FLOP_FP16_PJ = Hardware.Tech.Op.FlopFp16.energy
    ENERGY_OP_INT8_PJ = Hardware.Tech.Op.OpInt8.energy
    dram_byte_energy = ENERGY_DRAM_PJ_PER_BYTE * byte
    fp16_op_energy = ENERGY_FLOP_FP16_PJ * flop
    int8_op_energy = ENERGY_OP_INT8_PJ * flop

    # ┌── 2. EXECUTE (The Compute) ─────────────────────────────────────────
    fp16_ratio = (dram_byte_energy / fp16_op_energy).to("").magnitude
    int8_ratio = (dram_byte_energy / int8_op_energy).to("").magnitude

    # ┌── 3. GUARD (Invariants) ───────────────────────────────────────────
    check(fp16_ratio > 100, "DRAM byte movement should exceed FP16 arithmetic energy by about two orders of magnitude.")
    check(int8_ratio > 500, "DRAM byte movement should be hundreds of times more expensive than INT8 arithmetic.")

    # ┌── 4. OUTPUT (Formatting) ──────────────────────────────────────────────
    fp16_ratio_mult_str = fmt_multiple(fp16_ratio, commas=False, precision=1)
    int8_ratio_mult_str = fmt_multiple(round(int8_ratio), precision=0, commas=False)
```

Per access, data movement can cost far more than arithmetic, so $\EnergyPerByteMoved \gg \EnergyPerOperationCompute$. Under the energy constants used in this text, moving one byte from off-chip Dynamic Random-Access Memory (DRAM) consumes roughly `{python} EnergyMovementRatios.fp16_ratio_mult_str` the energy of an FP16 multiply and `{python} EnergyMovementRatios.int8_ratio_mult_str` that of an INT8 (8-bit integer) multiply [@horowitz2014]. Whether movement dominates a complete workload also depends on the number and width of transfers relative to its operation count. The physical reason for the per-access gap is that data movement requires charging and discharging wires over longer distances, while arithmetic occurs locally within a processing unit's circuits. Minimizing avoidable data movement $(\DataVolume)$ can therefore improve both speed and energy efficiency. Part III states this per-event comparison as a governing principle of optimization (principle \ref{pri-energy-movement}).

::: {#chk-introduction-iron-law .callout-checkpoint title="The iron law"}

The iron law $(\Time = \frac{\DataVolume}{\Bandwidth} + \frac{I/O}{\PeakRate \cdot \EfficiencyHw} + \Latency)$ is the analytical backbone of this book. Before proceeding, verify you can manipulate its terms:

- [ ] **Memory term $(\DataVolume/\Bandwidth)$**: identify the physical resource that bounds this term and name one workload regime where it dominates.
- [ ] **Compute term $(\Operations/(\PeakRate \cdot \EfficiencyHw))$**: identify the hardware quantity and utilization factor that bound this term.
- [ ] **Latency term $(\Latency)$**: identify which costs remain after data movement and arithmetic have been optimized.
- [ ] **Peak throughput**: holding the other quantities fixed, if you double $\PeakRate$, which term improves, and why does total execution time fall by less than half when movement and overhead also contribute?

:::

The same physical terms that determine time and energy also determine cost: every byte moved, operation executed, and millisecond of latency consumes infrastructure budget. The next test is therefore economic, evaluating whether added compute buys enough model improvement to justify the expenditure.

### Return on compute (RoC) as an economic lens {#sec-introduction-roc-invariant}

In the spirit of quantitative design, **return on compute (RoC)**\index{Return on compute!definition} measures the incremental accuracy gain per added dollar of infrastructure investment, in accuracy points per dollar:
$$ \text{RoC} = \frac{\Delta \text{Accuracy}}{\Delta \text{Compute Cost}} $$

A 1-percentage-point gain in accuracy may fail the RoC test if it requires a 10$\times$ increase in $\Operations$ (total operations); the decision depends on the value of that gain and the available budget. Read through this lens, an optimization can improve the numerator by extracting more signal from the same data or reduce the denominator by lowering execution cost. Its value must still be checked against the system's other requirements. The bitter lesson teaches that scale works, but the iron law governs *how* to afford it.

### Lighthouse models put the iron law into practice {#sec-introduction-lighthouse-models-9b1c}

The iron law organizes the core engineering imperatives of this book. The memory term demands robust ingestion, validation, and feature pipelines. The compute term requires maximizing arithmetic intensity and hardware utilization across specialized accelerator architectures. The latency term forces strict control over serialization delay, communication overhead, and serving jitter. Together, these terms transform abstract system requirements into actionable physical constraints.

Abstract equations become tangible through concrete workloads. Five recurring **lighthouse models**\index{Lighthouse model!definition} serve as diagnostic probes for the iron law throughout this book. These canonical workloads reappear across chapters to test how physical constraints affect distinct architectural patterns. At this stage, the task is to connect each workload to the resource that can limit it; later treatments explain the model structures and execution mechanisms behind those constraints.

Each lighthouse model illustrates a distinct stress case for the iron law under the workload conditions described here:

- **ResNet-50**\index{ResNet-50!iron-law workload} probes compute throughput: by repeatedly reusing learned weight filters across spatial positions and batched inputs, arithmetic throughput ($\Operations/(\PeakRate \cdot \EfficiencyHw)$) dominates execution time.
- **GPT-2/Llama**\index{GPT-2!bandwidth-bound decode}\index{Llama!bandwidth-bound decode} probes memory bandwidth: generating text token-by-token for one request at a time fetches billions of weight parameters from memory with minimal reuse per token, making data movement ($\DataVolume/\Bandwidth$) the binding constraint.
- **DLRM**\index{DLRM!memory capacity bound} probes memory capacity, the iron law's precondition that the workload fits at all: embedding tables mapping millions of user and item IDs reach about a hundred gigabytes in reference models (terabytes in production) and exceed single-accelerator device memory.
- **MobileNetV2**\index{MobileNetV2!definition} and **Keyword Spotting**\index{Keyword spotting!definition} probe latency ($\Latency$) and energy limits: inference must satisfy millisecond deadlines within milliwatt power budgets on battery-powered edge devices and microcontrollers.

The iron law makes these differences actionable. Applying the same equation to two workloads yields opposite optimization strategies: doubling peak compute $\PeakRate$ accelerates compute-bound convolutions like ResNet-50 once reuse amortizes memory access, but leaves memory-bound language generation virtually unchanged; doubling memory bandwidth $\Bandwidth$ accelerates bandwidth-bound generation while leaving compute-saturated convolutions unchanged. @Tbl-lighthouse-examples summarizes why each lighthouse model serves as a diagnostic tool for a specific bottleneck.

The AlexNet system combined a convolutional architecture whose parallel matrix operations matched GPU capabilities with the `{python} ImageNetStats.images_m_str` labeled images in the 2012 ImageNet challenge training split[^fn-imagenet-dataset-scale] [@deng2009]. #| echo: false
```{python}
#| label: training-compute-growth-summary
# ┌─────────────────────────────────────────────────────────────────────────────
# │ TRAINING SCALE TRANSITION (IRON LAW → EFFICIENCY)
# ├─────────────────────────────────────────────────────────────────────────────
# │ Context: Closing paragraph of Iron Law section (pre-Efficiency Framework)
# │
# │ Goal: State the seven-orders-of-magnitude training-scale gap in one sentence.
# │ Show: GPT-4-class public estimates are about 10^7× AlexNet training compute.
# │ How: Compare illustrative training-compute endpoints.
# │
# └─────────────────────────────────────────────────────────────────────────────
import math
from mlsysim import Literature
from mlsysim.fmt import fmt, check

# ┌── LEGO ───────────────────────────────────────────────
class TrainingScaleTransition:
    """Seven-order training-scale gap cited at the Iron Law → Efficiency transition."""

    # ┌── 1. LOAD (Constants) ───────────────────────────────────────────────
    alexnet_training_flops = next(e["flops"] for e in Literature.ComputeTrend.entries if e["model"] == "AlexNet")
    gpt4_class_training_flops = next(e["flops"] for e in Literature.ComputeTrend.entries if e["model"] == "GPT-4-class")

    # ┌── 2. EXECUTE (The Compute) ─────────────────────────────────────────
    compute_growth_ratio = gpt4_class_training_flops / alexnet_training_flops
    compute_growth_order = round(math.log10(compute_growth_ratio))

    # ┌── 3. GUARD (Invariants) ───────────────────────────────────────────
    check(1e7 <= compute_growth_ratio <= 3e7, f"Expected about 10^7 growth, got {compute_growth_ratio:.2e}.")
    check(compute_growth_order == 7, f"Expected seven orders of magnitude, got {compute_growth_order}.")

    # ┌── 4. OUTPUT (Formatting) ──────────────────────────────────────────────
    compute_growth_order_str = fmt(compute_growth_order, precision=0, commas=False)
```

Co-design across the D·A·M axes means that optimizing one component often shifts pressure to another. AlexNet's co-design success came at a cost affordable in 2012 (two consumer GPUs for a week), but modern foundation models demand training compute roughly `{python} TrainingScaleTransition.compute_growth_order_str` orders of magnitude larger. If the iron law governs *how fast* a system runs, an engineering framework remains necessary to reason about *how efficiently* it uses those resources.
